# local-open-spaces 의사결정 기록 (Decision Log)

## 1. 문서 목적

본 문서는 `local-open-spaces` 프로젝트에서 내려진 주요 기술적·기획적 의사결정을 기록한다.

단순한 결과만 기록하지 않고, 결정 이유와 향후 영향(Roadmap, Architecture, Spec)을 함께 기록한다. 새로운 기능이나 아키텍처 구조를 제안할 때 기존 의사결정과 충돌하는지 확인하는 검수 기준으로 활용한다.

---

# Decision 001

## 제목
서비스 초기 단계는 고비용 서버/인프라 구축 대신 Zero-Cost 기반의 공공 데이터 수집 파이프라인 및 PostGIS spatial DB로 구현한다.

## 결정 내용
`local-open-spaces`는 초기 유료 인프라 구축이나 유료 지도 API 종속을 지양하며, 무료 티어(Zero-Cost) 기술 스택을 바탕으로 정제된 열린 공간 및 시한성 이벤트 데이터를 구축하는 구조로 시작한다.

## 결정 이유
- 초기 서비스 단계에서 고정 서버 비용 지출을 최소화(0원)하여 지속 가능성 확보
- 대한민국 공공 데이터 포털에서 제공하는 7대 공공 API 무료 쿼리 한도 내에서 수집 가능
- Supabase PostGIS 무료 티어 및 Kakao Maps API(일 300,000건 무료) 활용으로 대용량 공간 데이터 연산 및 마커 표현 가능

## 영향
- **현재 구현:** GitHub Actions 기반 주기적 수집 Workflow + Supabase PostGIS Stored Procedure (RPC)
- **미래 확장:** 서비스 이용자 및 검색 쿼리 폭증 시 서버리스 Caching Layer(Upstash Redis 등) 도입 고려

# Decision 002

## 제목
위치 및 거리에 기반한 데이터 처리 및 반경 연산은 클라이언트(JS)가 아닌 Supabase PostGIS DB 엔진 내에서 처리한다.

## 결정 내용
사용자의 위치(Lat, Lng) 기준 반경 검색, 거리 계산(`distance_meters`), 마커 필터링 등의 공간 연산을 클라이언트 JavaScript 코드가 아닌 PostgreSQL PostGIS Stored Procedure(RPC)로 일임한다.

## 결정 이유
- 클라이언트 측 디바이스 연산 부담을 줄이고 메인 지도 렌더링 성능 최적화
- GIST 인덱스를 활용한 Spatial Query로 십만 건 이상의 장소/행사 데이터 중 지정 반경(500m, 1km, 3km) 내의 데이터만 빠르게 리턴 가능

## 영향
- **현재 구현:** `get_nearby_spaces_and_events` Stored Procedure 작성 및 RPC 호출
- **미래 확장:** 공간 재정의 및 다중 지역 경계(Polygon) 검색 시 PostGIS 쿼리 확장만으로 대응 가능

# Decision 003

## 제목
선제적으로 작성된 확장 기능 모듈은 백엔드/프론트엔드 수준에서 작성을 허용하되, 미승인/미오픈 기능은 Feature Flag 기반으로 화면상에 비활성화(Disabled/Hidden) 처리한다.

## 결정 내용
개발 효율성을 위해 향후 확장될 기능(예: 고급 소셜 공유, 맞춤 알림 구독, 마이페이지 저장소 등)을 선제적으로 구현하는 것을 허용한다. 다만, 승인된 Spec 범위 외의 기능은 Feature Flag 제어로 화면 UI에서 노출하지 않는다.

## 결정 이유
- 코드 재작성(Refactoring) 비용 절감 및 모듈형 구조 유지
- 사용자 UX 혼선 방지 및 기획 승인 단계에 맞춘 유연한 피처 플래그 전환 가능

## 영향
- **현재 구현:** Feature Flag 환경변수 또는 Component UI Flag(`is_enabled`)로 노출 제어
- **미래 확장:** 승인 절차 완료 시 플래그 켜기(Toggle On)만으로 즉시 서비스 오픈

# Decision 004

## 제목
반응형 레이아웃은 Breakpoint(`768px`) 기준 Mobile과 Desktop 전용 2단 멀티 레이아웃 시스템을 채택한다.

## 결정 내용
- **Mobile (`< 768px`):** 지도 풀스크린 + 바텀시트(Bottom Sheet) 인터페이스
- **Desktop (`>= 768px`):** 좌측 컨트롤/리스트 패널 + 우측 메인 지도 패널 (2단 Split View)

## 결정 이유
- 모바일 사용자의 손가락 터치 UX와 데스크톱 사용자의 마우스/대화면 탐색 UX의 본질적 차이 수용
- 동일 데이터 기반으로 디바이스에 최적화된 마커/리스트 상호작용 제공

## 영향
- Layout Component 분리 및 Kakao Map SDK `relayout()` 이벤트를 통한 반응형 대응

# Decision 005

## 제목
AI 활용은 공공 API 데이터의 수집 보조 및 카테고리 자동 정제/분류 파이프라인 도구로 한정한다.

## 결정 내용
공공 API의 비정형 텍스트(장소 설명, 행사 내용)를 파싱하고 정제하여 카테고리를 자동 태깅하는 백앤드 데이터 처리 파이프라인 용도로만 AI를 활용한다.

## 결정 이유
- 공공 API 데이터의 정제되지 않은 불명확한 장소/행사 설명 텍스트를 고품질 정형 데이터로 변환
- 검증되지 않은 AI 대화형 서비스나 생성형 기능을 배제하여 가짜 정보 생성을 방지하고 데이터 신뢰성 확보

## 영향
- **현재 적용:** 데이터 자동 분류 및 태깅 파이프라인 구축 (`spec/ai/tagging-rule.md`)

# Decision 006

## 제목
구현 결과물의 검수 및 PR 승인은 기획 Spec 및 프로젝트 방향성 기준으로 기획 AI가 수행한다.

## 결정 내용

## 결정 이유
본 프로젝트의 주요 검수 포인트는 단순히 Syntactic Code Quality를 넘어 기획 의도와 데이터 파이프라인 스펙의 완벽한 일치 여부이기 때문이다.

## 영향
- 검수 프로세스: 기획 Spec 작성 → 구현 AI 코드 작성 → 기획 AI Spec 준수 검수 및 승인

# Decision 007

## 제목
Supabase Auth 계정 권한 관리는 `user_metadata.role` 기반의 RBAC(Role-Based Access Control)을 적용한다.

## 결정 내용
- 관리자 계정 구분을 위해 Supabase Auth의 `user_metadata.role` 메타데이터 클레임(`admin`)을 활용한다.
- `public.is_admin()` 헬퍼 함수를 도입하여 RLS(Row Level Security) 정책을 작성함으로써 일반 사용자가 관리자 전용 데이터 연산 및 관리 기능에 접근하지 못하도록 통제한다.

## 결정 이유
- 별도의 Role 관리 테이블 생성으로 인한 DB 복잡도를 줄이고 Supabase 메타데이터만으로 확실한 보안 격리 구현
- 향후 일반 사용자 커뮤니티 및 관심 장소 저장 기능 확장 시 기존 RLS 구조 손상 없이 유연한 권한 부여 가능

## 영향
- **보안 강화:** `supabase/migrations/*_rbac_admin_role.sql` 작성 및 검증 완료
- **미래 확장:** 사용자 마이페이지 및 장소/행사 북마크 기능 구현 시 역할별 RLS 간편 적용

# Decision 008

## 제목
서비스 방향을 "동네 열린 공간 탐색"에서 "가성비 놀거리 큐레이션(아이·가족 대상)"으로 확장 재정의하며, `docs/spec.md`를 UI/데이터 정책의 Single Source of Truth(SSOT)로 지정한다.

## 결정 내용
- 서비스 모토를 "오늘/이번 주말, 아이·가족과 가성비 있게(0원~1만 원) 뭐 하고 놀지?"로 재정의한다.
- 데이터 수집 범위를 기존 7대 공공 API 중심에서 **80% 공식/공공 API + 20% 보완 크롤링/제휴 API(쿠팡 파트너스, 네이버 쇼핑 등 커머스 핫딜 포함)** 구조로 확장한다.
- 화면 구조를 기존 상단 탭(지도/도감/캘린더)에서 **하단 5탭 고정 내비게이션([추천픽]-[스팟픽]-[이벤트픽]-[찜]-[마이])** 중심으로 재편한다. 기존 지도/도감/캘린더 뷰는 폐기가 아니라 새 탭 구조 안으로 재배치한다 (내주변=지도, 카테고리=기존 도감 그리드 개념 확장).
- 추후 하단 고정 네비게이션 항목은 사용자의 지시로 변동될 수 있음을 명시한다.
- AI 태깅 표준 카테고리를 기존 `PARK/SPORTS/CULTURE`(공간), `FESTIVAL/EXHIBITION/PERFORMANCE/POPUP/RESERVATION`(이벤트) 체계에서 **5대 핵심 카테고리(체험·클래스/야외·자연/전시·박물관/공연·축제/키즈·액티비티)** 로 확장하며, 기존 세부 카테고리는 DB 원본값으로 유지하고 신규 5대 카테고리는 그 위에 얹는 **UI 표시용 매핑 레이어**로 도입한다 (`spec/data/ai-rule.md` 3.3 참고).
- 예약 마감건은 메인 노출에서 제외하고, 오늘/주말 당일 즉시 이용 가능한 정보를 우선 노출한다.

## 결정 이유
- 사용자(기획 담당)가 대화 중 명시적으로 전달한 "최신 통합 규약"에 따른 서비스 피벗 지시
- 기존 문서(`project/overview.md`, `architecture.md`, `spec/common/search.md`, `spec/data/ai-rule.md` 등)에 부분적·비일관적으로 반영되어 있던 이전 자율 루프의 산발적 수정 내역을 하나의 공식 결정으로 정리할 필요

## 영향
- **문서 재정렬 필요:** `project/overview.md`, `project/architecture.md`, `project/data_sources.md`, `spec/data/ai-rule.md`, `spec/common/search.md`, `spec/event/event-card.md`, `spec/space/space-card.md` — 본 결정 반영해 정리 완료 (2026-08-22)
- **코드 마이그레이션 대기 (미착수, 별도 승인 필요):**
  1. DB `category`/`event_type` 원본값은 유지하되, 5대 UI 카테고리 매핑을 프론트엔드/RPC 레이어에 반영
  2. 하단 5탭 내비게이션 + 홈 화면(캐러셀/카테고리 그리드/큐레이션 피드) 신규 구현 — 현재 코드는 여전히 상단 3탭(지도/도감/캘린더) 구조
  3. 쿠팡 파트너스/네이버 쇼핑 등 커머스 핫딜 API 연동 — 현재 미착수
  4. 산림청, 네이버 Local API 등 신규 데이터 소스 수집 스크립트 — 현재 미착수
  5. 요금 오탐 방지 OCR/Fallback 룰(`is_free: true` 기본 추정) — 현재 미구현
- 위 코드 마이그레이션 항목은 범위가 커서 `implementation/todo.md`에 개별 항목으로 분리해 다음 단계에서 순차 진행한다.

# Decision 009

## 제목
`public.events.location`의 `NOT NULL` 제약(Decision 002 연동)을 해제하고, `location_precision` 컬럼(`EXACT`/`CITY_APPROX`/`UNKNOWN`)으로 위치 정밀도를 구분한다.

## 결정 내용
- Task 9-6-1에서 경기데이터드림 API1(`GGCULTUREVENTSTUS`, 3067건)을 실측한 결과, 원본 API 자체에 주소/좌표 필드가 전혀 없어 기존 스키마(`location NOT NULL`)로는 전량 스킵될 수밖에 없었다.
- 사용자가 TITLE/HOST_INST_NM 텍스트에 경기도 시/군명이 일부 포함돼 있음을 직접 확인·제시하며, 다음 방식의 도입을 채팅으로 명시적으로 승인했다(2026-08-23):
  1. 시/군명이 텍스트에서 매칭되는 행은 해당 시/군 중심좌표(근사값)로 `location_precision = 'CITY_APPROX'`를 부여해 노출한다.
  2. 시/군명이 전혀 매칭되지 않는 행도 버리지 않고 `location = NULL`, `location_precision = 'UNKNOWN'`으로 저장해 메인 페이지의 "경기도권 기타" 섹션에서만 노출한다.
  3. 지도/주변 검색(반경 기반 RPC `get_nearby_spaces_and_events`)에는 `location_precision = 'EXACT'`(실제 주소 지오코딩) 행만 노출한다 — 근사/미상 좌표가 지도에 정확한 위치처럼 표시되어 사용자를 오도하지 않도록 한다.
- `events.location`은 `geometry(Point, 4326) NOT NULL`에서 `NULL 허용`으로 변경하고, `location_precision VARCHAR(20) NOT NULL DEFAULT 'EXACT'`(CHECK: 3개 값만 허용, `UNKNOWN`이면 `location`도 반드시 NULL이어야 하는 정합성 CHECK 제약 포함)를 신설한다.
- 기존 `open_spaces`, `events`의 다른 모든 소스(정확한 주소로 지오코딩된 기존 어댑터들)는 영향 없이 `EXACT`로 남는다 — 이 정책은 API1처럼 원본에 위치 정보 자체가 없는 극히 일부 소스에만 적용되는 예외다.

## 결정 이유
- 원본 데이터에 없는 좌표를 지어내는 것(추측)보다는, 정밀도를 명시적으로 구분해 "덜 정확한 데이터도 버리지 않고 노출하되 정직하게 표시"하는 쪽이 제3장 제5조(추측 금지)와 콘텐츠 최대 활용(제2장 제3·4조) 원칙에 더 부합한다.
- Decision 002(PostGIS 공간 연산 DB 처리)가 전제했던 "모든 이벤트는 정확한 좌표를 가진다"는 가정이 실측으로 깨졌음이 확인됐고, 이를 스펙에 정직하게 반영하지 않으면 향후 수집 스크립트가 계속 같은 한계에 부딪힌다.

## 영향
- **Spec 변경:** `project/database_schema.md` 3.2(`events` 테이블) 갱신 필요.
- **마이그레이션:** `scripts/migrations/2026-08-23-*.sql`로 `location` NOT NULL 해제, `location_precision` 컬럼/CHECK 제약 추가, `get_nearby_spaces_and_events` RPC에 `location_precision = 'EXACT'` 필터 추가.
- **코드 영향 범위:** `scripts/ingest/adapters/lib/schema-mapper.mjs`(`buildEventRow` 가드 완화), `scripts/ingest/adapters/gg-culture-events-adapter.mjs`(API1 시/군명 매칭 로직), `src/lib/home/get-home-feed.ts`(위치 미상 이벤트 조회 함수 신설), `src/components/home/home-view.tsx`(신규 섹션), `src/components/map/detail-modal.tsx`(비-EXACT 항목 지도 UI 숨김), `src/types/database.types.ts`.

## Decision 017: 공공데이터 원천 메타필드 직수집, Paging Loop 전수 수집, SVCID NULL 병합 적재 및 정밀 로깅

- **날짜**: 2026-08-25
- **상태**: 승인
- **비고**: 사용자 지시 원문의 "Decision 017" 번호를 그대로 사용한다. 직전 기록은 Decision 013이며 014~016은 본 문서에 존재하지 않는다(별도 세션에서 기록되었을 가능성이 있어 임의로 013a 등으로 재번호하지 않고, 사용자가 명시한 번호를 그대로 채택한다).
- **결정 사항**:
  1. **수집 범위 확대**: 서울시 API 4대 대분류(`문화체험`, `교육강좌`, `체육시설`, `공간시설`) 전수 수집(`진료복지` 제외).
  2. **전수 적재 및 테이블 분리**: 데이터 속성에 따라 `open_spaces`(공간/시설: `체육시설`/`공간시설`) 및 `events`(행사/체험/클래스: `문화체험`/`교육강좌`) 테이블로 적합 매핑하여 저장한다. (사용자 지시 원문의 "spaces" 테이블은 본 프로젝트의 기존 실제 테이블명 `open_spaces`를 가리키는 것으로 해석한다 — 제3장 제5조 추측 금지에 따라 신규 테이블을 만들지 않고 기존 스키마를 그대로 사용한다.)
  3. **SVCID NULL 병합 적재**: 동일 `SVCID` 중복 건 발생 시 1건으로 통합하되, 한쪽 컬럼이 NULL이고 다른 쪽에 데이터가 있다면 존재하는 데이터로 컬럼을 채워 병합(Merge) 적재한다. 이는 (a) 한 번의 수집 배치 내 중복과 (b) 기존 DB에 이미 적재된 행과의 충돌 양쪽 모두에 적용한다.
  4. **Null-safe 원본 적재**: 주소/좌표, 요금, 예약 정보 등 미비 항목이 있더라도 드롭 없이 NULL 적재한다. `source` 원천 정보(예: `seoul_public_reservation`)를 필수 표기한다.
  5. **원천 메타필드 직수집**: 대분류(`MAXCLASSNM`), 중분류(`MINCLASSNM` - 농장체험, 서울형키즈카페, 체육관, 전시 등), 접수기간, 이용기간, 서비스상태(`SVCSTATNM`), 이용대상(`USETGTINFO`), 결제구분(`PAYATNM`)을 DB 고유 컬럼/메타로 적재한다. (구현 시 실제 검증된 API 필드명을 기준으로 하며, 사용자 지시 원문의 필드명과 실측 필드명이 다를 경우 실측값을 따르고 그 차이를 구현 기록에 명시한다.)
  6. **Paging 루프 전수 수집**: API 첫 응답의 `list_total_count` 기반으로 START_INDEX~END_INDEX를 1,000건 단위로 자동 증가시키는 Loop를 구현하여 전체 데이터 건수를 100% 순회/수집한다.
  7. **무중단 예외 처리**: 단일 건 파싱 에러 발생 시 수집 스크립트 중단을 방지하고 건별 try-catch로 skip 처리한다.
  8. **파이프라인 정밀 모니터링**: `docs/pipeline-log.md`에 API별 수집/DB적재 건수, 중복 예외/병합 상세(대상 테이블명, 중복 건수, NULL 병합 건수), 에러 상세(원인별 건수)를 일간 기록한다.
  9. **뱃지/카테고리 정화**: 억지 카테고리 매핑 및 체육/공간시설 '키즈' 뱃지 오매핑을 전면 제거한다. `USETGTINFO`에 유아/어린이/초등학생/가족이 명시되거나 `MINCLASSNM`이 키즈/체험 전용 시설인 경우에만 키즈 뱃지를 부여한다.

### 결정 이유
- 서울시 공공서비스예약 통합 API(`tvYeyakCOllect`)가 문화체험/교육강좌/체육시설/공간시설 등 성격이 다른 데이터를 하나의 엔드포인트로 함께 내려주는 것이 실측으로 재확인되어, 성격에 맞는 표준 테이블로 분리 적재해야 데이터 활용도가 높아진다(제2장 제3·4조 콘텐츠·데이터 중심).
- 기존 구현은 위치/날짜 등 일부 메타데이터가 없으면 행 자체를 드롭했는데, 이는 제2장 제4조(데이터는 핵심 자산)에 위배되므로 드롭 대신 정직하게 NULL로 표시해 보존한다.
- 기존 `체육시설 → KIDS_ACTIVITY` 강제 매핑은 실제로는 성인 대상 체육시설도 다수 포함하는 카테고리를 임의로 좁게 재단한 오매핑이었다(제3장 제5조 추측 금지 위반 사례).

### 영향
- **DB 마이그레이션**: `events`/`open_spaces`에 `source` 컬럼 추가, `events`에 `raw_data` 컬럼 추가, `open_spaces.location`의 `NOT NULL` 해제 및 `location_precision` 컬럼 추가(Decision 009와 동일 패턴을 `open_spaces`에도 적용), `get_nearby_spaces_and_events` RPC의 `open_spaces` 분기에 `EXACT` 정밀도 필터 추가.
- **코드 영향 범위**: `scripts/ingest/adapters/seoul-yeyak-adapter.mjs`(MAXCLASSNM 기준 재분류 및 테이블 분리 적재로 전면 재작성), `scripts/ingest/adapters/lib/schema-mapper.mjs`(`buildOpenSpaceRow`에 `locationPrecision`/`source` 지원 추가, `buildEventRow`에 `source`/`rawData` 지원 추가), `scripts/ingest/adapters/base-collector-adapter.mjs`(다중 테이블 분리 적재를 위한 `targetTable: 'multi'` 모드 및 `transformSplit()` 훅 추가), `scripts/ingest/lib/supabase-admin.mjs`(`upsertRowsSafeMerge`의 배치 내 중복도 NULL 병합하도록 개선), `scripts/ingest/lib/ai-tagging.mjs`(공간형 시설 전용 정밀 키즈 뱃지 판별 함수 추가), `docs/pipeline-log.md`(API별 상세 리포트 블록 추가).
- 기존 24개 어댑터(단일 테이블 대상)는 이번 변경으로 동작이 바뀌지 않는다 — 신규 훅/모드는 전부 opt-in이다.

### Decision 019: 맘스픽(Mom's Pick) 등급/게이미피케이션 & 커뮤니티 체계 도입

- **날짜:** 2026-09-02
- **상태:** 승인 (Approved)
- **Spec:** `spec/community/mom-pick-grades.md`

#### 맥락
Decision 018로 일반 사용자 인증이 도입됨에 따라, 로그인 사용자의 활동(후기/체크리스트 작성)을 기반으로 한 5단계 등급 체계와 등급별 권한 게이팅(커뮤니티 피드, AI 챗봇 무제한 이용, 찜, 반응 확인, 맞춤 푸시 알림, 스포트라이트 노출)을 갖춘 "맘스픽" 커뮤니티 기능이 필요함. 기존 "무로그인 MVP" 지향과 별개로, 로그인 사용자를 대상으로 한 리텐션·기여 유도 장치로 도입한다.

#### 결정 사항
1. **5단계 등급 체계**: 비로그인(Visitor) → 🌱새싹맘 → 🌿열심맘 → 🌳우수맘 → ✨파워맘. 각 등급의 달성 조건과 부여 권한은 `spec/community/mom-pick-grades.md` 1절 표를 따른다.
2. **등급 게이팅 범위**: 맘스픽 커뮤니티 피드 및 마이페이지는 로그인 사용자만 이용 가능하다. AI 챗봇은 비로그인 시 1회 한정 체험, 새싹맘 이상은 무제한이다.
3. **활동 데이터 모델 신설**: 후기/체크리스트(`mom_pick_posts`), 좋아요(`mom_pick_likes`), 찜(`user_bookmarks`), 푸시 구독(`push_subscriptions`) 테이블을 신규 도입한다. 모두 `profiles`와 동일하게 `auth.uid()` 기반 RLS를 적용한다.
4. **"채택" 메커니즘**: 좋아요 수와 별개로, 관리자가 어드민 화면에서 우수 후기를 수동으로 "채택" 지정한다(`mom_pick_posts.is_adopted`/`adopted_at`/`adopted_by`). 우수맘/파워맘 산정의 "채택 수"는 이 값을 기준으로 한다.
5. **등급 산정 규칙**: 달력월 기준(매월 1일 리셋)으로 당월 누적 활동 건수를 매일 배치 재계산한다. 강등은 즉시 적용(유예 없음) — 월초 리셋 시 조건을 다시 채울 때까지 새싹맘으로 내려간다.
6. **마이크로 리뷰/체크리스트 입력 형태**: 마이크로 리뷰는 별점(1~5) + 선택적 한줄 텍스트. 체크리스트는 전 스팟 공통 5항목(주차 편의/수유실 유무/유아의자 유무/키즈메뉴 유무/기저귀교환대 유무)의 boolean 응답으로 고정한다.
7. **파워맘 선발**: "상위 1%" 대신 월간 정원제(기본 10명, 관리자 설정 가능한 값)로 선발한다.
8. **푸시 알림 인프라 신설(MVP 포함)**: 기존 `spec/notification/notification-settings.md`의 알림은 로컬스토리지 기반 인앱 벨(앱을 열어야 갱신)로, "매일 아침/주말에 앱을 안 열어도 오는" 우수맘 이상 전용 요구사항을 충족하지 못한다. 따라서 브라우저 Web Push API 기반의 별도 인프라(서비스 워커, VAPID 키, `push_subscriptions` 테이블, 서버 발송 스케줄)를 신규로 구축한다. VAPID 키는 구현 단계에서 직접 생성해 환경변수로 등록한다.
9. **명시적 비목표(이번 범위 제외)**:
   - 커피 쿠폰(기프티콘) 실물 리워드 자동 발급/지급 연동 — 사용자가 직접 수동 지급하므로 시스템 구현 대상에서 제외한다.
   - 네이버 블로그 검색 API 기반 "블로그 아웃링크 프리뷰" — 추후 별도 Spec으로 다룬다.
   - 어드민 화면의 등급/신고/제재(콘텐츠 모더레이션) 관리 UI — 이번 범위에 포함하지 않는다.

#### 결정 이유
- 로그인 인프라(Decision 018)만으로는 사용자가 지속적으로 콘텐츠(후기/체크리스트)를 남길 유인이 없어, 제2장 제3·4조(콘텐츠·데이터 중심)를 실질적으로 달성하려면 기여-보상 순환 구조가 필요하다.
- 커피 쿠폰 자동화나 네이버 블로그 연동까지 한 번에 구현하면 제1장 제3조(MVP 우선)를 벗어나는 과도한 범위가 되므로, 사용자가 명시적으로 비목표로 지정한 항목은 이번 Decision에서 제외한다.
- 기존 알림 시스템이 실제 푸시가 아님을 실측으로 확인했으므로, "매일 아침/주말 푸시"라는 우수맘 등급 요구사항을 거짓으로 충족한 것처럼 재사용하지 않고 정직하게 신규 인프라로 분리한다(제3장 제5조 추측 금지).

#### 영향
- **신규 Spec 문서**: `spec/community/mom-pick-grades.md` — 등급 매트릭스, DB 스키마 제안, 푸시 인프라 설계.
- **DB 마이그레이션(예정)**: `mom_pick_posts`, `mom_pick_likes`, `user_bookmarks`, `push_subscriptions` 신규 테이블, `profiles.grade` 컬럼 추가.
- **코드 영향 범위(예정)**: 후기/체크리스트 작성 UI, 등급 산정 배치(기존 `run-daily.mjs`류 오케스트레이터에 스텝 추가), 찜/좋아요 UI, 어드민 "채택" 관리 화면, 서비스 워커 + Web Push 발송 배치, 기존 하단 탭/마이페이지에 등급 표시 반영.
- 커피 쿠폰 자동화·네이버 블로그 API·어드민 모더레이션 UI는 이번 Decision의 구현 범위에서 명시적으로 제외되며, 추후 별도 Decision/Spec이 있어야 착수한다.

### Decision 021: 네이버 블로그 검색 API 기반 관리자 "블로그 큐레이션 모달" 도입

- **날짜:** 2026-09-05
- **상태:** 승인 (Approved)

#### 맥락
Decision 019(맘스픽 등급 체계 도입) 9항 "명시적 비목표"에서 "네이버 블로그 검색 API
기반 '블로그 아웃링크 프리뷰' — 추후 별도 Spec으로 다룬다"고 명시적으로 보류했다.
이번에 사용자가 관리자 화면에서 특정 open_spaces 스팟의 키즈/체험 관련 큐레이션을
효율적으로 처리하기 위한 상세 기획(수집 방식/저장 정책/UI 구성/하이라이팅 키워드/
뱃지 11(실측 12)종)을 직접 제시했다 — 이 지시 자체가 그 "별도 Spec"에 해당한다고
판단해 이번 Decision으로 승인·반영한다.

#### 결정 사항
1. **On-Demand 수집**: 관리자가 open_spaces 상세(RawDataModal, open_spaces 탭)에서
   버튼을 눌렀을 때만 네이버 블로그 검색 API(정확도순 sort=sim, 상위 3개)를 호출한다
   — 자동/배치 수집 없음.
2. **1년 룰**: 가져온 3개 글의 postdate를 확인해 전부 1년 이상 지났으면 모달에
   "⚠️ 최근 1년간 후기 없음 — 폐업/방치 검토" 경고를 표시한다.
3. **저장/폐기 정책**: 블로그 본문(텍스트)은 절대 DB에 저장하지 않고 모달이 닫히면
   폐기되는 참고용 데이터다. 블로그 1·2·3의 원본 URL만 `spot_curations`에 저장한다.
4. **저장 대상 확장**: `spot_curations`에 `blog_url_1/2/3`(text), `curation_badges`
   (text[], 11(실측 12)종 중 다중 선택)를 추가한다. "노출 중분류"는 이미 존재하는
   `open_spaces.service_category_id`를 그대로 재사용한다(제5장 제4조 기존 구조 우선 —
   spot_curations에 중복 컬럼을 새로 만들지 않음).
5. **[정정] 인증 실패 원인(당초 오판 → 재확인)**: 최초 구현 시 `.env.local`의
   `NAVER_CLIENT_ID`/`NAVER_CLIENT_SECRET`로 옛 엔드포인트
   (`openapi.naver.com/v1/search/blog.json` + `X-Naver-Client-Id/Secret` 헤더)를
   호출해 `401 NID AUTH Result Invalid`가 났고, 이를 "키/앱 설정 문제"로 오판해
   기록했었다. 이후 사용자가 네이버 개발자센터의 공식 공지(2026-06-29 게시, 2026-
   06-25부로 검색 API가 NAVER Cloud Platform의 "NAVER API HUB"로 이관됨 — 신규
   애플리케이션은 옛 콘솔에서 더 이상 발급 불가)를 제공해, 실제 원인이 키가 아니라
   **엔드포인트/인증 헤더 자체가 바뀐 것**임을 재확인했다. 같은 `.env.local` 키로
   새 엔드포인트(`https://naverapihub.apigw.ntruss.com/search/v1/blog`, 헤더
   `X-NCP-APIGW-API-KEY-ID`/`X-NCP-APIGW-API-KEY`)를 호출하니 200과 함께 실제
   검색 결과가 왔다(2026-09-05 재검증). 응답 JSON 필드 구조(title/link/description/
   bloggername/postdate)는 기존과 동일해 파싱 로직은 변경하지 않았다 —
   `src/app/api/admin/spot-curations/blog-search/route.ts`만 엔드포인트/헤더를
   교체했다. **현재 실제로 정상 동작한다.**
6. **[정정] "본문 텍스트" 범위(당초 추측 → 실측으로 재확인, 2026-09-05)**: 네이버
   블로그 검색 API 자체는 여전히 전체 본문이 아니라 `description`(약 200자 요약
   스니펫)만 제공한다. 다만 당초 이 항에 "실제 블로그 페이지 전체 본문은 대부분
   iframe 안에 렌더링돼 있어 안정적으로 크롤링할 수 없다"고 적었던 것은 **직접
   확인 없이 PC 버전(blog.naver.com)만 근거로 한 추측이었고 틀렸다**(제3장 제5조
   위반 사례로 정직하게 남긴다). 사용자가 "가져온 내용자체도 짧게하고 잘려서"라고
   재차 지적해 직접 재검증한 결과, **모바일 버전(m.blog.naver.com)은 본문
   (`.se-main-container` 또는 구형 `#postViewArea`)이 서버 렌더링된 HTML에 그대로
   들어 있어 안정적으로 추출 가능함**을 확인했다(`src/lib/admin/naver-blog-body.ts`,
   신규 API `GET /api/admin/spot-curations/blog-body`). 이제 블로그 URL이
   blog.naver.com/m.blog.naver.com이면 전체 본문(최대 8,000자)을 가져와 요약 대신
   보여주고, 그 외 출처(티스토리 등, 블로그마다 템플릿이 달라 범용 추출이 어려움)나
   추출 실패 시에만 기존 요약 스니펫으로 조용히 폴백한다. **저장/폐기 정책은 전혀
   바뀌지 않는다** — 이 전체 본문도 DB에 저장하지 않고 화면 표시 후 폐기한다(위
   3항 정책 그대로).
7. **[신규] 검색 결과 품질 문제 확인(실측)**: "호박터숯불촌" 등 실제 스팟명으로
   직접 재현 테스트한 결과, NAVER API HUB의 관련도순(`sort=sim`) 블로그 검색이
   스팸성 블로그(무관한 키워드 나열 게시물)를 상위에 올리거나, 흔한 일반
   검색어에서도 실제 네이버 블로그보다 티스토리 위주로 결과를 편향되게 반환하는
   사례를 여러 쿼리에서 재현 확인했다 — 이는 네이버 API HUB(2026-06-25 신규
   이관, 아직 초기 단계) 자체의 검색 품질 문제로 판단된다. 우리 쪽 쿼리 문구를
   바꿔봐도(따옴표 강제 매칭, 지역명 추가 등) 결과가 달라지지 않았다. 대신
   관리자가 직접 찾은 정확한 URL로 현재 탭을 바꿔치기할 수 있는 "다른 URL로
   바꾸기" 기능을 추가해 실용적인 탈출구를 제공했다. (8항에서 원인을 더
   정확히 좁혔다 — 아래 참고.)
8. **[정정] 정렬 기준을 `sort=sim` → `sort=date`로 교체(2026-09-06)**: 7항에서는
   "쿼리 문구를 바꿔도 결과가 달라지지 않아 교정할 방법이 없다"고 결론지었는데,
   이때 시도한 변형은 전부 `query` 문구뿐이었고 `sort` 파라미터 자체는 바꿔보지
   않았다 — 사용자가 NAVER API HUB 공식 요청 형식 문서를 다시 제시해줘서 `sort`가
   `sim`(기본값)/`date` 두 가지임을 재확인하고 직접 비교했다. 같은 요청에서
   `sort=sim`만 스팸/무관 결과가 나왔고, `sort=date`는 "호박터숯불촌"을 정확히
   다룬 최근 글(2026-08-31~09-05 작성)들이 상위에 정확히 나왔다 — 문제는 우리
   쿼리가 아니라 **NAVER API HUB의 `sim` 랭킹 자체가 지금 저품질**이라는 뜻이었다.
   이 기능의 목적 자체가 "최근 1년 이내 후기가 있는지" 확인이라 `date`(최신순)가
   기능 취지에도 더 맞아, 사용자 확인 후 기본 정렬을 `date`로 교체했다
   (`src/app/api/admin/spot-curations/blog-search/route.ts`). "다른 URL로
   바꾸기" 수동 교체 기능(7항)은 `date`로도 여전히 안 맞는 결과가 나올 수 있는
   경우를 위해 그대로 남겨둔다.

#### 결정 이유
- 사용자가 제시한 요구사항이 Decision 019가 요구한 "별도 Spec" 수준으로 충분히

- 네이버 API 인증 실패와 본문 전체 크롤링의 실제 가능 여부를 추측하지 않고 직접
  호출/확인한 뒤에만 결정에 반영했다(제3장 제5조 추측 금지).

#### 영향

- **신규 API**: `GET /api/admin/spot-curations/blog-search`(네이버 블로그 검색 서버

### Decision 022: 스팟픽 지도 반경 컷오프 폐지 + 노출 중분류(service_categories) 기준 카테고리 필터 전면 전환
- **날짜:** 2026-09-08
- **상태:** 승인 (Approved) — 사용자가 직접 명시적으로 지시.

#### 배경 — 기존 스킵(보류)의 재검토
`implementation/todo.md`(개선사항3-1)로 지시된 "반경 컷오프 완전 폐지 + 도
전역 노출"과 "카테고리 필터를 노출 중분류 기준으로 전면 교체"는 같은 날
먼저 스킵(보류) 처리됐었다:
- 반경 컷오프 폐지는 당시 승인된 `spec/map/spatial-search.md` §2.1("1km/5km/
  10km 중 선택, 10km 초과 탐색 금지")·§3.1(반경 내 1,000개 초과 시 안내)과
  정면 충돌했다.
- 노출 중분류 기준 전면 전환은 실측(`open_spaces` 142,118건 중
  `service_category_id` 매핑 3,982건 = 2.8%) 결과, 그대로 전환하면 전체
  스팟의 97.2%가 모든 카테고리 필터에서 사라지는 회귀였다.

사용자가 두 스킵 모두에 대해 직접 확인 후 이번 결정으로 명시적으로
재승인했다: "반경 컷오프 완전 폐지 + 도 전역 노출로 해줘(지도에 찍히는 거
기준).. 현재 노출 중분류 기준으로 카테고리 필터 전면교체할것.. 지금
관리자화면에서 데이터들에 대하여 노출 중분류 기준으로 매핑중임.. 추후에
대부분 필요한 데이터 매핑하더라도. 현재 기준 약 20% 데이터만 남지 않을까
싶음" — 낮은 커버리지를 인지한 상태에서 그 트레이드오프를 감수하겠다는
의사결정이다.

#### 결정 내용
1. **`spec/map/spatial-search.md` §2.1/§3.1 개정**: 스팟픽 지도(`/nearby`)의
   반경 선택/컷오프 정책을 폐지한다. 노출 중분류를 선택하면 지도에는 반경
   제한 없이 전국 단위로 해당 중분류의 전체 스팟을 표시한다(§3.1의 "1,000개
   초과 시 최상위 1,000개만 렌더링 + 안내 토스트" 정책은 유지 — 전역 데이터
   양이 많아질 경우를 대비한 안전장치로 그대로 재사용 가능하다는 것을 확인함).
2. **카테고리 필터 데이터 출처 전면 교체**: 표준 중분류(`category_min`) 기반
   `CORE_SPOT_CATEGORIES`(2026-08-28~29 도입) 대신, 관리자가 직접 큐레이션하는
   노출 중분류(`service_categories`/`open_spaces.service_category_id`)를
   스팟픽 지도의 유일한 카테고리 출처로 쓴다. 대분류(parent_category)→중분류
   (category_name) 2단 바텀시트 UX 골격은 기존 것을 그대로 재사용한다.
3. **바텀시트 반경 선택(5/10/20km)**: 지도(전역 노출)와 별개로, 바텀시트
   결과 리스트는 사용자가 5/10/20km 중 고른 반경 내에서 실시간 GPS 위치
   기준 거리순으로 정렬해 보여준다.
4. **`CORE_SPOT_CATEGORIES`(category_min 기반)는 폐지하지 않는다**: 관리자
   화면(`spot-curations-panel.tsx`의 "키즈친화 식당" 후보 목록 조회 등)은
   여전히 표준 중분류 기준으로 동작해야 하므로 그대로 둔다 — 이번 결정은
   "스팟픽 지도의 소비자 노출 카테고리"에 한정된다.

#### 결정 이유
- 사용자가 낮은 커버리지(2.8%, 추후에도 ~20% 예상)를 명확히 인지하고 그
  트레이드오프를 직접 승인했다 — 더 이상 "임의 판단"이 아니라 명시적
  의사결정이다(제3장 제5조의 취지는 "확인 없이 넘겨짚지 않는 것"이지 사용자가
  이미 확인한 사안까지 재차 보류하는 것이 아니다).
- 노출 중분류는 관리자가 실제로 큐레이션(뱃지/가격/이미지 등)한 스팟만
  매핑되므로, 스팟픽에 이 기준으로 노출되는 스팟은 자동으로 "이미 검수된
  양질의 데이터"만 남는다 — 콘텐츠 품질 우선(제2장 제3조)과 부합한다.
- 노출 중분류당 매핑 건수가 표준 중분류보다 훨씬 적어(최대 2,304건 vs
  표준 중분류 최대 57,692건 실측) 반경 컷오프를 없애도 §3.1의 1,000개
  렌더링 상한 정책이 그대로 안전하게 작동한다.

#### 영향
- **신규 RPC**: `get_spots_by_service_category(p_service_category_id)` —
  반경/거리 조건 없이 `service_category_id` 등치 조건만으로 전국 조회
  (`scripts/migrations/2026-09-08-get-spots-by-service-category-rpc.sql`).
- **신규 API**: `GET /api/nearby/service-categories`(공개, 노출 중분류
  목록+카운트 — `service_categories`는 RLS+정책 없음이라 서비스 롤 필요).
- **삭제**: `GET /api/nearby/spot-category-counts`와
  `getSpotCategoryMinCounts`(표준 중분류 카운트) — 스팟픽에서 더 이상 쓰지
  않아 완전히 고아 코드가 됐다(다른 어떤 화면도 참조하지 않음을 확인 후 삭제).
- **코드 영향**: `map-explorer.tsx`(카테고리 선택 시 데이터 소스/지도 줌
  레벨/바텀시트 반경 분기 추가), `spot-category-filter.tsx`(데이터 출처를
  `CORE_SPOT_CATEGORIES`→`service_categories`로 교체, 반경 선택 UI 추가),
  `get-nearby.ts`(`getSpotsByServiceCategory` 추가).
- `spec/map/spatial-search.md` §2.1/§3.1을 이 Decision에 맞춰 개정.

### Decision 023: 스팟픽 지도 노출 중분류 데이터를 "전국"에서 "현재 위치의 도(道) 단위"로 축소

#### 맥락
Decision 022로 "노출 중분류 선택 시 지도는 반경 컷오프 없이 전국 단위 노출"로
정했으나, 사용자가 이후 실사용에서 "판교원로 68(경기도 성남시 분당구)에서
어린이 도서관을 골랐는데 대구·세종 스팟까지 지도에 찍힌다 — 확인 필요"라고
지적했다(implementation/todo.md 개선사항2-5).

사용자가 이번에 명시적으로 판단을 내렸다: "반경 컷오프(10/20/30km) 폐지는
유지하되, 각 노출 중분류를 선택해서 보여주는 데이터는 **현재 설정한 위치가
포함하는 도(道) 단위**의 데이터로 제한한다. 판교원로 68 → 경기도 + 서울시.
강릉이 현재 위치면 강원도 내 데이터. 노출 중분류 기준이라 도 단위 데이터가
충분히 커버 가능한 범위로 보여진다."

#### 결정 내용
1. **반경 컷오프 폐지는 그대로 유지**(Decision 022 그대로) — 5/10/20/30km 등의
   반경 선택으로 지도 마커를 자르는 정책은 없다.
2. **노출 중분류 선택 시 지도/리스트 데이터 범위**: "전국"이 아니라 **사용자가
   설정한 현재 위치가 속한 광역(도/광역시)** 단위로 제한한다.
   - 특례: **경기 ↔ 서울은 서로 포함**한다(판교 등 경계 생활권 반영 — 사용자
     지시 "경기도 + 서울시"). 그 외 광역은 자기 자신만 노출한다.
   - 현재 위치의 광역을 판별할 수 없으면(주소/시군구명에 광역 표기 없음) 필터를
     걸지 않는다(안전 폴백 — 근거 없이 스팟을 숨기지 않음, 제3장 제5조).
3. **구현 방식**: RPC(`get_spots_by_service_category`)는 그대로 두고, 반환 결과를
   **클라이언트(`map-explorer.tsx`)에서 광역 기준으로 필터**한다. 노출 중분류당
   매핑 건수가 적어(Decision 022에서 실측 최대 2,304건) 도 단위 데이터를
   클라이언트가 받아 거르는 부담이 무시할 만하고, RETURNS TABLE 변경("cannot
   change return type") 리스크를 피한다.
4. **바텀시트 리스트/건수는 도 단위 필터와 독립 — 순수 반경 기준**: 사용자
   추가 확정 — "바텀시트는 지도 마커 도단위 표시와 다르게 반경 설정이 따로
   있으니 반경 기준으로 나오는 게 맞다. 도단위 사전 필터 없이." 따라서 바텀시트
   리스트/상단 건수(`mobileSheetItems`)는 **광역 필터 이전의 `categoryItems`**를
   소스로 쓰고 선택 반경(5/10/20km)으로만 좁힌다 — 도 경계에 걸친 인접 스팟도
   반경 안이면 포함된다. 도 단위 제한은 지도 마커(위 2번)에만 적용한다.
   (2026-09-10 Step 93의 "GPS 없어도 설정 위치 기준 반경 필터" 수정은 그대로.)

#### 결정 이유
- 사용자가 실사용 후 "대구/세종까지 찍힌다"는 구체적 회귀를 직접 지적하고,
  대안(도 단위 제한 + 경기·서울 특례)을 명시적으로 지시했다 — 임의 판단이 아니다.
- 노출 중분류는 관리자 큐레이션 대상만 매핑되므로 도 단위로 좁혀도 "볼 게 없는"
  회귀가 나지 않는다(콘텐츠 품질·밀도 모두 확보).

#### 영향
- **신규**: `src/lib/spaces/province.ts`(주소/시군구명 → 광역 정규화,
  `getVisibleProvinces`, `isSpotInProvinces`) + 단위 테스트.
- **코드 영향**: `map-explorer.tsx` — `provinceScopedCategoryItems` useMemo로
  `categoryItems`를 현재 위치 광역 기준 필터. `baseItems`/`visibleItems`(지도
  마커·데스크톱 목록)/`isEmptyByFilter`는 이 값을 사용하고, `mobileSheetItems`
  (바텀시트 리스트·건수)는 광역 필터 이전의 `sheetSourceItems`(= `categoryItems`)를
  써서 반경으로만 좁힌다.
- `spec/map/spatial-search.md` §2.1을 이 Decision에 맞춰 개정(§3.1 마커 상한/
  클러스터링 정책은 변경 없음).
- **후속(범위 밖)**: 대분류 바텀시트의 노출 중분류별 카운트(`/api/nearby/
  service-categories`)는 여전히 전국 카운트다 — 광역 스코프 카운트로 맞추는
  것은 별도 작업.

### Decision 024: SEOUL_YEYAK 체육시설/공간시설(대관·사전예약제) 데이터를 open_spaces에서 events로 재라우팅 — Decision 017 2항 개정

- **날짜:** 2026-09-11

#### 맥락

#### 결정 내용

#### 결정 이유

### Decision 028: 문화센터 강좌 데이터를 마트/백화점 5개 브랜드 전제로 단일 통합
테이블(`culture_club_classes`)로 재설계 — 2026-10-04 "표준화 금지" 결정을 보강

- **날짜:** 2026-10-06
- **상태:** 승인 (Approved) — 사용자 직접 지시.

#### 맥락
2026-10-04(`emart_culture_club_classes`/`lottemart_culture_club_classes` 테이블
생성 당시)에는 "각각을 억지로 같은 규격으로 표준화하지 않는다 — 공유는 화면/찜
메커니즘 레벨에서만"으로 결정했었다(브랜드가 2개뿐이고 3번째 브랜드 계획이
아직 없던 시점). 이번에 사용자가 "AK플라자/신세계/현대백화점까지 최소 5개
브랜드로 문화센터 데이터를 모을 것"이라는 확정된 사실을 전제로, 통합검색
("롯데마트/이마트 구분 없이, default는 전체")과 찜·찜알림 기능을 5개 브랜드로
확장 가능한 구조로 재검토해달라고 요청했다.

뷰(VIEW, UNION ALL) 방식과 물리적 테이블 통합 방식을 비교 제안했고, 뷰는
검색/조회만 통합되고 찜(`user_bookmarks`)·관리자 패널·상태감시 스크립트는
브랜드마다 계속 복제돼야 한다는 한계를 짚었다 — 사용자가 이 트레이드오프를
확인한 뒤 "확신은 못하겠지만 제안한 대로 하라"고 최종 승인했다. **이 결정이
2026-10-04 결정을 대체한다** — 당시엔 몰랐던 "5개 브랜드 확정"이라는 새 사실에
근거한 재검토이며, 추측이나 임의 변경이 아니다.

#### 결정 내용
1. **`culture_club_classes` 단일 테이블로 통합**: `brand`(emart/lottemart/
   ak_plaza/shinsegae/hyundai) + `source_class_id`(원본 class_id, 브랜드
   스코프) + 공통 정규화 컬럼(2026-10-06 개선사항2·3·5에서 이미 만든
   `min_age_months`/`max_age_months`/`schedule_start_date`/`schedule_end_date`/
   `schedule_days_code`/`round`/`total_sessions`/`normalized_status`/
   `instructor_name` 등)을 실제 타입 컬럼으로 둔다.
2. **브랜드 전용 필드는 `raw_extra jsonb`로**: 검색/필터 조건으로 쓰이지 않는
   브랜드별 특이 필드(이마트의 `channel_online`/`occupied_full_flag`, 롯데마트의
   `like_count`/`discount_badge_text` 등)는 공통 컬럼으로 승격하지 않고 JSONB에
   보관한다 — 상세보기 참고 정보 용도뿐이라 타입 컬럼을 브랜드마다 계속 늘리는
   것보다 낫다.
3. **`user_bookmarks`도 FK 통합**: `emart_class_id`/`lottemart_class_id`(브랜드
   늘어날수록 컬럼이 계속 늘어나는 구조)를 `culture_club_class_id` 하나로
   합친다. `spot_id`/`event_id`는 별개 도메인이라 그대로 둔다.
4. **수집(ingest) 스크립트의 독립성은 그대로 유지**: 각 브랜드의 스크래핑/파싱
   로직은 전혀 건드리지 않는다 — 마지막 upsert 대상 테이블만 통합 테이블로
   바뀐다. 한 브랜드의 수집 실패가 다른 브랜드의 수집에 연쇄 영향을 주지
   않아야 한다는 요구사항(사용자 명시)을 만족하려면, 통합 후에도 브랜드별
   스크립트/스케줄(GitHub Actions 워크플로 또는 로컬 PC 작업)이 서로 완전히
   독립적인 프로세스로 남아야 한다 — 하나의 "전체 실행" 오케스트레이터로
   묶지 않는다.
5. **찜 상태감시는 통합하되 브랜드별로 분기**: 찜(`culture_club_class_id`)이
   어떤 브랜드 강좌인지 `culture_club_classes.brand`로 먼저 식별한 뒤, 그
   브랜드 전용 "현재 상태 재확인" 로직(이마트는 API 재조회, 롯데마트는 상세
   페이지 스크래핑 — 사이트마다 다름)으로 분기한다. 한 행의 재확인 실패가
   다른 행/다른 브랜드의 재확인까지 중단시키지 않게(행 단위 try/catch 유지)
   한다.

#### 결정 이유
- 뷰는 "조회 통합"만 풀어주고, 찜/알림/관리자 패널처럼 "쓰기 또는 브랜드별
  분기 로직이 필요한 기능"은 브랜드 수만큼 복제되는 구조가 그대로 남는다 —
  5개가 되면 이 복제가 유지보수 비용의 실제 핵심이 된다.
- 공통 정규화 스키마(2026-10-06 개선사항2·3·5)가 이미 완전히 다른 두 수집
  방식(GraphQL API vs HTML 스크래핑)에서 성공적으로 동작을 검증했다 — 백화점
  문화센터도 결국 제목/지점/요일/시간/연령/상태/강사/수강료라는 같은 개념을
  다루므로 일반화 가능하다고 판단했다.
- 지금(브랜드 2개, 약 2만 1천여 건) 마이그레이션하는 비용이 브랜드 3개가 더
  붙은 뒤 마이그레이션하는 비용보다 훨씬 작다.

#### 영향
- **DB**: 신규 `culture_club_classes`(+ 인덱스/RLS), 기존 `emart_culture_club_
  classes`/`lottemart_culture_club_classes`의 데이터를 복사 이전(완료 후 폐기
  여부는 컷오버 검증 후 별도 결정). `user_bookmarks.emart_class_id`/
  `lottemart_class_id` → `culture_club_class_id`로 통합(기존 북마크 데이터
  마이그레이션 필요).
- **코드**: `emart-culture-club.mjs`/`lottemart-culture-club.mjs`(및 detail/
  ping/status-watch 스크립트)의 최종 upsert 대상 변경, 북마크 관련 코드
  (`bookmarks.ts`, `bookmark-button.tsx`, 각 마트 화면의 찜 아이콘 조회) 전부
  갱신 필요, 두 상태감시 스크립트를 브랜드 분기형 단일 스크립트로 재구성.
  관리자 패널/프론트엔드 조회 API도 통합 테이블을 보도록 전환.
- **단계적 진행**: 데이터 손실 위험을 줄이기 위해 (1) 신규 테이블 생성 +
  무손상 데이터 복사(기존 테이블/기존 코드 경로는 그대로 유지) → (2) 신규
  경로 전체를 테스트로 검증 → (3) 수집/조회/찜 코드를 한 번에 전환(컷오버) →
  (4) 안정화 확인 후 기존 테이블 정리, 순서로 진행한다.

선택했을 때만 노출 중분류 기준이 적용되고, 기본 화면은 Decision 022가
명시한 대로 반경 내 전체 스팟을 보여준다"로 보고했으나, 사용자가 다시
정정했다: "카테고리 자체도 노출중분류들로만 구성이 되어야되는건 당연하고
이때는 선택한 카테고리에 대하여 해당 노출중분류 스팟만나오는거아니야..
아무 카테고리도 안고른 기본화면도 노출중분류의 하나의 카테고리만
선택한게 아니라 노출중분류가 매핑된 데이터들 중에서 반경내 전체 스팟을
보여주는거야.. 내가 전제조건을 노출중분류가 매핑됐는지로 얘기했을텐데?"

즉 원래 전제는 "스팟픽에 노출되는 모든 스팟은 노출 중분류가 매핑된
것만"이었고, Decision 022의 "기본 화면은 전체 조회" 문구/구현은 그
전제를 놓친 것이었다 — 트레이드오프를 다시 논의해 뒤집은 게 아니라,
원래 전제가 구현에 반영 안 된 버그였다는 사용자의 정정이다.

#### 실측으로 확인한 원인
`get_nearby_spaces_and_events` RPC의 `p_category_mins`가 null인 분기
(카테고리 미선택 시 기본 지도 조회, `map-explorer.tsx`가 쓰는 유일한
경로)가 `open_spaces` 쿼리에 `service_category_id`를 전혀 거르지
않았다 — `location_precision='EXACT'`와 그룹 대표 1건 조건만 걸고
있었다. 반면 카테고리를 선택했을 때 쓰는 경로(`get_spots_by_service_
category` RPC, `p_category_mins`가 있는 분기)는 원래부터 올바르게
동작하고 있었다.

#### 결정 내용
`get_nearby_spaces_and_events`의 `p_category_mins is null`(기본 화면)
분기, SPACE 쿼리에 `and s.service_category_id is not null`을 추가한다.
`p_category_mins`가 있는 분기(카테고리 선택 시 및 `getNearbyKidsRestaurants`
등 category_min 기반 별도 기능)와 EVENT 쪽(이 개념이 원래 없음)은
건드리지 않는다.

**실측으로 발견한 성능 회귀 — 부분 인덱스로 해결**: 인덱스 없이 이
조건만 추가하자 EXPLAIN(ANALYZE)로 4,449ms가 나왔다(기존 GiST 인덱스로
거리순 스캔하면서 매핑 안 된 86%를 하나씩 걸러내다 보니, limit 1001을
채우려면 ~13,500건을 훑어야 했음) — 실제 PostgREST(anon 롤) 호출로도
`statement timeout`으로 500 에러가 났다(라이브 REST 호출로 직접 재현
확인). `service_category_id is not null`로 걸러진 부분(partial) GiST
인덱스(`idx_open_spaces_location_geography_mapped`)를 추가하자 173ms로
돌아왔다(25배 단축) — 라이브 REST 재호출로 200 응답(723ms→195ms,
`service_category_id` 전부 채워짐)을 재확인했다.

#### 결정 이유
- 사용자가 원래 전제를 직접 재확인했다 — "로그인 여부와 무관" 하다는
  지적도 맞다(이 필터는 인증과 전혀 무관한 로직이었다).
- 실측 확인(2026-10-10): `open_spaces` 143,241건 중 10,584건(7.4%)만
  노출 중분류가 매핑돼 있어, 기본 화면에 이 필터를 걸면 보이는 스팟
  수가 크게 줄어든다 — 사용자가 이 트레이드오프를 인지한 상태에서
  "그게 원래 전제였다"고 재확인했으므로 임의 판단이 아니다.

#### 영향
- **DB**: `scripts/migrations/2026-10-10-nearby-rpc-default-view-
  require-service-category.sql`(적용 완료) — 부분 GiST 인덱스
  `idx_open_spaces_location_geography_mapped` 신규 추가 + `get_nearby_
  spaces_and_events` 함수 재정의(반환 타입/파라미터 시그니처는 동일,
  WHERE 조건만 추가).
- **코드**: TypeScript 쪽 변경 없음(RPC 내부 로직만 바뀌고 반환 스키마는
  그대로라 `get-nearby.ts`/`map-explorer.tsx` 호출부는 그대로).
- **스펙**: `spec/map/spatial-search.md` §2.1 "노출 중분류 미선택 시
  (기본 화면)" 항목 정정.
- **라이브 검증**: 수정된 RPC를 판교(37.3947, 127.1086) 5km 기준으로
  실제 anon 키 REST 호출(브라우저 호출과 동일 경로)로 재현해 200 응답
  (195~723ms)과 반환 SPACE 34건 전부 `service_category_id`가 채워져
  있음을 확인. 인덱스 추가 전에는 이 동일한 REST 호출이 500(statement
  timeout)으로 실패하는 것도 직접 재현해 확인했다.

### Decision 031: 롯데백화점 문화센터 수집 일시 정지 — WAF 차단, 사용자 로컬 PC 포함 확인
- **날짜:** 2026-10-13
- **상태:** 승인 (Approved) — 사용자 직접 지시("일단 롯데백화점은 멈춰").

#### 배경
문화센터 8개 브랜드 알림 점검 중 `pipeline_logs`에서 `LOTTE_DEPARTMENT_
CULTURE_CLUB`의 반복 FAILED를 발견했다. 조사해보니 그 일부는 테스트
스위트가 실제 프로덕션 Discord/DB를 오염시킨 가짜 기록이었지만(별도 수정
완료, `implementation/2026-10-13-culture-club-test-suite-production-
pollution-fix.md`), 그와 별개로 이 세션(클라우드/샌드박스 네트워크)에서
`culture.lotteshopping.com/search/list.ajax`에 라이브로 직접 요청해본 결과
`lrclsCtegryCd=02`/`03` 둘 다 실제 WAF 차단 페이지("The request / response
that are contrary to the Web firewall security policies have been
blocked.")를 받았다. 사용자가 **자신의 로컬 PC에서도 동일하게 막히고
있음을 직접 확인**해줬다("지금 waf 차단 내 로컬 pc에서 똑같이 막히고
있어") — 2026-10-06 이마트가 겪은 것(`implementation/2026-10-06-emart-
local-pc-bridge.md`)과 달리, 이번엔 로컬 PC까지 포함해 막혀 있어 "로컬
PC로 옮기면 우회된다"는 기존 해법이 통하지 않는 경우다.

#### 결정 내용
롯데백화점 문화센터 수집을 **코드 변경 없이, 운영(스케줄러) 레벨에서
일시 정지**한다. 이 브랜드는 GitHub Actions 워크플로가 아니라 Windows
작업 스케줄러로만 등록돼 있다(`implementation/2026-10-09-lotte-
department-culture-club-integration.md`): `LocalOpenSpaces-
LotteDepartmentBatch`(목록, 5시간 간격)·`LocalOpenSpaces-
LotteDepartmentDetailFetch`(상세, 5시간 간격) — 이 세션(샌드박스)에서는
사용자의 실제 Task Scheduler를 조회/제어할 수 없어(`schtasks` 호출이 이
환경에선 빈 결과만 반환), 사용자가 직접 아래 명령으로 두 작업을
비활성화해야 한다:
```
schtasks /change /tn "LocalOpenSpaces-LotteDepartmentBatch" /disable
schtasks /change /tn "LocalOpenSpaces-LotteDepartmentDetailFetch" /disable
```
재개 시(차단이 풀리거나 우회 방안이 마련된 뒤)는 `/disable`을 `/enable`로
바꿔 실행.

#### 결정 이유
- 로컬 PC까지 막혀 있다는 건 "데이터센터 IP만 차단"이라는 기존 가설이
  이 브랜드엔 적용되지 않는다는 뜻이다 — 계속 재시도하면 계정/IP 차단이
  더 굳어질 위험(추측이지만 일반적인 WAF 운영 상식)과, 어차피 실패할
  요청에 Discord 실패 알림만 반복 적재되는 노이즈를 막기 위해 사용자가
  직접 중단을 지시했다.
- 코드(스크립트/워크플로 파일) 쪽에는 이 브랜드를 멈출 스위치가 없다
  (이마트처럼 `.yml.disabled`로 끌 수 있는 GitHub Actions 워크플로 자체가
  없음) — 그래서 이 결정은 "운영 작업(Task Scheduler 비활성화)"이며,
  사용자가 자신의 PC에서 직접 실행해야 한다는 점을 명시해 둔다.

#### 영향
- 코드/스펙 변경 없음 — 문화센터 통합 화면에서 롯데백화점은 당분간
  신규 강좌가 갱신되지 않고 기존 데이터만 남는다(기존 행을 지우거나
  `is_excluded` 처리하지는 않음 — 사용자가 별도로 요청하지 않았다).
- 재개 조건(우회 방안 마련, 또는 차단이 자연 해제됨 확인)과 재개 방법은
  이 결정 항목 자체에 남겨 뒀다 — 추후 세션이 이 브랜드의 반복 실패를
  다시 "고쳐야 할 버그"로 오인하지 않도록 한다.

### Decision 033: 전국 주차장 표준데이터 통합 — 부설 1:1 FK 매칭 + 노외 반경검색 이원화, LLM 대신 결정적 이름유사도
- **날짜:** 2026-10-15
- **상태:** 승인(Approved) — `implementation/todo.md` 개선사항1 명세에 따라 진행,
  명세 자체가 "검토 필요"/"제안해주세요"로 열어둔 지점은 이 결정으로 확정.

#### 배경
`todo.md`가 "전국주차장정보표준데이터.csv"(18,939건) 기반 `parking_metadata`
테이블 구축을 지시하면서, 핵심 설계를 몇 가지 열어뒀다: ① 부설(건물 전용)/노외
(공용) 주차장을 FK 매칭과 반경검색 중 어느 쪽으로 할지, ② 18,000여 건 반경검색의
성능 최적화 방법, ③ 기존 `seoul_public_parking_lots`와의 병합 방식.

#### 결정 내용
1. **부설=FK 1:1 매칭, 노외=반경검색 — 이원화**(명세 원안 그대로 확정):
   `open_spaces.parking_id`(nullable FK)로 부설 주차장을 스팟에 직접 연결하고,
   `get_nearby_parking_lots` RPC는 `type_name='노외'`만 반환(부설은 반경검색
   목록에 중복 노출하지 않음 — 이미 그 스팟 자신의 전용 자원이므로).
2. **LLM 교차확인 대신 결정적 이름 유사도**: 매 실행 결정성(같은 입력 → 같은
   결과)이 필요한 반복 배치라 LLM 호출을 피했다. 50m 반경 내 후보를 PostGIS로
   찾은 뒤, 정규화(주차장/공영/지하 등 공통 단어 제거) + 2-gram 유사도로
   점수화, 0.5 미만은 매칭하지 않는다(오탐이 미탐보다 나쁘다고 판단해 보수적
   임계값). 실측: 888개 후보 쌍 중 222건 매칭.
3. **성능 최적화 — 새로운 장치 불필요**: 13,977건(노상 제외 후)은 PostGIS
   GIST 인덱스 + `st_dwithin` 조합(이미 `get_nearby_spaces_and_events` 등에서
   검증된 패턴)으로 충분하다 — 수십만 건 규모에서나 의미 있는 별도 캐싱/샤딩은
   이번 규모에 과잉설계로 판단, 추가하지 않았다.
4. **기존 `seoul_public_parking_lots` 테이블 — 삭제 대신 이름만 변경 보관**:
   전국 표준데이터가 서울 소재 856건도 포함해(실측 확인) 더는 필요 없지만,
   두 출처를 행 단위로 교차 매칭/병합하진 않았다(서로 다른 소스라 이름 표기가
   달라 자동 매칭 오탐 위험, 제3장 제5조 추측 금지) — `DROP` 대신
   `seoul_public_parking_lots_deprecated_20261015`로 이름만 바꿔 되돌릴 수
   있게 남겼다.
5. **`get_nearby_spaces_and_events` RPC는 건드리지 않음**: 이 RPC는 과거
   4,449ms 성능 회귀를 겪고 부분 인덱스로 겨우 해결한 전례가 있는 민감한
   경로라, `parking_id` 노출을 위해 컬럼을 더 얹는 대신 상세 모달이 열릴 때만
   스팟 1건을 가볍게 별도 조회(`getSpotParkingId`)하는 쪽을 선택했다.
6. **ingest는 전체교체(TRUNCATE 대신 DELETE+재적재), GitHub Actions 미편입**:
   `주차장관리번호`가 유일키가 아님을 실측 확인(18,939건 중 고유 17,798개,
   서로 다른 지자체 데이터 충돌 1,141건)해 증분 upsert 대신 매번 전체 교체.
   이 CSV는 API가 아니라 사람이 수동으로 올리는 스냅샷이라, 자동 월간
   워크플로에 넣지 않고 로컬 수동 실행(`npm run ingest:parking-metadata`)으로
   뒀다 — 매달 같은 파일을 의미 없이 재적재하는 것을 피함.

#### 영향

   '놀이방식당'/'키즈친화 식당(오케이존)'과 달리 어떤 정적 그룹의 minors에도
   없어 이 경로로 '기타'에 속한다. `category_min='식당'` 전체는 1,612건
   (category='KIDS_ACTIVITY' 1,611건 + 'ETC' 1건).

#### 결정 내용
2번(`category_min='식당'` 전체, 1,612건)이 사용자가 말한 "표준중분류
기타>>식당"이다 — "표준 중분류"라는 단어 자체가 1번(category, 소비자
화면 전용 5대+기타 UI 탭 구분)이 아니라 2번(category_min, 관리자 화면
전용 분류 체계) 쪽 용어와 정확히 일치하고, 1번 해석으로는 식당이 1건뿐이라
"csv로 추출해달라"는 요청의 실익이 없다. `get_open_spaces_by_category_min`
RPC(신규, get_spots_by_service_category와 동일 패턴 — standard_name 우선,
dedup 대표만)로 `category_min='식당'`을 조회해 1,594건(대표 아닌 중복
18건 제외)을 추출했다.

#### 영향

### Decision 037: 네이버 플레이스 검색 단계 — Playwright 대신 fetch(__APOLLO_STATE__ 정적 파싱)
- **날짜:** 2026-10-15
- **상태:** 승인(Approved) — todo.md 개선사항4 1~3단계(검색/주소교차검증/ID
  추출) 구현 착수 전 실측 확인.

#### 배경
todo.md 개선사항4는 "playwrite 를 이용하여 구현"하라고 명시했다. 하지만
이미 이 프로젝트의 관리자 네이버 플레이스 크롤링 기능(`naver-place-
crawler.ts`, 2026-09-18)이 상세/메뉴/공지/리뷰투표 페이지가 전부 Next.js
서버 렌더링이라 `window.__APOLLO_STATE__`에 데이터가 정적으로 박혀있어
헤드리스 브라우저 없이 fetch만으로 파싱 가능함을 이미 확인해 둔 상태였다.
검색 결과 페이지도 같은 방식인지 직접 떠서 확인했다(2026-10-15, 실측):
`map.naver.com/p/search/<검색어>`를 Playwright로 열면 내부적으로
`pcmap.place.naver.com/place/list?query=<검색어>...`를 iframe으로
불러오는데, **이 list 페이지 자체도 서버 렌더링**(`PlaceListBusinessesItem:
<id>` 엔티티에 명칭/도로명주소/지번주소/전체주소/좌표가 전부 포함)이라
plain fetch만으로 동일한 검색 결과를 그대로 받을 수 있었다.

#### 결정 내용
검색(1단계)과 뒤이을 상세·리뷰 스크래핑(4단계)을 모두 fetch 기반으로
구현한다 — Playwright/헤드리스 브라우저는 쓰지 않는다. 근거:
1. **차단 위험이 더 낮다**: 이 세션에서 이미 두 번 실측된 전례 — (a) 네이버
   WAF가 IP 단위로 429 레이트리밋을 건다는 사실(`naver-crawl/route.ts`,
   2026-09-27), (b) 이마트/롯데 문화센터 스크래핑이 GitHub Actions(클라우드
   IP)에서 WAF에 차단된 전례(`emart-culture-club.mjs`). 일반 HTTP 클라이언트
   요청이 헤드리스 브라우저보다 자동화 탐지 신호가 적어 상대적으로 안전하다.
2. **더 안정적이고 빠르다**: 브라우저 구동/렌더링 대기가 없어 요청당
   지연이 적고, DOM 셀렉터 변경에 취약하지 않다(Apollo 캐시 키 구조는
   DOM 레이아웃보다 덜 자주 바뀐다 — 이 프로젝트의 기존 크롤러가 이미
   여러 달째 이 방식으로 안정 동작 중).
3. **기존 구조 재사용**(제5장 제4조): `naver-place-crawler.ts`가 이미
   검증한 방식과 완전히 같은 패턴(파싱 함수만 독립 복제, 네트워크는
   fetch)이라 새로운 리스크를 들이지 않는다.

Playwright(`@playwright/test`, devDependency로 이미 존재)는 혹시 이후
단계(리뷰 탭의 "아이와 가기 좋아요" 필터 클릭 등 정적 파싱만으로 안 되는
상호작용)에서 필요해지면 그때 그 지점에서만 쓴다 — 현재까지는 불필요했다.

#### 영향
- **코드**: `scripts/naver-kids-restaurant-agent/lib/`(naver-search.mjs,
  address-match.mjs, apollo-state.mjs 등), `search-and-match.mjs`.
- **실측 검증**: "원조남원추어탕" 동명이인 사례(경기 시흥시/안산시)에서
  주소 교차검증으로 정확한 지점을 골라냄을 라이브 호출로 확인.

### Decision 039: 자동 블로그 후기 캐싱 — 신뢰도 검증에 상호명 일치를 항상 필수로
- **날짜:** 2026-10-16
- **상태:** 승인(Approved) — 사용자가 독립적으로 2번 신고(위키/MOKA)한
  실사용 버그를 실측 재현 후 확정.

#### 배경
`/api/spot-blog-reviews`(관리자 큐레이션이 없을 때 네이버 블로그 검색
API로 자동 조회 → 신뢰도 검증 → 캐싱, 2026-09-10 구현)의 `isTrustedBlogItem`
이 "지역 정보가 있으면 상호명은 확인조차 하지 않고 지역명만으로 신뢰
판정"하는 구조였다. 실측: "위키(WIKI)"(성남 분당)는 "나무위키"/"위키인포"
같은 완전 무관한 블로그가 본문에 "분당"/"성남"이 우연히 섞여 있다는
이유만으로 통과했고, "현대어린이책미술관 MOKA"(성남 분당 판교)는 "현대
백화점 판교점" 맛집 후기 등이 "현대"+"판교" 조합이 우연히 일치한다는
이유만으로 통과했다. 캐시가 있던 32개 스팟 전체를 재검증한 결과 29개
(91%)가 이 버그에 영향을 받고 있었다 — 개별 스팟 단위 문제가 아니라
이 자동 캐싱 기능 전체의 구조적 결함이었다.

#### 결정 내용
1. 상호명 일치를 **항상** 필수로 요구한다(지역 정보 유무와 무관). 관리자
   큐레이션 화면의 "워닝 표시"(`hasRegionMismatch`, `use-spot-curation-
   form.ts`)는 사람이 결과를 직접 보고 거르는 보조 신호라 지역명만으로도
   충분하지만, 이 경로는 사람 검수가 전혀 없는 완전 자동 노출이라 더
   엄격한 기준이 필요하다 — 두 로직을 하나로 합치지 않고 분리된 채로
   유지한다.
2. 상호명이 4자 미만으로 짧으면("위키" 등) 더 긴 무관한 단어에 묻혀
   있을 위험이 실제로 있어(나무위키/위키인포) 독립된 단어/구 경계로
   등장하는지까지 확인한다. 4자 이상으로 충분히 길고 구체적인 이름은
   그 자체로 고유해 공백 유무(예: "용인어린이상상의숲" vs "용인어린이
   상상의 숲") 같은 사소한 표기 차이에 흔들리지 않도록 느슨한(공백
   무시) 포함 비교를 쓴다 — 실측 중 엄격한 검사를 모든 이름에 적용했다가
   이 정상 사례를 떨어뜨리는 과잉교정을 직접 발견해 되돌렸다.
3. 상호명에 영문 괄호 병기가 있으면(예: "위키(WIKI)") 그 표기를 떼고
   핵심 상호명만 비교한다 — 실제 블로그 본문이 괄호 영문 표기까지
   그대로 적는 경우는 드물다.

#### 영향
- **코드**: `src/lib/spaces/blog-review-cache.ts`(`isTrustedBlogItem` 재작성),
  테스트 16개(회귀 테스트 3건 포함)로 전부 통과 확인.
- **데이터**: 자동 캐시가 있던 32개 스팟 중 29개(+ 수동 확인한 위키/MOKA
  2개, 총 31개)의 `blog_review_urls`를 비우고 `blog_review_updated_at`을
  null로 되돌려 즉시 재검증되게 했다. 나머지 3개는 수정된 로직을 전부
  통과해 그대로 유지했다.

### Decision 040: 스팟픽 블로그 후기 — 자동 조회/캐싱 기능 전체 폐지, 관리자 수동 큐레이션만 노출

전용이던 `blog-review-cache.ts`(신뢰도 검증/캐시 신선도 판정)는 완전히
쓰이지 않게 돼 삭제했다. 관리자가 직접 검색해 고르는 수동 큐레이션
워크플로(`use-spot-curation-form.ts`, `naver-blog-search.ts`,
`blog-search-server.ts`)는 이번 결정과 무관하게 그대로 유지한다 — "자동"
경로만 없앴을 뿐, "사람이 확인한 결과를 노출"하는 기능 자체는 todo.md
개선사항2-7 원문 의도(신뢰성 있는 것만 보여주기)에 더 부합한다.
