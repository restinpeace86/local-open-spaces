> **상태: 분석 결과 보고 — DB 스키마/데이터 변경 전혀 없음, 대표 승인 요청**
> `target_audience`/`target_audience_source`/`category_source` 컬럼을 추가하지 않았고
> `events` 테이블 어떤 값도 변경하지 않았다. 이 문서는 `events.title`/`raw_data`만 읽어
> (SELECT) 지시받은 알고리즘을 애플리케이션 코드(JS) 메모리에서 시뮬레이션한 결과다.

## 0. 가장 먼저 보고해야 할 구조적 제약 — "설명(contents)" 필드가 존재하지 않음

지시된 알고리즘은 0~2단계에서 "제목(`title`) 및 설명(`contents`)"을 스캔하도록 돼 있다.
그런데 실측 확인 결과, **`events` 테이블에는 `contents`/본문 설명 컬럼 자체가 없고**,
소스별 원본 보존 컬럼인 `raw_data`도 아래와 같이 소스에 따라 상태가 완전히 다르다:

| 소스 | 건수 | `raw_data` 상태 |
| :--- | ---: | :--- |
| `seoul_public_reservation`(SEOUL_YEYAK) | 1,625건 | 원본 전체 보존(`USETGTINFO`/`DTLCONT` 등 25개 필드 포함) |
| `seoul_public_culture` | 18,951건 | **`raw_data = {}`(완전히 빈 객체)** |
| `gg_public` | 2,955건 | **`raw_data = {}`(완전히 빈 객체)** |
| `tourapi_4.0` | 240건 | **`raw_data = {}`(완전히 빈 객체)** |

즉 전체 26,404건 중 **22,146건(83.9%)은 본문/설명 텍스트가 애초에 DB에 없다** — 이 3개
소스의 수집 스크립트(`seoul-culture-events.mjs`/`gg-culture-events-adapter.mjs`/
`tour-api-festival.mjs`)가 원본 응답의 상세설명 필드(예: 서울시 문화행사의 `PROGRAM`,
TourAPI의 `overview` 등)를 애초에 저장하지 않았기 때문이다(추측이 아니라 실제 DB 조회로
확인한 사실). 이번 분석은 이 3개 소스에 한해 **`title`만으로** 0~2단계를 시뮬레이션했다 —
지시된 "설명(contents)" 스캔은 데이터가 없어 수행할 수 없었다는 점을 명확히 밝힌다.

**이 제약이 결과에 미치는 영향**: 아래 5절에서 보듯 최종 NULL 잔여율이 81.05%로 매우 높다.
원인 분석 결과, 절대다수(전체 NULL의 약 76%)가 "제목만으로는 판단 불가능한 일반 문화
콘텐츠"(콘서트/전시/공연/축제/박물관 등, 대상 연령이 제목에 드러나지 않음)였다 — 이는
키워드를 아무리 추가해도 근본적으로 해결되지 않는 **데이터 자체의 한계**다. 3절/6절에서
상세히 다룬다.

## 1. 서울시(SEOUL_YEYAK) `USETGTINFO` 1차 정형화 결과

실측 확인한 `USETGTINFO` 원본 값은 괄호 부연설명과 쉼표 다중 나열이 섞여 있다(예:
`" 성인, 유아(영유아는 보호자 1인 동반 필수), 청소년(중고등학생), 초등학생"`). 괄호 제거 후
쉼표로 분리한 토큰이 **전부 하나의 표준 태그로 모일 때만** "1:1 매핑 성공"으로 집계했다.

`ALL`로 볼지, 별도의 6번째 값(예: `ADULT`)을 신설할지, 그냥 `NULL`로 남길지 결정이
필요하다. 나머지 "복합값"(161건)과 "알 수 없는 토큰"(96건)은 0/1/2단계 파이프라인으로

## 6. NULL 잔여 패턴 분석 및 추가 키워드 제안

0/1/2단계 대상(SEOUL_YEYAK 제외) 최종 NULL 20,957건의 제목에서 등장 빈도가 높은 단어를
집계했다(상위): `도서관`(1,507), `전시`(1,288), `콘서트`(1,195), `박물관`(1,169),
`공연`(903), `축제`(845), `체험`(582), `미술관`(548), `음악회`(527), `페스티벌`(497),
`기획전`(439), `시민`(433), `뮤지컬`(399), `공예`(381), `학교`(360), `연극`(320),
`만들기`(287), `아카데미`(277), `키즈`(195) 등.

**중요한 판단**: 이 상위 빈도 단어 대부분(전시/콘서트/공연/축제/음악회/뮤지컬/연극/기획전
등)은 **일부러 키워드로 추가하지 않는 것을 제안한다.** 이런 단어들은 "일반 문화 콘텐츠"라는
사실만 알려줄 뿐 대상 연령과는 무관해서(성인 전용 콘서트도, 온가족 콘서트도 다 "콘서트"라는
단어를 포함), 이걸 CHILD/FAMILY로 끼워 맞추면 지난 작업에서 발견한 "OO문화재단→역사 오매칭"
과 같은 성격의 오탐을 대량으로 만들 위험이 크다(무리한 추정 금지 원칙과 정면으로 배치됨).
**근본 해결책은 키워드 추가가 아니라 0절에서 지적한 `contents`(본문 설명) 필드를 애초에
수집하지 않는 파이프라인의 공백을 메우는 것**이다 — 서울시 문화행사/TourAPI/경기데이터드림
원본 API에는 상세설명 필드가 실제로 존재한다(이미 요청 중인 응답에 포함돼 있을 가능성이
높음, 수집 스크립트가 저장을 안 했을 뿐). 이 부분은 별도의 데이터 파이프라인 보강 작업으로
제안한다(이번 작업 범위 밖, 승인 시 별도 진행).

그럼에도 불구하고, 오탐 위험이 낮고 신뢰도가 높다고 판단되는 **추가 키워드는 아래와 같이
제안**한다(전부 제안 단계, 확정 아님):

### 6.1. 1단계(자동 확정) 추가 제안 — 높은 신뢰도

| 태그 | 추가 제안 키워드 | 근거 |
| :--- | :--- | :--- |
| CHILD | `어린이집`, `유치원` | 아동 전용 기관명 — 오탐 가능성 거의 없음 |
| **ALL(신설 규칙)** | `테니스장`, `풋살장`, `축구장`, `체육관`, `골프장`, `농구장`, `족구장`, `야구장`, `다목적경기장`, `배드민턴장`, `탁구장`, `배구장`, `수영장`, `운동장`, `피클볼장` | 스포츠 **시설 대관** 게시물(예: "잠실제3풋살경기장-평일(조기사용)")은 프로그램이 아니라 공간 예약이라 나이 제한 개념 자체가 없다 — 특정 대상이 아니라 `ALL`로 확정하는 것이 CHILD/FAMILY로 억지로 넣는 것보다 정확하다(직전 [7대 대분류] 작업의 category_min 36종과 동일한 목록 재사용 가능) |

### 6.2. 2단계(텍스트 파싱) 추가 제안 — 중간 신뢰도

| YOUTH | `청소년` | 현재 2단계 목록에 "청소년"이 빠져 있어(0단계 "청년"과는 다른 단어) "OO청소년센터/청소년수련관" 같은 명백한 사례도 NULL로 남았다(실측 확인: "보라매청소년센터 강당") |

### 6.3. 0단계(소거) 추가 제안 — 낮은 확신, 검토 요청

6.1의 "ALL 신설 규칙"만 반영해도 NULL 잔여 중 스포츠 시설 대관 게시물 상당수가 정리될

  - 포스터: `thumbnail_url`이 있으면 원본 크기로 표시, 없으면 "이미지 없음" 안내.
  - 본문 전체 텍스트: 0절에서 확인했듯 `seoul_public_culture`/`gg_public`/`tourapi_4.0`은
    `raw_data`가 비어 있어 본문을 보여줄 수 없다 — 이 경우 "이 소스는 본문을 보존하지
    않습니다(제목만 확인 가능)"라는 안내를 명시해야 관리자가 "왜 본문이 안 보이지"라고
    오인하지 않는다.
  - 장소/일시: 기존 컬럼(`venue_name`/`sigungu_name`/`start_date`/`end_date`) 그대로 사용.
  - 원문 URL 직행 버튼: `reservation_url`(있으면) 또는 원본 소스 도메인 링크.
  - 하단 드롭다운 저장 시 규약: 중분류 변경 시 `category_min_source = 'MANUAL'`(기존 규약
    그대로), 타겟 변경 시 `target_audience_source = 'MANUAL'`(신규 컬럼, 동일 패턴) 함께
    기록 — 이후 자동 재분류 배치가 이 두 값을 덮어쓰지 않도록 보존한다.
