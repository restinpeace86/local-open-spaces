## 1. 소스 범위(Scope) 결정 — 매우 중요

1차 시뮬레이션에서 전체 NULL(43,445건)에 키워드를 그대로 적용했더니, `LOCALDATA_PLAYGROUND`
등 4개 소스에서 아파트 브랜드명이 우연히 자연/문화 키워드에 걸리는 오탐이 발견됐다(예:
"수목원호정포레스트", "수목원제일풍경채 보육시설 옆" — 실제로는 놀이시설이 설치된 아파트
단지명일 뿐, 수목원이 아니다). 총 43,445건 중 이 4개 소스에서 114건(1.8%)이 이렇게
오탐됐다.

**결정**: 이번 taxonomy는 아래 **8개 source_type만** 대상으로 한다. 나머지 4개 소스
(`LOCALDATA_PLAYGROUND`/`LOCALDATA_AMUSEMENT`/`SWIMMING_POOL`/`GG_EVENTS`)는 이 taxonomy의
데이터 도메인 자체가 아니므로 키워드 매칭도, '기타' 폴백도 적용하지 않는다(그대로 NULL
유지 — 이들은 다른 관점의 정제가 필요하다면 별도 작업으로 다룬다).

```
KOR_TOUR_API_V4, CULTURAL_FACILITY_SUMMARY, CULTURE_FACILITY, PUBLIC_FACILITY_OPEN,
GO_CAMPING, NATIONAL_PARK_ECOTOUR, CITY_PARK, PARK_API
```

이 8개 소스의 NULL 합계는 **26,888건**이다.

이름에 "공원"이 문자 그대로 없는 경우(예: "산끝", "식골", "낙타")가 대부분이라, 소스가
`city_park`라는 이유만으로 전부 "공원"이라 단정하는 건 새로운 추측이 된다(제3장 제5조
추측 금지). 이번 taxonomy는 "명확히 매핑되는 것만" 다루는 게 목적이므로, 이 잔여분은
`기타`로 안전하게 떨어뜨려 관리자가 검토하게 한다(3절).

## 3. '기타' 폴백 설계

- **적용 범위**: 1절에서 정한 8개 source_type 한정, `category_min IS NULL`이고 아래 4절
  키워드 규칙 중 어느 것에도 매칭되지 않은 행.
- **구현 방식**: `category_rules` 테이블에 빈 문자열(`''`) 키워드로 "항상 매칭"되는 행을
  넣는 방식은 **채택하지 않는다** — `category_rules`는 daily/monthly 배치가 공유하는 범용
  엔진(`applyCategoryRules()`)이 source_type 구분 없이 전체 open_spaces에 적용하므로,
  이렇게 하면 1절에서 제외하기로 한 4개 소스(놀이시설 등)에도 '기타'가 무차별
  적용되어버린다. 대신 **전용 함수**(`scripts/ingest/lib/detailed-category-fallback.mjs`)로
  source_type을 명시적으로 제한한 뒤 '기타'를 채운다 — 기존 범용 엔진은 건드리지 않는다.
- **실행 순서**: (1) 4절 키워드 규칙을 `category_rules` 테이블 경유로 먼저 적용(기존
  `applyCategoryRules()` 배치 스텝) → (2) 그 다음 전용 '기타' 폴백 함수 실행. 이 순서를
  지켜야 키워드로 분류될 수 있었던 행이 먼저 '기타'로 채워지는 일이 없다.

## 6. 대표 확인 필요 없이 바로 실행 가능하다고 판단한 근거

이 작업은 (a) `category_min IS NULL`인 행만 채우고 기존 값을 절대 덮어쓰지 않으며(기존
엔진의 안전장치 그대로 재사용), (b) 삭제/구조 변경이 아니라 태깅만 하는 가역적 UPDATE이고,
(c) 오매칭 발견 시 `category_min_source`로 걸러(`RULE`) 관리자가 `/admin/data-grid`에서
언제든 재검토·수동 보정 가능해, 이전 세션의 하드 삭제(open_spaces 중복 정제)만큼의 위험도가
아니라고 판단해 시뮬레이션 검증 완료 후 곧바로 적용까지 진행한다.
