## 2. 핵심 발견 — 신호가 거의 전부 `raw_data.DTLCONT` 한 필드에 몰려 있음

두 키워드 모두 "raw_data 기타 필드" 매칭의 절대다수가 `DTLCONT`(서울시 공공서비스예약
API의 "상세내용" 필드, `source=seoul_public_reservation`)에서 나왔다:
- "어린이"(NULL): `DTLCONT` 7 / `THEMECODE` 9 / `USE_FEE` 3 / 기타 2
- "보호자"(NULL): `DTLCONT` 17(사실상 전부)
- "어린이"(ALL): `DTLCONT` 103 / `SVCNM` 21 / `PLACENM` 15 / 기타 5
- "보호자"(ALL): `DTLCONT` 183(전부)

`DTLCONT`는 **현재 파이프라인의 어느 단계에서도 전혀 스캔되지 않는 필드**다 — 0순위(원천
타겟 필드 3종)에도, `description`(현재 `seoul_public_reservation` 소스는 description 백필
대상이 아니었음)에도 포함되지 않는다. 즉 이번에 발견한 신호는 기존 로직의 버그가 아니라
"애초에 들여다본 적 없는 필드"에서 나온 순수한 신규 발견이다.

## 4. 해석과 주의점

- **NULL 대상(347건 중 최대 60건, 17.3%)**: 현재 3단계(원천 필드/카테고리/텍스트) 어디에도
  매칭되지 않아 완전히 미분류 상태인 행들이다. `DTLCONT`를 스캔 대상에 포함시키면 이 중
  상당수를 실제로 분류할 수 있는 여지가 있다 — 가장 직접적인 개선 기회다.
- **ALL 대상(1,439건 중 최대 430건, 29.9%)**: 여기는 해석에 주의가 필요하다. 이 행들의
  `target_audience=ALL`은 대부분(1,433/1,439건) 원천 `USETGTINFO`가 문자 그대로
  `"제한없음"`이라 정확하게 매핑된 값이다 — 즉 **오분류라고 단정할 수 없다**. `DTLCONT`에
  "어린이"/"가족"이 언급된다고 해도, "누구나 참여 가능하지만 특히 가족 단위로도 즐길 수
  있다"는 설명일 수 있어 "제한없음"과 모순되지 않는다. 다만 향후 "가족 추천" 같은 별도
  신호로 활용할 가치는 있어 보인다(target_audience 자체를 덮어쓰는 것과는 다른 논의).
- 두 경우 모두 **DB에 어떤 변경도 하지 않았다** — 이 문서는 시뮬레이션 수치 보고이며,
  실제 규칙 반영 여부는 별도 승인이 필요하다.
