# [버그 제보] 어드민 스팟 큐레이션 등록 화면 — 검색 선택/영업시간·메뉴 파싱

## 구현 일시
2026-09-02

## 배경
관리자가 실제로 화면을 쓰다가 카카오톡/메시지로 남긴 사용성 제보 3건을 그대로 재현·
진단해 고쳤다.

## 진단 및 조치

### 1. "스팟 검색 결과를 클릭해도 반영이 안 되네"
- Playwright로 실제 클릭 플로우를 재현한 결과, **선택 로직 자체(state)는 정상 동작**
  했다 — 클릭하면 `selectedSpot`이 정확히 설정되고 검색창이 사라지는 것을 확인했다.
  다만 두 가지 실제 문제를 발견해 고쳤다:
  1. **검색 API가 콜드 스타트 시 최대 5초 가까이 걸릴 수 있음**(실측: 1.2~5초 변동,
     웜 상태에서는 250~330ms) — 이 사이 사용자가 "검색 중" 상태를 인지하지 못하고
     클릭해도 반응이 없다고 느낄 여지가 컸다. "검색 중..." 문구를 회색 잔글씨에서
     파란색 강조 문구("🔍 검색 중이에요, 잠시만 기다려주세요...")로 바꿔 눈에 띄게 했다.
  2. **선택 후 UI가 검색창을 완전히 다른 모양(회색 카드)으로 바꿔버려** "이름이
     입력란에 채워졌다"는 느낌이 들지 않았다 — 검색 입력란과 동일한 테두리 스타일의
     읽기전용 필드 형태(✅ 체크 아이콘 포함)로 바꿔, 선택된 이름이 실제로 "채워졌다"는
     것을 시각적으로 분명히 했다.
  - 추가로 AbortController를 도입해 새 검색이 시작되면 이전 요청을 확실히 취소하도록
    방어를 강화했다(느린 응답이 뒤섞일 가능성을 원천 차단 — 실제 원인으로 확정하지는
    못했지만 재발 방지 차원의 보강).

### 2. "영업시간 자동 파싱 시 브레이크타임/라스트오더가 안 채워짐" — 근본 원인 확정, 수정
- 제보 원문("매일 / 11:00 - 21:00 / 15:00 - 17:00 브레이크타임 / 20:30 라스트오더")을
  그대로 넣어 재현한 결과, **시간이 키워드보다 앞에 오는 표기**("15:00 - 17:00
  브레이크타임", "20:30 라스트오더")에서 파싱이 실패함을 확인했다.
- **근본 원인**: 기존 `extractLabeledRange`/`extractLabeledTime`은 "키워드 위치부터
  뒤쪽 텍스트만" 검색해, 키워드보다 *앞*에 있는 시간을 아예 못 봤다(키워드 뒤에는
  더 이상 시간이 없으니 매칭 실패).
- **수정**: 줄 단위로 키워드가 포함된 줄을 찾고, 그 줄 안에서 키워드와 *가장 가까운*
  시간(범위)을 채택하도록 바꿨다 — 키워드가 시간보다 앞이든 뒤든, 같은 줄에 다른
  숫자가 여러 개 섞여 있든(예: 메인 시간+브레이크+라스트오더가 한 줄에 있는 기존
  지원 형식) 모두 정확히 근접한 값을 고른다. 기존 6개 테스트(키워드가 시간보다
  앞에 오는 형식) 전부 그대로 통과함을 확인했다.

### 3. "메뉴 복붙 파싱이 안 됨(형식이 다를 수도)" — 근본 원인 확정, 신규 형식 지원 추가
- 제보 원문(메뉴판을 그대로 긁어온 "이름" / (빈 줄) / "가격" / (빈 줄) / "설명" 반복
  형식)을 그대로 넣어 재현한 결과, 단 한 줄도 파싱되지 않음을 확인했다.
- **근본 원인**: 기존 파서는 "이름 가격원"이 한 줄에 함께 있는 형식만 인식했는데,
  제보된 형식은 이름/가격/설명이 전부 별도 줄로 나뉘어 있었다 — 이런 배달앱/홈페이지
  메뉴판 복사-붙여넣기 결과가 실제로 매우 흔한 모양이다.
- **수정**: 가격만 단독으로 있는 줄("12,000원")을 새로 인식해, 그 직전에 본 텍스트
  줄을 이름으로 확정하는 방식을 추가했다. 이름 → 가격 → 설명 순서가 항상 유지되는
  구조라(설명은 항상 가격 *다음*에 옴), 가격을 찾을 때마다 이름 후보를 비워두면
  설명 줄이 다음 이름 자리를 잘못 차지하는 일이 없다. `menu_items` 스키마가
  `{name, price}`만 저장하도록 이미 확정돼 있어(`2026-09-01-create-spot-curations-
  table.sql`) 설명은 의도적으로 버린다(스키마를 임의로 바꾸지 않음). 기존 4개 테스트
  (단일 줄 형식) 전부 그대로 통과함을 확인했다.
- **부가 개선**(제보: "영업시간/메뉴 텍스트 붙여넣기 화면이 좀 작다"): 영업시간
  textarea를 2줄→5줄, 메뉴 textarea를 3줄→8줄로 늘리고 `resize-y`를 허용해 붙여넣은
  내용을 스크롤 없이 더 잘 확인할 수 있게 했다. 메뉴 라벨/플레이스홀더도 새로 지원하는
  두 형식을 모두 안내하도록 갱신했다.

## 정정 및 후속 조치 (2026-09-02, 사용자 재제보 반영)

위 1번 항목("검색 클릭-선택")과 이미지 붙여넣기에 대한 진단이 부족했다 — 사용자가
더 구체적인 재현 절차를 다시 알려줘서 근본 원인을 다시 찾아 고쳤다. 아래 내용으로
정정한다.

### 1-정정. 스팟 검색 결과 클릭 — "입력칸에 그 데이터가 들어가야 하는데 안 들어간다"
사용자가 명확히 지적: 문제는 "선택이 안 되는 것"이 아니라 **"선택한 이름이 검색
입력란 자체에 반영돼야 하는데 안 된다"**는 것이었다(예: "하노" 입력 → "하노이진영"
검색됨 → 클릭 → 입력칸에 "하노이진영"이 들어가야 함). 직전 수정에서 회색 카드로
바꾼 것 자체가 이 기대와 어긋났다.
- **수정**: 검색 입력란을 선택 후에도 그대로 유지하고, `value`를
  `selectedSpot ? selectedSpot.name : spotQuery`로 바꿔 선택한 이름이 입력란
  값 자체로 채워지도록 했다(요청 원문 그대로의 흐름). 입력란을 직접 다시 수정하면
  선택이 자동으로 풀리고 재검색된다. "변경" 버튼은 초기화용으로 남겨뒀다.
- **추가로 발견한 진짜 클릭 실패 원인**: 검색 결과 목록(`<ul>`)이
  `overflow-y-auto`로 스크롤 가능한데, 스크롤 가능한 목록에서 클릭 시 마우스가
  미세하게 움직이면(트랙패드 등) 브라우저가 이를 드래그로 판단해 `click` 이벤트
  자체가 발생하지 않을 수 있다 — `onClick`을 `onMouseDown`(드래그 여부와 무관하게
  버튼을 누르는 즉시 발생)으로 바꿔 이 문제를 피했다(자동완성 위젯들이 흔히 쓰는
  방식).
- **실측 확인**: "등록하기"를 눌렀을 때 "먼저 스팟을 검색해서 선택해 주세요" 에러가
  뜨던 것도(사용자가 분명히 선택했는데도) 이 두 수정으로 함께 해결됨을 실제 저장까지
  성공시켜 확인했다(테스트로 생성된 큐레이션 행은 검증 직후 삭제).

### 2-정정. 이미지 붙여넣기 — "클릭하고 있는 상태에서 Ctrl+V해야 됨" — 근본 원인 확정
Playwright로 `document.activeElement`를 직접 찍어본 결과, 붙여넣기 대상 안내 문구를
클릭해도 실제로는 그 아래 **"이미지 URL 직접 입력" `<input>`으로 포커스가 가버리는
것**을 확인했다.
- **근본 원인**: 이 구역 전체("대표 이미지" 붙여넣기 div + URL 입력 input)가 하나의
  `<label>`로 감싸져 있었다. HTML `<label>`은 클릭하면 그 안의 연관된 폼 컨트롤로
  브라우저가 자동으로 포커스를 옮기는 내장 동작이 있는데, 이 동작이 붙여넣기 대상
  div에 직접 호출한 `.focus()`보다 우선해 URL input으로 포커스를 가로채고 있었다 —
  그래서 "포커스가 계속 그 input에 남아있는 상태"에서만 어쩌다 Ctrl+V가 되던 것이다
  (사용자가 "누르고 있는 상태에서"라고 표현한 것과 정확히 일치).
- **수정**: 감싸던 `<label>`을 평범한 `<div>`로 바꿔 이 자동 포커스 위임 자체를
  없앴다. Playwright로 클릭 후 `document.activeElement`가 실제로 붙여넣기 대상
  div가 됨을 재확인했다.

### 3. (질문 답변) "오픈/close/브레이크타임/라스트오더 순서가 뒤섞여 있어도 되나?"
— 네, 문제없다. 각 값은 줄의 **위치/순서가 아니라 키워드 존재 여부**로 판별하므로
어떤 순서로 나열돼 있어도 동일하게 정확히 파싱된다. 실제로 순서를 뒤섞은 입력으로
신규 테스트를 추가해 확인했다.

### 4. 등록 폼 팝업이 배경 클릭으로 실수로 닫히는 문제
바텀시트류(AiRecommendSheet 등)는 배경 클릭으로 닫히는 게 기존 관례지만, 이 등록
폼은 텍스트 붙여넣기/이미지 업로드/자동 파싱 등 입력량이 많아 실수로 배경을 클릭했을
때 작성 중이던 내용을 통째로 잃는 리스크가 훨씬 크다. 외부 오버레이의
`onClick={onClose}`를 제거해, 이제 **✕ 버튼**과 **등록/수정 성공** 두 경로로만
닫히도록 했다. Playwright로 배경 클릭 후에도 모달이 열려 있음을 확인했다.
