# 블로그 전체 본문 API 프로덕션 500 오류 수정 (jsdom 서버리스 번들링 문제)

## 구현 대상
사용자 지시: "이거 아직 잘려보여.... [화면 캡처 인용] 여기까지만 보이고 스크롤
해도 뭐 내려가는거 없어 범위자체가 2줄밖에 안나올정도고.. 더보기 버튼 같은것도
없고.. 원문보기랑 다른 url로 바꾸기 밖에없어" — 직전 커밋(중첩 스크롤 트랩 제거)
이후에도 여전히 짧은 요약만 보인다는 재보고.

## 구현 일시
2026-09-06

## 실측으로 원인을 좁힌 과정
1. Playwright로 실제 브라우저를 띄워 로컬 dev 서버에서 진짜 클릭 흐름(검색 →
   행 클릭 → "블로그로 큐레이션" 클릭 → 탭 대기)을 그대로 재현 → **로컬에서는
   전체 본문(1,317자)이 정상적으로 오고 화면에도 그대로 렌더링됨**을 확인했다
   (박스 높이 550px, "✓ 전체 본문 표시 중" 마커 존재). 코드 자체는 정상이었다.
2. 사용자에게 "어디서 보고 계신지" 확인 → **배포된 사이트(Vercel)**였다.
3. 실제 배포 URL(`local-open-spaces.vercel.app`)의
   `/api/admin/spot-curations/blog-body`를 직접 호출 →
   **HTTP 500, 응답 시간 0.44초**. 실제 네이버 페이지를 가져오는 네트워크 요청은
   보통 1~3초 걸리는데(로컬 실측 기준) 0.44초 만에 실패했다는 건 그 요청을
   시작하기도 전에, 즉 **모듈을 불러오는 시점(jsdom import)에서 죽었다**는
   강한 신호였다.

## 근본 원인
`jsdom`은 내부적으로 일부 파일을 동적 `require`로 불러온다. Next.js가
Vercel 서버리스 함수를 만들 때 사용하는 정적 트레이싱(코드를 분석해 실제
실행에 필요한 파일만 함수에 포함시키는 방식)은 이런 동적 require를 감지하지
못해, 실제로 필요한 jsdom 내부 파일 일부가 배포된 함수에서 빠진다 — 로컬
`next build && next start`는 전체 `node_modules`가 그대로 있어 문제없이
동작하지만, Vercel에 올라간(트레이싱된 일부 파일만 존재하는) 함수는 그 파일을
찾지 못해 콜드 스타트 시점에 곧바로 죽는다. `sharp`/`canvas`처럼 네이티브
바인딩이나 동적 require를 쓰는 패키지에서 흔히 보고되는 전형적인 문제다.

## 수정
`next.config.ts`에 `serverExternalPackages: ['jsdom']` 추가 — 이 패키지를
번들링하지 않고 런타임에 그대로 `require`하도록 지시한다(Vercel이 함수 배포 시
`node_modules`에서 해당 패키지를 그대로 가져다 쓰게 됨 — 정적 트레이싱을
우회하는 Next.js 15+ 표준 해법).

## 검증
- `npx tsc --noEmit` 통과.
- `npm run test`: 115개 파일 / 1209개 테스트 전체 통과(이 변경은 빌드 설정만
  바꾸므로 테스트 결과에 영향 없음, 회귀 없음 확인 차원).
- `npm run build` 통과 — `serverExternalPackages` 키가 유효하게 인식됨(설정
  경고 없음), `/api/admin/spot-curations/blog-body`가 정상적으로 함수 라우트로
  포함됨.
- **실제 배포 재현**: 커밋/푸시 후 Vercel 자동 배포가 완료되면 동일한 프로덕션
  URL로 `/api/admin/spot-curations/blog-body`를 다시 호출해 200 + 본문 텍스트가
  오는지 재확인 예정(배포 반영에는 수 분이 걸릴 수 있음).

## 특이 사항
- 로컬에서만 검증하고 "정상 동작 확인"이라고 보고했던 이전 턴의 결론이 실제로는
  틀렸다 — 로컬 dev/build/start 환경과 Vercel 프로덕션 서버리스 환경의 차이를
  놓친 것. 이번엔 실제 배포 URL을 직접 호출해 재현한 뒤에만 원인 판단과 수정을
  진행했다(제3장 제5조 추측 금지 — 환경 차이를 짐작이 아니라 직접 두 환경 모두
  호출해 비교 확인).
