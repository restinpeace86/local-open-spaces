# [개선사항 10] 비로그인 사용자의 맘스픽 메인 화면 접근 허용 및 인터랙션 로그인 유도 처리

## 구현 일시
2026-09-03

## 배경 조사
`MomPickView`는 `useMomPickAccess()`가 `'guest'`를 반환하면 곧바로 `LoginPromptModal`만
보여주는 하드 블록 화면을 렌더링했고, 그 화면이 의존하는 서버 API
(`/api/mom-pick/dashboard`/`expert`/`trending`/`live`)도 공용 가드
`requireCommunityAccess()`에서 비로그인이면 401을 반환해 애초에 게스트가 피드 데이터
자체를 받을 수 없었다(실측 코드 확인) — 클라이언트만 고쳐서는 해결되지 않고 서버
가드도 함께 풀어야 하는 구조였다(이전 세션 계획 메모에서 이미 예상한 지점).

또한 요구사항이 언급한 "상세 페이지 진입 시 로그인 체크"에 대응하는 개별 게시글 상세
페이지/라우트가 이 앱에 실제로 존재하지 않음을 확인했다(`DashboardPostCard`가 이미
닉네임/등급/스팟명/후기 또는 체크리스트/좋아요까지 전부 인라인으로 보여주고 있어 별도
상세 진입 동선이 필요 없는 구조) — 없는 기능을 새로 지어내지 않고(제3장 제5조 추측
금지, 제7장 제4조 미래 기능 구현 금지), 실제로 존재하는 진입점인 "글쓰기"에 대해서만
Soft-wall을 구현했다.

## 구현 내용
1. **`requireCommunityAccess()`**: 비로그인이면 401을 반환하던 것을 `{ ok: true }`로
   바꿔 읽기 전용 열람을 허용한다. 로그인했지만 새싹맘 미달성인 사용자에 대한 기존
   403 정책(Decision 019)은 이번 지시 범위 밖이라 그대로 유지했다. 이 함수를 쓰는
   4개 라우트(dashboard/expert/trending/live) 모두 순수 읽기 전용 목록/미리보기라
   글쓰기와 무관하다.
2. **`MomPickView`**: `'guest'` 전용 하드 블록 분기를 없애고, `'allowed'`/`'not_sprout_
   yet'`과 같은 레이아웃(헤더 + 글쓰기 영역 + 피드)을 공유하도록 통합했다.
   - 피드 로딩 조건을 `state === 'allowed'`에서 `state === 'allowed' || state ===
     'guest'`로 확장.
   - 글쓰기 영역: `state === 'guest'`면 실제 `PostComposer`(스팟 검색/별점/체크리스트
     입력 폼) 대신 "✍️ 로그인하고 후기·체크리스트 남기기" 버튼만 보여준다 — 클릭 시
     실제 입력 폼은 전혀 렌더링되지 않고 곧바로 `LoginPromptModal`을 연다(개선사항
     8과 동일한 "입력 시작 전에 막는다" 원칙, 페이지 진입 즉시가 아니라 클릭한
     순간에만 뜬다는 점이 기존 하드 블록과의 차이).
   - `not_sprout_yet` 사용자에 대한 기존 동작(글쓰기 유도 안내 모달, 피드 비노출)은
     이번 지시 범위가 아니라 전혀 건드리지 않았다.

## 검증
`npx tsc --noEmit`/`npm run test`(96파일 972건, 기존 그대로 — `mom-pick-view.tsx`는
단위 테스트가 없는 상태 컴포넌트라 기존 관례를 따름)/`npm run build` 통과.

라이브 dev 서버 검증: `curl http://localhost:3000/api/mom-pick/dashboard`(인증 헤더
없이)가 이전이라면 401을 냈을 요청에서 실제로 `200 {"expert":[],"trending":[],
"live":[]}`을 반환함을 확인 — 이 서버 가드가 실제 차단의 근본 원인이었고, 이제
풀렸음을 실증했다.

**주의(정직한 한계 고지)**: `MomPickView`의 게스트 분기(작성 버튼 클릭 → 로그인 모달)
자체는 `useMomPickAccess()`가 클라이언트에서 비동기로 인증 상태를 판별한 뒤에만
확정되는 순수 클라이언트 렌더링이라, 브라우저 자동화 도구가 없는 이 환경에서는 curl로
직접 클릭 인터랙션까지 재현·확인하지 못했다. 차단의 실질적 근거였던 서버 가드는 위처럼
직접 검증했고, 클라이언트 쪽은 기존에 이미 검증된 `state` 분기 패턴(`allowed`/
`not_sprout_yet`과 동일한 조건부 렌더링 관례)을 그대로 확장한 것이라 코드 추적으로
정확성을 확인했다.
