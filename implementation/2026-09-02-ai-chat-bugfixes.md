# [버그 수정] 챗봇 문제점 6건

## 구현 일시
2026-09-02

## 배경
사용자가 실사용 중 발견한 AI 챗봇의 6가지 문제점 제보에 따른 수정.

## 수정 내용

### 1. 새 메시지 자동 스크롤 안 됨
메시지/로딩 표시/결과 카드가 추가될 때마다 스크롤 컨테이너를 맨 아래로 강제 이동시키는
`useEffect`를 추가했다(`ai-chat-sheet.tsx`). 매번 수동으로 올려야 했던 문제 해결.

### 2. 지역 변경이 "동네 이름을 정확히 쳐야만" 가능해 국소적임
`LocationOnboardingModal`의 시/군/구 목록 선택 기능(`getSigunguOptions`)은 기존에도
있었지만 **GPS 실패 시에만 열리는 숨겨진 2차 Fallback**이었다 — 검색창에 정확한
동네/주소를 입력하지 않으면 쓸 방법이 없었다. "🗺️ 지역 목록에서 선택" 버튼을 상시
노출로 승격해, 정확한 주소를 몰라도 목록에서 바로 시/군/구를 고를 수 있게 했다(이
목록은 실제 DB에 데이터가 있는 지역만 나오므로 이 앱의 서비스 지역, 즉 서울/경기권을
폭넓게 다룬다).

**실측으로 발견해 함께 고친 진짜 원인**: 사용자가 겪은 "검색 중 문제가 생겼어요" 에러의
실제 원인이 바로 이 항목과 연결돼 있었다 — 아래 5번 참고.

### 3. 예산 "1만원 이하"가 인당인지 가족 전체인지 모호함
라벨을 "1인 기준 1만 원 이하"/"1인 기준 2~3만 원 이하"로 명시했다(`step-options.ts`).
다만 open_spaces에는 실제 이용료 숫자 컬럼이 없어(기존에 이미 확인된 데이터 한계)
"완전 무료" 외에는 여전히 실질적인 가격 필터링은 되지 않는다 — 라벨만 바로잡았고
없는 가격 데이터를 지어내지 않았다.

### 4. 연령대 "4~6세가 빠짐" / "다양한 연령이 함께"의 의미 불명확
실제로는 빠진 게 아니라 라벨 문구("영유아 0~3세")가 실제 판정 기준(0~6세, 영유아보육법
정의)과 달라 혼동을 줬다 — AI 챗봇 초개인화 작업(personalization.ts)에서 이미 0~6세
기준으로 구현해뒀던 것과 이 수동 선택 라벨이 서로 다른 문구를 쓰고 있었다. "영유아
(0~6세, 미취학)"/"초등 (7~12세, 취학)"/"전연령 (특정 연령 없이 온 가족 함께)"로
문구를 통일했다(로직 변경 없음, 라벨만 실제 기준에 맞춤).

### 5. 분위기(Vibe)가 대분류 단일 선택만 가능, 복수/전체 선택 불가
- 맞다, 대분류(신나게 뛰어놀기/교육 및 체험/힐링 자연/문화 즐기기) 기준이었다.
- `ChatAnswers.vibe: Vibe` → `vibes: Vibe[]`로 변경, 토글형 다중 선택 UI(선택 완료
  버튼 + 선택 개수 표시) + "전체 다 보여주세요" 버튼(빈 배열 = 필터링 안 함) 추가.
- `matchesVibe`는 이제 "선택한 것 중 하나라도 일치하면 통과", 빈 배열이면 전부 통과.

### 6. "검색 중 문제가 생겼어요"만 뜨고 원인을 알 수 없음
`process.env.NODE_ENV !== 'production'`일 때는 실제 에러 메시지를 그대로 붙여 보여주고,
프로덕션 빌드에서는 자동으로 일반 문구로 돌아가도록 분기했다 — 오픈 후 별도 원복 작업이
필요 없다.

**이 항목을 조사하다가 실제 근본 원인을 실측으로 찾아냈다**(아래 참고).

## 실측으로 발견해 함께 고친 심각한 성능 버그 (사용자가 겪은 실제 에러의 원인)
curl로 반경별 검색을 재현한 결과, **반경 15km("차로 30분 이내")/40km("1시간
이상")에서 검색이 매번 `statement timeout`으로 실패**함을 확인했다 — 오늘 이미 두 번
겪은 것과 동일한 근본 원인이다(`get_nearest_spot_weather`에 이어 세 번째). `EXPLAIN
ANALYZE`로 확인한 결과 `get_nearby_spaces_and_events` RPC가 `st_dwithin`(반경) 방식이라
스팟 밀집 지역(수도권)에서 반경이 커질수록 후보 수만 건을 먼저 모은 뒤 정렬해 15km에서
6.8초가 걸렸다.

PostGIS KNN 인덱스 연산자(`<->`)로 "전체 반경 무관 최근접 1001건을 먼저 뽑고 그 중
실제 반경 이내만 사후 필터링"하는 방식으로 재작성해(수학적으로 기존과 동일한 결과를
보장 — 반경 R 이내의 점은 정의상 무제한 최근접 1001건 안에 항상 포함됨), 15km 935ms/
40km 123ms로 개선했다(최대 55배).

**이 버그가 항목 2("경기도권 폭넓게 못 찾음")와도 직결된다** — 경기도 거주자가 넓게
찾으려면 정확히 이 15km~40km 반경을 써야 하는데, 그 반경 자체가 항상 타임아웃으로
실패하고 있었다. 지역 선택 UX 개선만으로는 해결되지 않았을 근본 문제였다.

## 검증
### 코드 검증
`npx tsc --noEmit`/`npm run test`(96파일 962건 — 신규 8건 포함)/`npm run build` 통과.

### 실측 검증
- 라이브 DB `EXPLAIN ANALYZE`로 15km(6798ms→935ms)/40km(→123ms) 개선 확인.
- dev 서버 curl로 반경 15000/40000이 실제로 정상 응답함을 확인(수정 전 100% 재현
  실패였음).
- `vibes: []`(전체) 검색이 정상 동작함을 curl로 확인.
- `database.types.ts` 재생성 후 diff 없음 확인(RPC 시그니처 불변, 본문만 최적화).

## 특이 사항
- 항목 3(예산)은 라벨만 고쳤을 뿐 실질적인 가격 필터링 기능 자체는 여전히 없다 —
  실제 이용료 데이터가 DB에 없어서다. 가격 필터를 실제로 작동시키려면 별도로 이용료
  데이터 수집/입력 체계가 필요하다(이번 범위 밖, 별도 논의 필요).
- 항목 6의 상세 에러 표시는 `NODE_ENV`로 자동 분기되므로 별도 조치 없이 실제
  프로덕션 배포(Vercel `next build`) 시 자동으로 일반 문구로 전환된다.
