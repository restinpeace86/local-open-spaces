현재 저장소의 수집 파이프라인 안정성을 높이기 위해 아래 3가지 작업을 수행해줘. todo.md 파일 내용을 참고하여 순서대로 진행해 줘.

1. 크론 스케줄 시간대 KST 새벽 3시 기준으로 재조정
- ingest-daily.yml, ingest-monthly.yml 등 크론 워크플로 파일들의 schedule 설정을 수정할 것.
- GitHub Actions 기본 기준시는 UTC이므로, 한국 시간(KST) 기준 새벽 3시 대에 실행되도록 UTC 기준 전날 저녁 18시 대로 맞출 것 (예: KST 새벽 3시 23분 -> cron: '23 18 * * *').
- 전 세계 리포지토리와의 정각(Top of the hour) 트래픽 부하(Dropped Runs)를 피하기 위해 반드시 정각(0분)이 아닌 비정규 분 단위로 설정할 것.
- YAML 파일 내에 "KST 기준 새벽 3시 XX분 (UTC 18:XX)" 형태의 주석을 반드시 명시할 것.

2. 수집 파이프라인 자동 재시도(Retry) 메커니즘 도입
- API 호출 일시적 타임아웃, 네트워크 불안정, DB 부하 등으로 인해 수집/적재가 실패했을 때, 단 한 번의 실패로 당일 데이터가 유실되지 않도록 코드 레벨(어댑터 및 쿼리 업서트 부)에 재시도(Retry) 래퍼 함수를 적용할 것.
- 타임아웃이나 일시적 에러 발생 시 지정된 횟수(예: 최대 3회)와 간격(예: 3~5초)을 두고 자동으로 재시도하도록 구현할 것.

3. open_spaces 테이블 성능 최적화 및 검증 준비
- 프로덕션 DB 측에서 ANALYZE public.open_spaces; 처리는 완료된 상태이므로, 다음 수집 파이프라인 트리거 시 open_spaces 타임아웃이 깔끔하게 해소되는지 로그를 통해 확인할 수 있도록 코드를 점검할 것.
- 반복 재현 시 대비하여 배치 묶음 크기(Batch Size)를 쪼개어 처리하는 청크(Chunk) 단위 업서트 구조도 검토해 줄 것.

현재 open_spaces 테이블을 확인해보니, 위경도 좌표가 완전히 동일하거나 동일한 장소가 2개 이상 중복으로 쌓여 있는 데이터 이슈가 확인되었어. 기존의 '일단 유연하게 적재한다'는 수집 원칙은 유지하되, 아래 내용을 반영하여 중복 데이터 문제를 해결해 줘.

1. open_spaces 테이블 중복 데이터 식별 및 정제
- open_spaces 테이블 내에서 위경도(Latitude, Longitude)가 완전히 동일하거나, 이름/주소가 겹쳐서 중복으로 쌓여 있는 데이터를 찾아내고 정리(Deduplication)할 수 있는 스크립트 또는 쿼리를 작성해 줘.
- 앞으로 수집 과정에서도 동일한 중복 데이터가 계속 파고들지 않도록 업서트(Upsert) 기준 키나 고유 식별 로직을 보완할 것.

2. 유연한 적재 원칙 유지
- 단, 데이터가 일부 누락(예: 위경도나 주소가 비어있는 경우)되었더라도 버리지 않고 일단 적재하는 기존의 유연한 정책은 절대 훼손하지 말 것.
- 정제 작업은 오직 '명백하게 겹치는 중복 데이터'를 깔끔하게 잡아내는 데에만 집중할 것.
