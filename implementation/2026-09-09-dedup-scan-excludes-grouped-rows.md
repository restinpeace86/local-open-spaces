## 원인 진단(실측)
신고 내용의 세 가지 가설(① 저장 트랜잭션 미커밋, ② 조회 쿼리의 상태
필터링 오류, ③ 프런트엔드 상태 동기화 문제)을 실제 프로덕션 DB를 직접
조회해 하나씩 검증했다.

1. **저장은 정상이었다**: `open_spaces.group_id`가 채워진 행 592건,
   `spot_dedup_groups` 이력 265건 — 전부 "자연/공원 > 캠핑장 / 피크닉장"
   중분류로 정확히 저장돼 있었다(①번 가설 기각).
2. **조회 쿼리에 실제 버그가 있었다**: [[2026-09-09-category-scoped-dedup-
   and-auto-expiry]]에서 추가한 "노출 중분류 지정 스캔" 모드의
   `find_spot_dedup_candidates` WHERE 절이 `service_category_id`만 걸렀지
   `group_id`를 전혀 확인하지 않았다. 중분류 지정 스캔에서는 병합해도
   `service_category_id`가 그대로 유지되는 게 의도된 동작이라(다른 중분류로
   바뀌면 안 됨), 이미 처리된 행이 매 스캔마다 계속 후보로 다시 잡혔다.
   실측: 캠핑장 중분류 첫 페이지(50건)를 스캔하면 그중 10건이 이미
   `group_id`가 있는(=이미 처리 완료된) 행이었다.
3. 프런트엔드는 서버가 준 데이터를 그대로 그리고 있었을 뿐이라 문제가
   없었다(③번 가설 기각).

## 변경 사항
`scripts/migrations/2026-09-09-exclude-grouped-rows-from-dedup-scan.sql`
— `find_spot_dedup_candidates`의 두 스캔 모드(미매핑 전체 / 노출 중분류
지정) 모두에 `and group_id is null` 조건을 추가했다. 이미 그룹으로
확정된 행은:
- 같은 좌표의 새 데이터가 그 그룹에 자동 편입되는 것은 이미
  `auto_assign_open_spaces_to_existing_groups`(daily batch)가 처리하고,
- 관리자가 그 그룹을 다시 열어보고 싶으면 개별 스팟 상세의 "🔗 중복 스팟
  검토"로 직접 열람할 수 있으므로,

이 1차 스캔 후보 목록에서 반복 노출할 필요가 없다.

## 검증
- 실측: 수정 전 캠핑장 중분류 첫 페이지 50건 중 10건이 이미 그룹핑된
  행 → 수정 후 동일 조회에서 0건(페이지 크기는 여전히 50건 그대로,
  즉 걸러진 만큼 다음 미처리 행으로 채워짐).
- 미매핑 전체 스캔 모드도 여전히 정상 동작(5건 조회) 확인.
- `npx tsc --noEmit` / `npm run test`(1357건, 프런트엔드 코드 변경 없어
  기존 그대로) / `npm run build` 전체 통과.

## 특이 사항
- 이 버그는 [[2026-09-09-category-scoped-dedup-and-auto-expiry]](Step 79,
  "노출 중분류 지정 스캔" 신규 도입)에서 함께 들어온 회귀였다 — 기존
  "미매핑 전체 스캔" 모드는 병합 시 `service_category_id`가 NULL이 아닌
  값으로 바뀌는 게 보통이라(관리자가 실제 중분류를 지정) 이 조건 없이도
  대부분 자연히 걸러졌었지만, 우연히도 아니었어도(중분류를 "선택 안 함"으로
  저장한 경우) 같은 문제가 있었을 것 — 이번에 두 모드 모두 근본적으로
  고쳤다.
- `open_spaces.group_id`(592건)와 `spot_dedup_groups`(265행) 대비
  `open_spaces`의 distinct group_id는 264개로 1개 적었다 — 조사 결과
  [[2026-09-09-category-scoped-dedup-and-auto-expiry]]의 한시성 예약 스팟
  자동 삭제가 이미 daily batch로 실행되어, 어떤 그룹의 멤버 전원이
  `seoul_public_reservation` 만료로 삭제된 것으로 보인다(의도된 동작,
  버그 아님).
