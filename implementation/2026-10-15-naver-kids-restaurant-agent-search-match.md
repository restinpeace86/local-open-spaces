## 변경 사항
### `scripts/naver-kids-restaurant-agent/lib/`(신규)
- `apollo-state.mjs`: `naver-place-crawler.ts`와 동일한 `__APOLLO_STATE__`
  파싱/역정규화 로직을 독립 복제(이 에이전트는 `src/`를 import하지 않음).
- `naver-search.mjs` + 테스트(4개): `pcmap.place.naver.com/place/list?query=`가
  검색 결과 페이지도 서버 렌더링(`PlaceListBusinessesItem:<id>` 엔티티에
  명칭/도로명주소/지번주소/전체주소/좌표가 전부 포함)임을 실측 확인(2026-10-15)
  해, Playwright 없이 fetch만으로 검색 결과를 받는다.
- `address-match.mjs` + 테스트(15개): 이름 유사도(2-gram, 포함판정 허용)와
  주소 유사도(도로명+번지 추출 후 정확 일치만 고득점, Dice 계수로 전체 문자열
  대체 비교)를 각각 0.5 이상 만족하는 후보 중 최고점 하나만 확정(`pickBestCandidate`).
  **실측으로 발견한 설계 버그**: 초안은 주소도 이름과 같은 "포함판정"(짧은
  문자열이 긴 문자열에 포함되면 1.0)을 썼는데, 번지 없는 도로명 조각이 항상
  완전한 주소의 부분 문자열이라 번지 일치 여부와 무관하게 무조건 1.0이 나와
  실제로 다른 건물(번지 다름)과 구분이 안 됐다 — 주소는 포함판정을 빼고
  도로명+번지 정확 일치만 고득점으로 수정했다.
- `gemini-client.mjs` + 테스트(5개): `scripts/ingest/lib/ai-tagging.mjs`의
  Gemini 호출 패턴(이 프로젝트에 설정된 LLM 키가 GEMINI_API_KEY뿐임, OPENAI_API_KEY
  없음 — 실측 확인)을 구조화 출력(`responseSchema`)만 호출부가 바꿀 수 있게
  일반화.
- `llm-search-term.mjs` + 테스트(3개): 1차 검색이 주소까지 맞는 확정 후보를
  못 찾았을 때만(결정성/비용 때문에 매번 쓰지 않음) 명칭+주소를 Gemini에 던져
  더 정확한 검색어(지점명 등)를 제안받는다.

### `scripts/naver-kids-restaurant-agent/search-and-match.mjs` + 테스트(7개)
1차 검색 → 주소 교차검증 → 실패 시 LLM 보조 검색어로 2차 검색 → 확정되면
`네이버플레이스ID`/`네이버플레이스URL` 컬럼을 식당.csv에 추가. 재시작 가능
설계: 이미 ID가 있는 행은 건너뛰고, 매칭 실패는 빈 문자열이 아니라
`NOT_FOUND` 마커로 명시 기록(재실행 시 무한 재시도 방지), 429(네이버 WAF
레이트리밋)는 NOT_FOUND와 구분해 빈 값으로 남겨 다음 실행에서 재시도되게
한다. 20건마다 중간 저장.

## 특이 사항
- **설계 변경(Decision 037)**: todo.md는 1~4단계 전체를 Playwright로 구현하라고
  했으나, 검색 결과 페이지도 다른 네이버 플레이스 페이지들과 동일하게 정적
  서버 렌더링임을 실측 확인해 fetch 기반으로 구현했다 — 브라우저 구동 없이
  동작해 네이버 WAF 차단 위험이 더 낮고(이 세션에서 이미 실측된 429 레이트리밋
  전례 있음), 안정성도 더 높다.
- 전체 1,594건 실행은 하지 않았다(1건당 최대 2회 검색 × 500ms 간격 기준
  최대 약 27분 소요 예상) — 다음 단계(4~6단계: 상세/리뷰 스크래핑 + LLM
  키즈친화 속성 추출) 구현을 마친 뒤, 전체 파이프라인을 이어서 실행할
  예정이다.
