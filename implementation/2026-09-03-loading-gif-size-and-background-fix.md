# [버그 수정] 로딩 GIF 크기 확대 + 배경 색상 불일치 해결

## 구현 일시
2026-09-03

## 배경
직전 최대 경량화(3.15MB→60KB) 이후 "너무 작다"/"배경이 흰색이 아니라 주변과 색이
다르다"는 피드백.

## 원인 조사
- **배경 색상**: 원본 GIF의 배경을 실측(코너 픽셀 4곳 샘플)한 결과 `(252, 252, 255)`
  — 완전한 흰색(`#ffffff`)이 아니라 아주 미세한 푸른기가 도는 색이었다. 압축 과정의
  팔레트 양자화(32색)에서 이 배경색이 `(249~251, 249~251, 249~251)` 근처로 살짝
  바뀌면서, 페이지의 순수 흰 배경(`bg-white`)과 미세하지만 눈에 띄는 색 차이가
  생겼다 — 압축이 원인을 악화시켰지만, 애초에 원본부터 완전한 흰색은 아니었다.
- **크기**: 이전 버전은 화면 표시 영역(96px 정사각 박스)에 object-contain으로
  넣었는데, 원본이 16:9 비율이라 실제로는 세로 여백이 낭비돼 체감 크기가 더 작아
  보였다.

## 수정 내용
- **배경 투명화**: 원본 배경색 `(252,252,255)`을 기준색으로 색상 거리 임계값(18)
  이내의 픽셀을 전부 투명 처리한 뒤 재인코딩했다 — GIF는 완전 투명/불투명만
  지원해(반투명 불가) 안티앨리어싱 경계에 아주 미세한 흔적이 남을 수 있지만, 실제
  페이지 배경도 흰색이라 육안으로는 이음매가 보이지 않는다.
- **해상도/크기 상향**: 320×180(이전 112×63의 약 2.9배 해상도)로 다시 인코딩하고,
  화면 표시도 `h-24 w-24 object-contain`(96px 정사각, 여백 낭비) →
  `w-40 h-auto`(160px 너비, 원본 16:9 비율 그대로 — 실제 표시 크기가 커짐과 동시에
  여백 낭비 제거).
- 프레임 수(22)/팔레트(40색+투명 1)는 이전과 비슷한 수준으로 유지해 화질과 용량의
  균형을 다시 맞췄다.
- 결과: 60,317 bytes → 409,076 bytes (원본 3,157,115 bytes 대비 여전히 약 7.7배
  경량화 — 화질/크기 개선 요구를 반영하면서도 원본보다는 훨씬 가볍다).

## 검증
### 코드 검증
`npx tsc --noEmit`/`npm run test`(96파일 964건, 회귀 없음)/`npm run build` 통과.

### 실측 검증
- Pillow로 재오픈해 `transparency` 정보가 실제로 설정됐는지 확인.
- 흰 배경 위에 알파 합성한 미리보기 이미지를 직접 눈으로 확인해 이음매 없이
  자연스럽게 섞이는지 확인.
- dev 서버 curl로 `/loading/loading_image.gif`가 409,076 bytes로 정상 서빙됨을 확인.

## 특이 사항
- 파일 크기가 이전(60KB)보다 커졌지만, 이번 요청("조금 더 컸으면") 자체가 화질/크기를
  키우는 방향이라 예상된 트레이드오프다 — 원본(3.15MB) 대비로는 여전히 크게
  경량화된 상태다.
