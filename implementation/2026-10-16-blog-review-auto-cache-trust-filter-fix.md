실측 재현 2건:

  우연히 들어있다는 이유만으로 통과.
- "현대어린이책미술관 MOKA"(성남시 분당구 판교) → "현대백화점 판교점"

  이유만으로 통과(이 미술관과 전혀 무관).

## 변경 사항
### `src/lib/spaces/blog-review-cache.ts`
1. **상호명 일치를 항상 필수**로 요구하도록 수정(지역 정보가 있어도
   생략하지 않음).
2. 다만 "위키"처럼 짧은(4자 미만) 이름은 "나무위키"/"위키인포"처럼 더 긴
   단어 안에 그냥 끼어 있어도 단순 포함 검사로는 걸러지지 않아,
   `containsAsWholeWord`로 그 상호명이 더 긴 한글/영문 단어의 일부가
   아니라 독립된 단어/구로 등장하는지까지 확인한다(공백을 지우기 전
   원문 기준 앞뒤 글자가 한글/영문/숫자가 아닌지 검사).
3. **1차 수정 후 실측으로 발견한 과잉교정**: 짧은 이름 전용 엄격 검사를
   모든 이름에 적용했더니, "용인어린이상상의숲"(공백 없이 저장)을 블로그
   글이 "용인어린이상상의 숲"(사람이 읽기 편하게 띄어 쓴 표기)으로 적은
   명백히 맞는 리뷰까지 떨어뜨렸다 — 4자 이상의 충분히 길고 구체적인
   이름은 그 자체로 고유해 더 긴 무관한 단어 안에 통째로 묻힐 위험이
   거의 없으므로, 공백을 전부 지우고 포함 여부만 보는 느슨한 비교로
   되돌렸다(`SHORT_NAME_LENGTH = 4` 기준으로 분기).
4. "위키(WIKI)"처럼 상호명에 영문 병기가 괄호로 붙어있으면 실제 블로그
   본문에 그 표기까지 그대로 적히는 경우는 드물어, 괄호 안 내용은 떼고
   핵심 상호명만으로 비교한다(`stripParenthetical`). 상호명이 1글자뿐이면
   판정 근거가 안 돼 무조건 신뢰하지 않는다.

### `src/lib/spaces/blog-review-cache.test.ts`
기존 테스트 중 일부가 상호명이 실제 로직에 반영되지 않던 옛 설계를 그대로
전제하고 있었다(스팟명을 'A'/'아무개' 같은 의미 없는 값으로 둬도 지역명만
으로 통과하는 것을 기대) — 현실적인 상호명으로 교체하고, 아래 회귀
테스트를 추가했다(16개 테스트 전부 통과):
- "나무위키"/"위키인포" 실측 사례(짧은 이름이 더 긴 무관한 단어에 묻힌
  경우는 불신뢰).
- "용인어린이상상의숲" 공백 표기 차이 사례(긴 이름은 공백 유무와 무관하게
  신뢰).

### 데이터 — 전체 자동 캐시 재검증 및 정리
사용자가 독립적으로 같은 버그를 2번 신고해(위키/MOKA) 패턴성 문제로
판단, 자동 캐싱이 적용된 전체 스팟을 재검증했다. 실측: 캐시가 있던 32건
중 **29건**이 수정된 로직으로는 통과하지 못하는 URL을 하나 이상 포함하고
있었다(예: "AK플라자 분당"은 2건 중 1건만 정상, "서초구_1808-05"는 3건
모두 유류가격/부동산세 등 완전 무관). 이 29건 + 수동으로 먼저 확인한
위키/MOKA 2건, 총 31건의 `blog_review_urls`를 비우고
`blog_review_updated_at`을 null로 되돌려, 10일 TTL이 끝날 때까지
기다리지 않고 다음 조회 시 즉시 새 로직으로 재검증되게 했다(남은 3건은
전부 통과해 그대로 유지).

## 검증
- `npx tsc --noEmit` / `npm run test -- --run`(330개 파일 3,291개 테스트) /
  `npm run build` 전부 통과(중간에 `profile-completion-guard.test.tsx` 1건이
  간헐적으로 실패했으나 이 변경과 무관한 기존 타이밍 플레이크임을 격리
  재실행으로 확인 — 3회 중 2회 실패/1회 통과, 전체 재실행 시 정상 통과).
- 캐시돼 있던 실제 URL들을 모바일 페이지(`m.blog.naver.com`)의
  `og:title`/`og:description`으로 직접 조회해 무관함을 확인(위키/MOKA 둘 다).
- 32건 전체를 같은 방식으로 재검증하는 일회성 스크립트를 실행해 29건이
  수정된 로직을 통과하지 못함을 확인하고 DB에서 실제로 비웠다(커밋 대상이
  아닌 임시 스크립트라 작업 후 삭제).

## 특이 사항
- 관리자 수동 큐레이션 화면(`use-spot-curation-form.ts`의 `hasRegionMismatch`)
  은 건드리지 않았다 — 그쪽은 관리자가 결과를 직접 보고 고르는 "경고 표시"
  일 뿐이라 지역명만으로도 충분하지만, 이번에 고친 경로는 사람이 전혀
  검수하지 않는 완전 자동 캐싱이라 더 엄격한 기준이 필요했다(용도가 다른
  두 로직을 하나로 합치지 않음).
- 캐시를 비운 31개 스팟은 다음에 그 스팟 상세를 조회하는 순간 네이버
  블로그 검색이 다시 실행돼 새 로직으로 재검증된 결과(0~3개)가 채워진다 —
  별도 배치를 돌리지 않아도 된다(기존 Cache-Aside 설계 그대로).
