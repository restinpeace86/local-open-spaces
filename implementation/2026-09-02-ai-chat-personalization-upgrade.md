# [개발요청] AI 챗봇 맞춤 추천 상세 구현 (초개인화 고도화 통합본)

## 구현 일시
2026-09-02

## 배경
기존 "스팟픽 AI 맞춤 추천 챗봇 엔진"(2026-09-01)의 8단계 인터뷰를 초개인화 요소(날씨
선제 제안, 지역 원클릭 선택, 로그인 프로필 자동 연동, 찜/방문 이력 반영)로 고도화하는
사용자 상세 요구사항. AI 챗봇 자체는 이 프로젝트에서 별도 `spec/` 문서 없이 채팅
지시로 직접 구현/개편해온 선례가 있어(spec/data/ai-rule.md는 다른 파이프라인용), 이번도
동일한 방식으로 진행했다.

## 구현 내용

### Step 1: 날씨 기반 선제적 제안 + 일정/지역 분기
- 인터뷰 시작 즉시 오늘 날씨를 조회해 요구사항 예시 문구 그대로 제안한다
  (`buildProactiveWeatherSuggestion`, weather-reaction.ts). 선택지 3종(제안대로/다른
  스타일/전체 믹스) → `outdoorPreference` 확정.
- "오늘 바로 vs 다른 날"(기존 WHEN_OPTIONS 재사용) 이후 다른 날짜를 고르면 그 날짜
  예보로 위 제안을 한 번 더 수행한다.
- 지역 선택: `useUserLocation()`의 `sigunguName`을 기본값으로 제안하고, "다른 지역"
  선택 시 기존 `LocationOnboardingModal`(GPS/검색/수동 선택 이미 구현됨)을 재사용해
  받는다. **이 변경은 챗봇 세션 한정 검색 중심 좌표만 바꾸고 앱 전역 위치(localStorage)
  는 건드리지 않는다** — 질문 하나로 전체 앱 위치가 조용히 바뀌면 사용자가 놀랄 수
  있다고 판단한 구현 결정.

### Step 2: 로그인 프로필 자동 연동 (나이 자동 계산)
- `profiles.birth_years`(Decision 018)로 나이를 "연 나이"(현재 연도 - 출생년도)로
  계산한다 — 생일(월/일) 데이터가 없어 정확한 만 나이는 계산할 근거가 없음(추측 금지,
  `src/lib/ai-chat/personalization.ts`).
- 나이 → `target_age_group` 도메인(영유아/초등/전연령) 매핑은 영유아보육법의 실제
  법정 정의(취학 전 만 6세 이하)를 그대로 따름(임의 경계값 아님). 자녀가 여럿이고
  나이대가 갈리면 '전연령'으로 자연스럽게 처리.
- 나이 정보가 있으면 KIDS_COUNT/KIDS_AGE 단계를 건너뛰고 곧장 VIBE로 이동, 출생년도
  숫자는 절대 노출하지 않고 환산된 나이만 담은 인사말을 띄운다. 정보가 없으면(비로그인/
  birth_years 미입력) 기존 수동 질문으로 자연 폴백.
- "기계적 이동수단 질문 절대 금지"는 기존 TRANSPORT_OPTIONS("도보 가능한 가까운 곳"
  등)가 이미 이동수단+거리를 하나로 결합한 칩이라 별도 조치 없이 이미 충족돼 있다고
  판단(구현 판단, 기록에 명시).

### Step 3: 찜/방문 이력 반영
- ① 찜(user_bookmarks, Decision 019) 스마트 연동: 검색 결과 스코어링에 큰 가중치
  (+50점)를 줘 상단 배치하고, `SearchResultItem`에 `isBookmarked` 플래그를 추가해
  카드에 하이라이트(❤️ 찜한 곳) 표시. 검색 라우트가 실제 조회한 스팟 이름으로 별도
  하이라이트 멘트("아, 그리고 엄마가 전에 찜해두셨던 [OO공원]이...")를 만들어 LLM
  환각 위험 없이 정확한 이름을 보여준다.
- ② 방문 이력 기반 중복 배제: 이 앱에는 별도 "방문 이력" 테이블이 없지만,
  `mom_pick_posts`(Decision 019 — 후기/체크리스트)는 본인이 실제로 그 스팟에 다녀왔다는
  사실을 이미 담고 있는 기존 데이터라, 신규 개념을 지어내지 않고 그대로 재해석해
  사용했다(제5장 제4조 기존 구조 우선). 완전 제외(후순위 아님) 방식 — 결과가 부족해지면
  기존 반경 완화 폴백이 흡수한다.
- ③ 실내/야외/식사 시간대 꼬리질문은 기존 MEAL 단계를 그대로 유지했다 — "스마트 조건부"
  경계(어느 시간대까지 물어야 하는지)가 원문 예시만으로는 명확히 정의되지 않아 임의
  규칙을 추측으로 추가하지 않고 기존 동작(모든 시간대에서 질문)을 유지했다(구현 판단,
  기록에 명시).

### 최종 출력 UX
- 검색 제출 후 최소 1.3초 로딩 텀 보장(`MIN_SEARCH_LOADING_MS`, 실제 응답이 더 빨라도
  `Promise.all`로 최소 대기).
- "부족하면 온가족 함께 태그로 보완"은 기존 반경 완화 폴백 + "공공시설 최소 1개 보장"
  믹스 룰이 이미 담당하는 역할과 동일해 별도 신규 태그를 만들지 않았다(target_age_group
  '전연령'이 사실상 "온가족 함께"에 해당하는 기존 값).
- 카드 UI에 찜 하이라이트 배지 추가.

## 실측으로 발견해 함께 고친 심각한 성능 버그
Step 1 구현 중 `/api/ai-chat/weather`가 서울 도심 좌표에서 매번
"canceling statement due to statement timeout"으로 실패하는 것을 실측으로 발견했다.
`EXPLAIN ANALYZE`로 원인을 직접 확인한 결과, `get_nearest_spot_weather` RPC
(2026-09-01 도입)가 `st_dwithin`(반경 20km) 방식이라 스팟 밀집 지역(서울 도심 반경
내 open_spaces 3만9천여 건)에서 후보를 전부 모은 뒤 정렬·limit을 적용해 3.86초가
걸렸다. PostGIS KNN 인덱스 연산자(`<->`)로 정렬하도록 재작성해 기존 GiST 인덱스
(idx_open_spaces_location_geography, 2026-08-29 도입)를 최근접 탐색에 실제로 활용하게
했다 — 실측 재검증 결과 3,863ms → 56ms로 개선, 서비스 라우트 curl 재확인으로 정상
응답 확인. 이 버그는 이번 세션 이전(2026-09-01)에 이미 존재했으나 그때는 발견되지
않았던 latent 이슈다.

## 검증
### 코드 검증
`npx tsc --noEmit`/`npm run test`(95파일 953건 — 신규 personalization.ts 테스트 9건
포함)/`npm run build` 통과.

### 실측 검증
- 라이브 DB에 `get_nearest_spot_weather` KNN 재작성 마이그레이션 적용, `EXPLAIN
  ANALYZE`로 인덱스 스캔 전환 및 실행시간 개선(3863ms→56ms) 직접 확인.
- dev 서버로 `/api/ai-chat/weather` curl 재현 — 수정 전 100% 재현 실패, 수정 후 정상
  응답(맑음/흐림/EITHER 3가지 문구 분기 모두 유닛 테스트로 커버) 확인.
- `/api/ai-chat/search` curl로 `isBookmarked`/`bookmarkedSpotName` 필드가 응답에
  정상 포함됨을 확인(비로그인 요청이라 각각 false/null — 로그인 사용자의 실제 찜/후기
  데이터가 있어야 true/실제 이름이 나오는 조건부 로직이라 이 이상은 실제 계정으로
  검증 필요).

## 특이 사항
- `database.types.ts`는 RPC 본문만 바뀌고 시그니처(입출력 타입)는 그대로라 재생성해도
  diff 없음을 확인 — 별도 커밋 불필요.
- 찜/방문 이력 반영 로직의 실제 효과(로그인 사용자가 찜한 곳이 진짜로 상단에 뜨는지,
  방문한 곳이 진짜로 빠지는지)는 실제 계정으로 찜/후기를 몇 건 만든 뒤 챗봇을 실행해
  눈으로 한 번 확인해보길 권장한다 — 이번 자동화 검증은 API 응답 필드 존재까지만
  확인했다(비로그인 상태로는 그 이상 실측이 불가능).
