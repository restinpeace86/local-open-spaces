# 중복 스팟 검수 — 스캔 페이지 100건 상향 + 그룹 오픈 시 실제 반경 재조회 보강

## 구현 대상
사용자 지시: "50건씩은 너무 적어 100건씩 스캔하기 해.. 그리고 한강
난지공원인가.. 이거 많이 묶여야하는데 50건씩하다보니 끊겨서 두개그룹으로
됐네."

## 구현 일시
2026-09-09

## 변경 사항
### 1. 스캔 페이지 크기 50 → 100
`spot-dedup-panel.tsx`의 `GROUPS_PAGE_SIZE`와 `/api/admin/spot-dedup/groups/
route.ts`의 `DEFAULT_LIMIT`을 100으로 올렸다. 겸사겸사 실제 버그도 하나
고쳤다: 기존에는 `GROUPS_PAGE_SIZE`가 버튼 문구("다음 50건 더
스캔하기")에만 쓰였을 뿐 실제 API 요청에는 `limit` 파라미터가 전혀 실려
있지 않아서, 실제 페이지 크기는 서버의 `DEFAULT_LIMIT`에만 의존하고
있었다 — 두 상수가 우연히 같은 값(50)이라 지금까지 드러나지 않았을 뿐이다.
이제 클라이언트가 `limit=100`을 명시적으로 실어 보내 단일 진실 공급원이
되도록 고쳤다.

### 2. 그룹을 열 때 실제 반경 재조회로 보강(핵심 수정)
스캔 페이지네이션은 geohash 정렬 순서로 진행되는데, 이 정렬이 실제 좌표
근접성을 완벽히 보장하지 않는 경계 사례가 있어(예: 한강공원 난지캠핑장처럼
같은 좌표에 수십 건이 몰려있는 경우) 같은 실제 장소의 멤버가 서로 다른
페이지로 흩어지면 한 번의 스캔에 다 걸리지 못해 그룹이 여러 개로 쪼개져
보일 수 있다. 페이지 크기를 올리는 것만으로는 근본 해결이 아니다(더 큰
케이스는 여전히 쪼개질 수 있음) — `handleOpenGroup`에서 그룹을 열 때마다
**각 멤버 좌표 기준으로 실제 30m 반경을 다시 조회**한다(기존
`find_nearby_open_spaces` RPC/`/api/admin/spot-dedup/nearby` 엔드포인트를
그대로 재사용 — `SpotDedupQuickModal`이 이미 같은 방식으로 쓰고 있음, 제5장
제4조). 스캔에서 놓친 멤버가 발견되면 자동으로 그룹에 합쳐 보여준다 — 페이지
크기와 무관하게 항상 "실제 위치 기준으로 완전한 그룹"을 보장한다.

- 이때 그룹을 여는 시점에 이미 'in_progress'로 임시 저장해둔 원본(보강 전)
  키가 보강 후 달라진 조합과 어긋나 유령 항목으로 남는 것을 막기 위해,
  보강된 전체 조합으로 다시 저장하고 원래 키는 정리한다([[2026-09-09-dedup-
  group-partial-exclusion]]에서 부분 제외 시 만든 것과 동일한 패턴).
- 보강 조회가 실패해도(네트워크 오류 등) 기존 스캔 결과 그대로 검수를
  계속할 수 있다(제5장 제11조 — 부가 기능 실패가 핵심 흐름을 막지 않음).

## 검증
- `spot-dedup-panel.test.tsx`: 신규 2개 — (1) 스캔에서 2건만 잡힌 그룹을
  열면 실제 반경 재조회로 놓친 3번째 멤버가 자동으로 합쳐져 3건이 됨을
  확인, (2) 보강 조회가 실패해도 기존 2건 그대로 검수 가능함을 확인.
  기존 "다음 50건 더 스캔하기" 관련 테스트는 "100건"으로 문구를 갱신했다.
- `npx tsc --noEmit` / `npm run test`(1384건, 기존 1382 + 신규 2) /
  `npm run build` 전체 통과.

## 특이 사항
- 보강 조회는 그룹 멤버 수만큼 병렬 요청(`Promise.all`)을 보낸다 — 이
  패널에서 다루는 그룹은(체크박스 부분 제외 기능 도입 이후) 실사용 범위에서
  보통 2~5건 수준이라 부담이 크지 않다. 수십~수백 명 규모의 극단적으로 큰
  그룹이 자주 발생한다면 대표 멤버 1~2건만 조회하는 최적화가 필요할 수
  있다는 한계를 감수한다.
