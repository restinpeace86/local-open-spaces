# 네이버 플레이스 검색 — "공원" 변형 재시도 추가 (유아숲체험원 매칭 보완)

## 구현 대상
사용자 지시(2026-10-16, 유아숲체험원 매칭 중): "제목/명칭 그대로도 넣어보고
안나오면 다르게도 바꿔봐 예를들어 불암산공원 유아숲체험원은 불암산 유아숲체험원
처럼."

## 구현 일시
2026-10-16

## 변경 사항
### `scripts/naver-kids-restaurant-agent/search-and-match.mjs`
`buildGenericRetryTerm(name)` 추가 — 이름에서 괄호 내용과 "공원"을 제거해
변형이 생기면(원본과 다르면) 그 이름으로 한 번 더 검색한다. 1차(원본명)
검색 실패 시, LLM 보조 검색어 단계보다 먼저 시도한다(결정적 문자열 변형이라
무료·빠름). 주소 교차검증(`pickBestCandidate`)은 그대로 거치므로 "공원"이
없는 다른 카테고리(식당 등)에서도 안전하다 — 변형 자체가 안 생기면(null)
재시도를 건너뛰고, 변형이 생겨도 주소가 안 맞으면 매칭되지 않는다(오탐
방지, 추가 네트워크 요청만 하나 더 생김).

### `search-and-match.test.mjs`
테스트 2개 추가(공원 제거 재시도 성공 사례, "공원" 없는 이름은 재시도
단계 자체를 건너뜀 — 호출 횟수로 확인).

## 검증
- `npx tsc --noEmit` / `npm run test -- --run`(331개 파일 3,301개 테스트) /
  `npm run build` 전부 통과.
- **실측으로 확인한 한계**: "불암산공원 유아숲체험원" 사례를 직접 재현해본
  결과, 이 특정 건은 "공원" 제거가 아니라 **애초에 1차 검색(원본명)만으로도
  "불암산 유아숲체험장"이 결과에 포함돼 있었다** — 문제는 검색어가 아니라
  우리 DB의 "불암산공원 유아숲체험원"이 같은 산 안에 서로 다른 번지로 4건
  등록돼 있는데, 네이버에는 그 중 1곳(불암산 산림치유센터)만 독립된
  Place로 등록돼 있어 나머지 3건은 애초에 대응하는 Naver Place가 없을
  가능성이 높다는 것이다 — 이 경우 "매칭 실패(NOT_FOUND)"가 정확한
  결과이고, 검색어를 더 바꾼다고 해결되는 문제가 아니다(아래 "특이 사항"
  참고).

## 특이 사항
- 이번 추가는 사용자가 예시로 든 "공원 제거" 패턴만 구체적으로 구현했다 —
  "유아숲체험원으로 넓게 검색해서 주소로 매칭"이라는 두 번째 제안은 구현
  하지 않았다. 실측 확인 결과 그 넓은 검색도 결국 같은 한계(한 산에 여러
  번지 등록, 네이버엔 1곳만 Place로 존재)에 부딪혀 실효성이 낮아 보이고,
  좌표 기반 매칭으로 바꾸려면 `address-match.mjs`의 "도로명+번지 불일치 시
  낮은 점수" 규칙(Decision 039, 위키/MOKA 오탐 방지용)을 이 카테고리에서만
  완화해야 하는데 — 그 규칙은 다른 카테고리(식당 등)의 오탐을 막는
  핵심 장치라 여기서만 느슨하게 바꾸는 게 맞는지는 사용자 판단이 필요해
  임의로 바꾸지 않았다(제3장 제5조).
