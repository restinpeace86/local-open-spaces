# 중복 스팟 탐지 정확도 개선 — 실제 신고 사례 재현 및 4가지 근본 원인 해결

## 구현 대상
사용자가 관리자 화면에서 직접 확인한 실제 데이터로 중복 탐지 누락을 지적:
- "물빛어린이공원 바닥분수"와 "판교제2호(물빛)공원"은 같은 위치인데 좌표가 미세하게
  다르지만 묶이지 않는다.
- "성남시운중도서관"과 "운중도서관 시청각실"은 같은 곳인데 묶이지 않는다.
- "판교원마을 3단지 유아놀이터"와 "판교원마을3단지 산오름놀이터"도 같은 곳 같은데
  묶이지 않는다.

## 구현 일시
2026-09-05

## 조사 — 실측으로 확인한 4가지 근본 원인
세 사례를 라이브 DB에서 직접 조회·검증하며 순서대로 발견했다(추측 없이 전부 실측):

1. **좌표 근접 판정이 부정확함**: "물빛어린이공원 바닥분수"~"판교제2호(물빛)공원"은
   `ST_Distance(geography)`로 직접 확인한 실제 거리가 **26.2m**인데, 기존
   `ST_ClusterDBSCAN`의 degree 기반 근사 임계값(eps=0.00027도 ≈ 30m "근사치")을
   근소하게 벗어나 놓쳤다 — 위경도를 degree 단위 그대로 유클리드 거리로 비교하면
   위도에 따라 경도 1도의 실제 거리가 달라져 부정확하다.
2. **더 치명적인 원인 — 페이지네이션 순서**: "성남시운중도서관"~"운중도서관
   시청각실"(실제 6.9m)과 "판교원마을3단지" 두 놀이터(좌표·주소 완전히 동일)처럼
   명백한 중복조차 놓쳤다. 원인은 2026-09-04에 도입한 페이지네이션이 `id`(사실상
   무작위 uuid) 순으로 스캔해, 실제로 가까운 두 행이 같은 배치(50건)에 함께 걸릴
   확률이 142,113건 중 사실상 0에 가까웠기 때문이다 — `ST_GeoHash`로 확인해보니
   이 세 쌍 전부 geohash 앞자리가 7~9자리까지 동일하거나 거의 동일해 공간적으로는
   이미 매우 가까웠지만, id 순서상으로는 전혀 무관한 위치에 흩어져 있었다.
3. **콜레이션 버그**: geohash 기반 정렬로 고치는 과정에서, "위치 없는 행"을 위한
   대체 키(`'~' || id`)가 이 DB의 기본 콜레이션(`en_US.UTF-8`)에서 `'~' < 'a'`가
   **true**라(직접 확인) 유효한 geohash 값보다 먼저 정렬되는 반대 결과를 낳는 것을
   발견했다 — `COLLATE "C"`(순수 바이트 비교)를 명시해 해결했다.
4. **위치 정보 오염**: geohash 정렬 결과를 실제로 확인하는 과정에서, 위도 19.69/
   경도 117.99(한국이 아니라 남중국해 부근)라는 명백히 잘못된 좌표를 공유하는 행이
   **37건**(실측) 있음을 발견했다 — 실제 주소는 서울/부산/제주 등 전국 각지로
   전혀 무관한데 좌표만 우연히 같아, 그대로 두면 이 37건이 거대한 가짜 "중복 의심
   그룹"으로 잘못 묶일 뻔했다. 대한민국 바운딩 박스(위도 33~39, 경도 124~132)를
   벗어나는 좌표는 "위치 정보 없음"과 동일하게 취급하도록 방어했다.
5. **커서 페이지네이션 자체의 timeout**: 위 개선들을 반영한 `language sql` 함수가
   `p_after_key`가 NULL일 때(첫 페이지)는 빠르지만(227ms), **NULL이 아닌 실제 커서
   값을 넘기면 즉시 statement timeout**에 걸리는 것을 실측으로 발견했다 — 동일한
   조건을 함수 밖 리터럴로 직접 실행하면 인덱스를 정상적으로 쓰는데, 함수
   **파라미터**로 넘기면 플래너가 제네릭 계획으로 최적화하다 인덱스를 포기했다
   (2026-09-04 최초 timeout 사고와 동일한 클래스의 문제). `language plpgsql` +
   `EXECUTE format(...)`으로 바꿔 매 호출마다 커서 값을 리터럴로 직접 삽입한 SQL을
   즉석에서 새로 계획하도록 고쳤다(`quote_literal`로 인젝션 방지).

## 변경 사항

### DB 마이그레이션(4개, 순서대로 적용, 전부 라이브 반영 완료)
1. `2026-09-05-spot-dedup-geohash-scan-and-accurate-distance.sql`: 스캔 순서를
   `id` → `ST_GeoHash` 기반 공간 순서로 변경(전용 부분 인덱스 추가), 좌표 근접
   계산 자체는 SQL에서 제거(원시 lat/lng만 반환).
2. `2026-09-05-spot-dedup-scan-key-collation-fix.sql`: `COLLATE "C"` 명시로
   콜레이션 버그 수정.
3. `2026-09-05-spot-dedup-exclude-invalid-coordinates.sql`: 대한민국 바운딩
   박스를 벗어나는 좌표를 "위치 없음"과 동일 취급하도록 방어.
4. `2026-09-05-spot-dedup-fix-cursor-query-plan.sql`: `language sql` →
   `language plpgsql` + 동적 SQL(`EXECUTE format`)로 전환해 커서 페이지네이션
   timeout 해결.

### 애플리케이션 코드
- `src/lib/admin/spot-dedup-grouping.ts`: 좌표 근접 판정을 SQL(`ST_ClusterDBSCAN`)
  에서 애플리케이션(Haversine 공식, `haversineDistanceMeters` 신규 export)으로
  이전 — **누적된 전체 후보**를 대상으로 정확한 실제 미터 거리를 재계산한다.
  배치 경계에 걸려도 두 후보가 (어느 페이지에서든) 한 번씩만 스캔되면 정확하게
  합쳐진다. `DedupCandidateRow`에서 `proximity_cluster_id` 필드 제거.
- `src/app/api/admin/spot-dedup/groups/route.ts`: RPC 파라미터명 갱신
  (`p_after_id` → `p_after_key`), 외부 계약(쿼리 파라미터 `after`, 응답의
  `next_cursor`)은 둘 다 불투명한 문자열이라 변경 없음.
- `src/types/database.types.ts` 재생성(순수 반영, 수동 편집 없음).

## 검증(전부 실측 — 사용자가 지적한 실제 3개 사례로 직접 재현)
1. `haversineDistanceMeters`로 26.2m/6.9m 실측 거리를 정확히 재현하는 단위 테스트
   추가(회귀 방지).
2. 라이브 DB에서 `ST_Distance(geography)`로 두 사례의 실제 거리를 직접 확인(26.2m,
   6.9m) — 지시서의 "미세하게 다르지만"이라는 표현이 실제로는 최대 26m 차이임을
   확인.
3. `ST_GeoHash`로 세 쌍 모두 앞자리 7~9자리가 동일/거의 동일함을 확인해 페이지네이션
   순서 문제가 진짜 원인임을 검증.
4. 콜레이션 버그를 `select '~' < 'a'`로 직접 재현·확인.
5. 잘못된 좌표(19.69, 117.99) 공유 행 37건을 SQL로 직접 확인.
6. 커서 파라미터 timeout을 라이브 RPC 호출로 재현하고, plpgsql 전환 후 550ms로
   해결됨을 재확인.
7. **최종 통합 검증**: 수정된 RPC를 실제로 2페이지(100건) 연속 호출해 3개 사례의
   6개 행이 전부 함께 스캔되는지 확인했고, Haversine/주소 일치 로직을 그대로
   실행해 3쌍 모두(26.2m/6.9m/0m+동일주소) 정확히 연결됨을 확인했다.
8. 단위 테스트(`spot-dedup-grouping.test.ts`): 12개(신규 haversine 테스트 3개 +
   실측 사례 기반 회귀 테스트 2개 포함) 전체 통과.
9. `npx tsc --noEmit` 통과, `npm run test`(105개 파일/1107개 테스트, 기존 1102개 +
   신규 5개) 전체 통과, `npm run build` 프로덕션 빌드 통과.

## 특이 사항 (정직하게 기록)
- **geohash 순서가 "이 3가지 사례를 스캔 맨 앞에서" 보여주지는 않는다** — geohash는
  전 세계를 32진법으로 분할하는 순서라 "판교/성남" 지역이 알파벳순으로 어디쯤
  오는지는 지리적 중요도와 무관하다(실측: 대한민국 바운딩 박스 내에서 이 지역은
  약 70번째 백분위수에 위치, 처음 2페이지(100건)를 "그 지점부터" 스캔했을 때는
  즉시 함께 나타나지만, id=0부터 순서대로 스캔하면 여전히 수만 건을 지나야 한다).
  **핵심 개선점은 "어느 지역을 스캔하든, 그 지역 안의 진짜 중복은 반드시 함께
  나온다"는 것이지 "특정 사례가 맨 처음에 나온다"가 아니다** — 이 차이를 사용자가
  오해하지 않도록 명확히 기록한다.
- **위치가 없거나(NULL) 대한민국 밖으로 튀는 좌표를 가진 행 자체의 데이터 품질
  문제는 고치지 않았다** — 이 원천 데이터/지오코딩 파이프라인 결함은 이번 작업
  범위(탐지 도구가 이 결함에 오염되지 않도록 방어)를 넘어서는 별도 확인이
  필요하다. 37건이라는 규모 자체는 작아 급하지 않다고 판단했다.
- **"판교원마을 3단지" 두 놀이터**는 주소·좌표가 완전히 동일해 이미 정규화 주소
  일치로도 잡혔을 사례다 — 페이지네이션 문제만 해결됐어도 자동으로 잡혔을 것.
