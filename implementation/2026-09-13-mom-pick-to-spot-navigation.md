## 형식 선택(사용자가 추천을 요청함)
두 형식(① "이 장소가 궁금하신가요?" + 별도 CTA 블록, ② 장소 옆에 바로 가는
버튼) 중 ②에 가까운, 더 컴팩트한 "행(row) 버튼" 형식을 추천·채택했다 — 그리고
이 앱에는 이미 정확히 같은 목적의 UI가 있었다: 지도 화면(`detail-modal.tsx`,
개선사항10 "Event➔Spot" 이동)의 `📍 연결된 장소: {name} ›` 전체 너비 행
버튼이다. 이걸 그대로 재사용했다(제5장 제4조 기존 구조 우선). "궁금하신가요?"
블록을 채택하지 않은 이유:
- `PostDetailModal` 헤더에 스팟명이 이미 크게 보여서, 별도 블록에서 이름을
  다시 언급하면 정보가 중복된다.
- 블록형은 세로 공간을 더 쓰는데, 이 모달은 이미 태그/사진/좋아요로 내용이
  많다 — 컴팩트한 한 줄 행이 스크롤 없이 항상 보이는 데 유리하다.
- 기존 앱에 이미 있는 관례(같은 문구·모양)를 그대로 쓰면 사용자 입장에서
  "장소 연결" UI를 한 번 배우면 다른 화면에서도 똑같이 알아볼 수 있다.

## 구현 내용

### 1. `spot_id`를 DashboardPost까지 노출
`mom_pick_posts.spot_id`(2026-09-02 최초 테이블 생성 시부터 있던 컬럼,
`open_spaces.id` 참조)를 `mom-pick-dashboard.ts`의 `POST_COLUMNS`에 추가하고,
`DashboardPost.spotId: string | null`로 노출했다. 기존 `spotName`은 단순 표시
문자열(이름이 같은 스팟이 여러 개일 수 있음)이라 "정확히 어떤 open_spaces
행인지"를 특정할 수 없어, 별도로 id를 내려야 했다.

### 2. 신규 `GET /api/spots/by-id?id=<uuid>`
`/api/events/linked-spot`(개선사항10)이 이미 `SPACE_COLUMNS`/`toSpaceItem`으로
open_spaces 단건을 NearbyItem 모양으로 조회하고 있어 그 관례를 그대로
재사용했다. `{ item: NearbyItem | null }`을 반환한다.

### 3. `PostDetailModal`에 이동 링크 추가
헤더(스팟명/작성자/날짜) 바로 아래, 본문 태그 위에 `spotId`가 있을 때만
`📍 스팟픽에서 이 장소 보기 ›` 링크(`/nearby?spot={spotId}`)를 보여준다.
`spot_id`가 없는 글(이벤트를 가리키는 글, 또는 과거 데이터로 둘 다 비어있는
체크리스트 글 등)은 이동할 곳이 없으므로 행 자체를 숨긴다 — 이번 요청은
"스팟픽의 해당 장소"에 한정되어 있어(원문 그대로), 이벤트를 가리키는 글의
"이벤트픽으로 이동"은 이번 범위에 포함하지 않았다(제3장 제5조 추측 금지).

### 4. `/nearby`(map-explorer.tsx)의 `?spot=<id>` 딥링크 처리
`/nearby?spot=<id>`로 진입하면, 그 id로 `/api/spots/by-id`를 조회해 성공하면
곧장 `setSelectedItem(item)`으로 전체 상세(`DetailModal`)를 자동으로 연다.
기존 "마커 클릭 → 미리보기 → 재탭 → 상세"의 2단계 UX(2026-09-01)를 거치지
않고 바로 상세로 가는데, 이는 이미 리스트 클릭/AI 추천 등 "이미 한 번 명시적으로
고른 진입"에 적용되는 예외와 같은 성격이다(다른 화면에서 이미 스팟 하나를 콕
집어 온 경우이므로 미리보기 단계가 무의미).

## 특이 사항
- 이벤트를 가리키는 글(`event_id`)에 대한 "이벤트픽으로 이동"은 이번에
  구현하지 않았다 — 사용자 지시가 "스팟픽의 해당 장소"로 명시돼 있어 범위를
  넘기지 않았다. 필요하면 같은 패턴(`/api/events/linked-spot`처럼 이벤트
  단건 조회 + `/`(이벤트픽)에 `?event=<id>` 딥링크 추가)으로 확장 가능하다.
