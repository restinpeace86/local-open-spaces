# 문화센터 카드 라벨형 포맷(수업/접수/위치) + 이마트 썸네일 유실 버그 수정

## 구현 대상
사용자 피드백:
1. 카드를 "수업 9.2~11.4 매주 수요일 11:00-12:20 / 접수 7.24(금) / 위치
   롯데문화센터 본점 · 0.4km" 라벨형 포맷으로 바꿔달라. 접수일자는 날짜만
   (시간은 내부용으로만 유지), 접수 데이터가 없으면 "일정은 상세 페이지에서
   확인" 안내.
2. "사진 있는데 이마트껀 목록에 사진 없어서 그래? 상세쪽에 있는 사진을
   썸네일로 가져오면 안돼?" — 왜 리스트에 썸네일이 거의 안 나오는지 재조사.

## 구현 일시
2026-10-07

## 2번 — 재조사로 발견한 진짜 원인(지난 턴의 진단이 틀렸음)
지난 턴엔 "이마트 강좌의 92%는 원본에 사진 자체가 없다"고 결론 냈는데,
사용자가 "상세쪽엔 사진이 있다"고 지적해 다시 파봤다. 실측 결과 지난
진단이 틀렸다:
- `emart_culture_club_classes`(원본 테이블)는 실제로 6,563건 중 6,520건이
  이미 `detail_fetched_at`/`main_image_key`가 채워져 있었다(`emart-
  culture-club-detail.mjs`가 class_id당 한 번씩 상세 API를 조회해 채워둠).
- 그런데 화면이 실제로 읽는 통합 테이블(`culture_club_classes`)엔 544건
  (8.3%)만 이미지가 있었다 — 매일 도는 목록 배치(`emart-culture-club.mjs`)
  가 통합 테이블에 "이중 쓰기"할 때 `raw_extra`를 매번 새로 만들면서, 목록
  API 응답엔 애초에 `mainImage` 필드가 없어 `main_image_key`가 없는 채로
  덮어쓰고 있었다 — 상세수집이 이미 채워둔 값을 매일 지워버린 것.
- 또한 `emart-culture-club-detail.mjs`는 Windows 작업 스케줄러에 전혀
  등록돼 있지 않았다(실측: `schtasks /query`에 없음) — 2026-10-03 구현 때
  만들어졌지만 그 뒤로 자동 실행된 적이 없고, 지금 있는 데이터는 그때
  한 번 수동으로 돌린 결과였다.

## 변경 사항

### 2 — 이미지 유실 버그 수정
- `scripts/ingest/emart-culture-club.mjs`: 통합 테이블에 쓰기 전에 원본
  테이블에서 상세정보(이미지/설명/`detail_fetched_at`)를 class_id로 읽어와
  병합하는 `mergeDetailEnrichment()`를 추가(+ 원본 테이블 조회 함수
  `fetchDetailEnrichmentByClassId`). 이제 매일 돌아도 상세수집이 채운
  값을 지우지 않는다.
- `LocalOpenSpaces-EmartDetailFetch`(신규, 매일 09:40 — 메인 배치
  09:00보다 뒤에 둬서 그날 신규 class_id가 먼저 채워진 뒤 실행되게 함)
  작업 스케줄러 등록.
- 지금 바로 실제 배치를 다시 돌려 확인: 통합 테이블의 이미지 보유율이
  544건(8.3%) → 6,310건(96%)으로 즉시 반영됐다. 남아있던 상세수집 미처리
  43건도 수동으로 한 번 더 돌려 전부 처리했다(이제 이마트 전체가 거의
  다 상세수집 완료 상태).

### 1 — 카드 라벨형 포맷
- `ClassCard`를 "수업/접수/위치" 3줄 라벨 형식으로 바꿨다:
  - 수업: `{시작~종료 월.일}{단발성이면 하나만} 매주 {요일}요일 {시작-종료
    시간}` (예: "9.2~11.4 매주 수요일 11:00-12:20").
  - 접수: `register_start_at`(날짜만, 시간은 표시 안 함 — 접수 시작 알림
    기능은 여전히 전체 타임스탬프를 그대로 쓴다, `CultureClubReservationHint`
    참고) ~ `raw_extra.register_end_date`(이마트만 있음)를 "M.D(요일)" 또는
    "M.D(요일) ~ M.D(요일)"로. 데이터가 전혀 없으면(롯데마트 등) "일정은
    상세 페이지에서 확인"으로 안내(추측해서 날짜를 만들어내지 않음).
  - 위치: 기존 그대로(지점명 · 거리).
- **타임존 버그 발견 및 수정**: `register_start_at`은 "+09:00"까지 포함한
  완전한 타임스탬프라 `new Date(iso)` 후 `.getMonth()/.getDate()`를 부르면
  실행 환경의 로컬 타임존 기준으로 날짜를 읽어 KST가 아닌 환경에서는
  날짜가 하루 밀릴 수 있다(실측 — 테스트 환경에서 하루 어긋남을 직접
  확인). 이 앱은 한국 사용자 전용이라, UTC epoch에 9시간을 더해 UTC
  getter로 읽는 `kstDatePartsFromIso()`로 고쳐 실행 환경 타임존과 무관하게
  항상 KST 날짜가 나오게 했다.
