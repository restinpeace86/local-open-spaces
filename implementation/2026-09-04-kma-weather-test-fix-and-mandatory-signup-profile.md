사용자 지시(원문): "날씨 수집 배치의 재시도 지연 관련해서 봐줘 그리고 구글/카카오
인증되면 바로 회원가입폼으로 가서 닉네임, 아이 연령(연도: 22년생), - 2명이면 2명
받고.. 이건 기본으로 받게해줘 나중에 마이페이지에서 입력하는게 아니고..."

## 구현 일시
2026-09-04

## 변경 사항

### 1. `kma-weather-adapter.test.mjs` 재시도 지연 테스트 수정
직전 턴에서 발견해 미루고 있던, 이번 세션의 변경과 무관한 기존 결함이다. 원인:
`withRetry`(재시도 유틸)가 실패한 격자(nx=98)에 대해 실제로 5000ms → 10000ms를
순서대로 기다린다(2026-08-30 사용자 지시로 확정된 정책값 — 그 지연 자체는 버그가
아니다). 해당 테스트는 이 실제 지연을 fake timer 없이 그대로 기다리다 vitest 기본
테스트 타임아웃(5000ms)과 충돌해 항상 실패했다(실측: 이번 세션 변경 없이도 동일하게
재현 확인).

`vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync(5000)` → `(10000)`으로 두 번의
백오프 지연을 순서대로 흘려보내 실제 재시도 로직(횟수/지연 시간)은 그대로 검증하면서
실행 시간만 건너뛰도록 고쳤다. 반복 실행(3회)으로 안정적으로 통과함을 확인했다.

### 2. 구글/카카오 인증 직후 필수 프로필 입력 (닉네임 + 아이 출생년도)
**사전 확인**: `project/decision-log.md` Decision 018/019, `implementation/todo.md`,
코드 주석 전체를 검색했으나 "별도 회원가입 폼을 만들지 않는다"는 명시적 결정은 어디에도
없었다 — 기존 "로그인 후 마이페이지에서 편집" 방식은 Decision 018/019가 최소 범위로
구현하며 남은 결과물일 뿐, 그 자체를 지킬 의도로 내려진 결정이 아니었다(실측 확인 —
`my-page-view.tsx`/`birth-years-editor.tsx`의 주석도 "가장 단순한 폼"이라고만 설명할 뿐
신규 가입 폼을 배제하는 근거를 담고 있지 않았다). 상충하는 Decision이 없어 그대로
구현을 진행했다.

**기존 구조 재사용**: `profiles` 테이블에 `nickname`(nullable text)/`birth_years`
(int[], 기본 빈 배열) 컬럼이 이미 있었고, 저장 함수(`updateNickname`/`updateBirthYears`,
`src/lib/auth/profile.ts`)도 이미 있었다 — 새 DB 마이그레이션 없이 그대로 재사용했다
(제5장 제4조 기존 구조 우선).

**신규 구현**:
- `src/components/auth/complete-profile-view.tsx`(신규): 닉네임 + 아이 출생년도
  (여러 명 가능, "+ 아이 추가"로 행 추가)를 한 폼에서 받는다. 둘 다 유효한 값을 채워야
  제출 가능(닉네임 비어있음/유효한 출생년도 0명이면 커스텀 에러 문구, 저장 실패도 문구
  안내). 이미 한쪽만 채워진 경우(예: 닉네임만 있음) 기존 값을 덮어쓰지 않도록 진입 시
  먼저 불러와 채운다. `<form noValidate>`로 브라우저 네이티브 min/max 검증이 커스텀
  에러 문구보다 먼저 폼 제출을 막아버리는 문제를 없애고 검증을 전부 JS 로직 하나로
  통일했다(실측으로 발견 — 테스트 작성 중 네이티브 제약 검증이 onSubmit 자체를 막는
  것을 확인).
- `src/app/auth/complete-profile/page.tsx`(신규): 위 화면의 라우트. `useSearchParams()`
  (콜백이 넘긴 `?next=` 확인용)를 쓰므로 `/my/page.tsx`와 동일하게 Suspense로 감쌌다.
- `src/components/auth/profile-completion-guard.tsx`(신규): "인증 직후 한 번만 보여주고
  끝"이 아니라 "기본으로 받게" 만들기 위한 전역 가드. `auth/callback`의 리다이렉트만으로는
  회원가입 폼을 닫고 나가버린 사용자를 다시 잡을 수 없다(세션이 이미 있으면 이후 방문은
  콜백을 다시 거치지 않는다) — 로그인 상태에서 어느 화면으로 이동하든 프로필이
  비어있으면(`!nickname || birth_years.length === 0`) `/auth/complete-profile`로
  되돌려보낸다. 한 번 "완료됨"을 확인하면 그 세션 동안은 다시 조회하지 않아(페이지
  이동마다 profiles를 재조회하는 낭비 방지) 성능 영향은 미미하다. `src/app/layout.tsx`에
  `<BottomTabs />`와 나란히 전역 마운트했다.
- `src/app/auth/callback/route.ts`: `exchangeCodeForSession` 성공 직후, 신규/기존
  사용자 모두에 대해 프로필의 nickname/birth_years를 한 번 조회해 비어있으면 원래
  목적지(`next`) 대신 `/auth/complete-profile?next=<원래 목적지>`로 보낸다.
  `handle_new_user()` 트리거는 id만으로 빈 프로필 행을 만들 뿐 이 두 값을 채우지
  않으므로(실측 확인), 신규 가입자는 항상 이 화면을 먼저 보게 된다.

**기존 마이페이지 편집 기능은 유지**: `NicknameEditor`/`BirthYearsEditor`(`/my`)는
그대로 남겨뒀다 — "나중에 마이페이지에서 입력하는 게 아니고"는 "최초 수집을 마이페이지에
미루지 말라"는 뜻으로 해석했고(사용자 지시 원문), 이미 완료한 뒤 닉네임을 바꾸거나
둘째 출생년도를 추가하는 등 "나중에 수정"은 여전히 정당한 사용 사례라 제거하지 않았다.

## 특이 사항
- 회원가입/온보딩 화면인데도 `layout.tsx`가 모든 라우트에 `<BottomTabs />`를 무조건
  렌더링해, `/auth/complete-profile` 접속 중에도 하단 탭이 함께 보인다 — 탭을 눌러
  다른 화면으로 가더라도 `ProfileCompletionGuard`가 즉시 다시 이 화면으로 되돌려보내
  기능적으로는 우회되지 않지만, 하단 탭이 계속 보이는 것 자체는 다듬지 않았다(이번
  범위를 "필수로 받게 한다"는 기능 요구에 한정했다 — 온보딩 화면 전용 크롬 숨김은
  별도 후속 작업으로 남겨둘 만하다).
- 검증: `npx tsc --noEmit` 통과, `npm run test`(99개 파일/1041개 테스트, 항목1의
  기존 실패 테스트 포함 전체 통과), `npm run build` 프로덕션 빌드 통과(`/auth/
  complete-profile` 라우트 정상 생성 확인). 실제 카카오/구글 OAuth 왕복이나 브라우저
  화면 확인은 이 환경에 브라우저/OAuth 테스트 자격 증명이 없어 수행하지 못했다 —
  콜백 라우트의 리다이렉트 분기와 폼 검증/저장 흐름은 각각 단위/컴포넌트 테스트로
  검증했다.
