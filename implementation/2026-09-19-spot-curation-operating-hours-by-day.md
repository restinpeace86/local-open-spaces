# [스팟 큐레이션 — 요일별 영업시간]

## 구현 대상
사용자 지시(2026-09-19): 딸부자 닭갈비의 실제 네이버 영업시간(요일별로 다름 +
"목(9/24) 추석 연휴"/"금(9/25) 추석" 임시 스케줄)을 보여주며 "스팟 큐레이션에서
지금 영업시간이 이렇게 된 것들 못 담는 구조인데.. 요일별로 시간 담을 수 있고..
추석 연휴 같은 일시적인 거 담을 수 있어? 지금은 영업시작/영업종료/브레이크
시작/브레이크종료/라스트오더 이렇게만 있어서" — 확인 질문에 "요일별 표 진행,
매일 같으면 모든 요일 동일하게, 요일별로 다르면 요일별로"로 확정.

## 구현 일시
2026-09-19

## 설계 결정
- **요일별 정규 영업시간**: 새 필드 추가. 임시 예외(공휴일 등)는 이미 만든
  "공지 레이더" 기능이 이미 커버하고 있음을 확인했다(실측: 딸부자 닭갈비를
  실제로 크롤링해보니 "29일 30일 개인사정으로 쉽니다~"/"19일 20일 휴무입니다"
  같은 임시휴무 공지가 이미 자동으로 잡히고 있었음) — 정규 요일표에 억지로
  같이 담지 않고 그대로 공지 시스템에 맡긴다.
- 기존 `open_time`/`close_time`(단일 값)은 그대로 두고(하위 호환, 제5장 제3조),
  새 컬럼을 추가하는 방식을 택했다 — 기존 큐레이션 데이터가 깨지지 않는다.
- 브레이크타임/라스트오더는 요청 범위 밖(사용자가 "영업시작 영업종료"만 명시)이라
  요일별로 확장하지 않고 기존 단일 필드 그대로 유지했다.

## DB 스키마
`scripts/migrations/2026-09-19-spot-curations-operating-hours-by-day.sql`(적용
완료): `spot_curations.operating_hours_by_day jsonb` 추가 —
`[{day, open, close}]` 최대 7개, null이면 요일별 기능 미사용(기존 단일 값만 사용).

## 파싱 — `src/lib/admin/spot-curation-parsers.ts`에 추가
`extractRegularWeekdayHours(businessHourDays)`: 크롤러가 이미 요일별로 구조화해
둔 데이터(`NaverPlaceBusinessHourDay[]`)를 새로 파싱하지 않고 그대로 옮겨 담는다
(제5장 제4조). "매일 같으면 모든 요일 동일" 요구사항은 별도 로직 없이 자연히
충족된다(원본이 7일 전부 같으면 결과도 자연히 7일 전부 같음). `day`에 괄호+날짜가
붙은 임시 스케줄("목(9/24)")은 제외한다 — 그 요일의 진짜 정규 시간을 오늘
크롤링 데이터가 알려주지 않으면 억지로 추정해 채우지 않고 그 요일 칸을 비워
둔다(추측 금지, 제3장 제5조).

## 실측 중 발견 및 수정한 버그
`/api/admin/spot-curations`(관리자 CRUD, `select('*')`)에는 새 컬럼을 추가하면
자동으로 응답에 포함되지만, 유저가 실제로 보는 `/api/spot-curations`(공개 조회)는
컬럼 목록이 하드코딩돼 있어(`select('*')`가 아님) 새 컬럼을 빠뜨리면 **DB에는
저장되는데 화면에는 영원히 안 보이는 조용한 버그**가 된다 — 실제로 딸부자
닭갈비 스팟에 요일별 시간을 저장해보고 공개 API로 재조회해서 이 버그를 직접
재현·발견했다(단위 테스트만으로는 못 잡는 버그 — 컴포넌트 테스트는 fetch
응답을 목으로 만들어 실제 select 컬럼 목록을 검증하지 않기 때문). 컬럼 목록에
`operating_hours_by_day` 추가로 수정하고, 이 회귀를 다시 잡기 위한 라우트
테스트(`route.test.ts`, select 인자 검증)를 새로 만들었다.
