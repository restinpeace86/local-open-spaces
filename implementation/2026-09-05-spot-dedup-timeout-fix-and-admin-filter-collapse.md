# 관리자 화면 개선: 중복 스팟 검수 timeout 해결 + 데이터그리드 필터 UI 압축

## 구현 대상
사용자 지시(2026-09-05):
1. "관리자화면 중복 스팟 검수 및 매핑 탭에서 중복 의심 그룹 데이터 너무 많나봐 또
   timeout 걸리네.. 이것도 50여건씩 pagination 하던가..."
2. "open_spaces에 조건들이 너무 공간 많이 차지하네.. 출처(source_type)/출처
   (source)/카테고리/원천중분류는 숨기기 하던가 했으면 좋겠어. 등록일/표준 중분류
   (category_min)/검색어 입력창 정도로만 검색하고 있어. 이 3개 제외하고는 하나의
   영역에서 숨기기 펼치기 할 수 있도록 해. 조회하기 버튼도 등록일 라인쪽에 넣던가
   해서 불러오는 데이터 목록들 좀더 화면 포션 많이 차지할 수 있게 해줘."

## 구현 일시
2026-09-05

## 1. 중복 스팟 검수 timeout — 실측으로 확인한 진짜 원인
`EXPLAIN (ANALYZE, BUFFERS)`로 직접 재현한 결과, 문제는 클러스터링(ST_ClusterDBSCAN)
연산량이 아니라 **`open_spaces` 테이블 통계 정보가 낡아서 생긴 쿼리 플래너의
오판**이었다:
- `service_category_id is null` 조건은 실제로 142,113건 전부(중분류 매핑이 아직
  하나도 안 된 초기 상태)에 해당하는데, 낡은 통계는 이를 711건으로 추정했다(약
  200배 차이).
- 이 잘못된 추정 때문에 플래너가 "Bitmap Heap Scan"(추정만큼만 훑으면 된다는
  전제)을 선택했는데, 실제로는 힙 블록 30,489개(사실상 테이블 전체)를 훑어야 해서
  `... limit 500` 하나에도 13.5초가 걸렸다.
- `ANALYZE open_spaces;`로 통계를 갱신하자 플래너가 즉시 "Index Scan using
  open_spaces_pkey"(id 순으로 훑다가 필요한 만큼만 채우고 조기 종료)로 바뀌었고,
  같은 쿼리가 **457ms**로, 클러스터링을 포함한 전체 RPC(limit=3000)는 **110ms**로
  떨어졌다. 이 조치는 라이브 DB에 이미 직접 실행해 반영했다(마이그레이션 파일이
  아니라 운영 개입 — 통계 갱신은 스키마 변경이 아니라 재실행 가능한 유지보수
  작업이라 별도 기록만 남긴다).

## 2. 방어적 페이지네이션 (사용자 요청대로 병행 적용)
근본 원인은 해소했지만, 테이블이 계속 갱신되는 한 autovacuum이 통계 갱신을 놓쳐
같은 증상이 재발할 수 있고 사용자가 명시적으로 페이지네이션을 요청했으므로 함께
적용했다.

### DB — `find_spot_dedup_candidates` RPC 페이지네이션 지원
`scripts/migrations/2026-09-04-spot-dedup-perf-fix-and-pagination.sql`(신규):
- `p_after_id uuid` 커서 파라미터 추가, 기본 `p_limit`을 50으로 낮춤(요청 그대로
  "50여건씩").
- 반환 타입을 `TABLE(...)`에서 `jsonb`(`{ candidates, next_cursor, has_more }`)로
  변경 — 기존 TABLE 방식은 "이번 배치에 후보가 0건이었지만 스캔 자체는 끝까지
  진행했다"는 상태를 표현할 방법이 없어(0행 = 빈 결과와 구분 불가) 페이지네이션
  진행이 멈춰버리는 문제가 있었다. 반환 타입이 바뀌어 `CREATE OR REPLACE`로 덮어쓸
  수 없어 `DROP FUNCTION` 후 재생성했다.
- `next_cursor`는 이번 배치가 실제로 스캔한 마지막 id(uuid는 `max()` 집계가 없어
  `order by id desc limit 1`로 계산), `has_more`는 이번 배치가 `p_limit`을 꽉
  채웠는지(다음 페이지 존재 여부)를 나타낸다.

### 백엔드/프런트 — 커서 기반 누적 로딩
- `GET /api/admin/spot-dedup/groups`: 더 이상 그룹을 미리 합쳐 반환하지 않고,
  RPC의 원시 결과(`candidates`/`next_cursor`/`has_more`)를 그대로 전달한다.
- `spot-dedup-panel.tsx`: 후보를 페이지마다 누적(`candidates` 상태)하고, 누적된
  전체 후보를 대상으로 매번 `groupDedupCandidates`(기존 순수 함수, 그대로 재사용 —
  제5장 제4조)를 다시 계산한다 — 서로 다른 페이지에 걸쳐 있던 후보가 나중에
  하나로 합쳐질 수 있게 하기 위함. `has_more`가 true면 "다음 50건 더 스캔하기"
  버튼을 보여주고, 처리 완료된 그룹은 멤버 id로 누적 후보에서 제거한다.

## 3. 관리자 데이터그리드 필터 UI 압축
`data-grid-client.tsx`: 상시 노출 3종(검색어/표준 중분류/등록일)만 남기고 나머지
(출처(source_type)/출처(source)/카테고리/원천 중분류/이벤트 전용 필터인 활성
상태·타겟 연령)를 "▾ 상세 필터 더보기" 토글 하나로 묶었다(기본 접힘 —
`isFiltersExpanded` 상태). "🔍 조회하기" 버튼을 등록일 줄 오른쪽 끝으로 옮겨 별도
줄을 차지하지 않게 했다. 필터 로직(어떤 상태가 무엇을 트리거하는지)은 전혀
건드리지 않고 순수하게 마크업 배치만 바꿨다 — 조회 동작/디바운스/pending-applied
패턴은 기존 그대로.

## 검증
- `EXPLAIN ANALYZE`로 통계 갱신 전/후 실제 실행 계획과 시간을 직접 비교(13.5초 →
  457ms, 전체 RPC 23.5초 → 110ms).
- 새 페이지네이션 RPC를 라이브로 두 페이지 연속 호출해 커서가 정상적으로 이어지는지
  확인(`next_cursor`가 매번 갱신되고 `has_more`가 올바르게 표시됨).
- 단위/컴포넌트 테스트: `spot-dedup-panel.test.tsx`에 "다음 50건 더 스캔하기" 버튼
  및 페이지 간 후보 누적→재그룹핑 테스트 추가(신규 1개, 기존 5개 갱신).
- `npx tsc --noEmit` 통과, `npm run test`(105개 파일/1098개 테스트) 전체 통과,
  `npm run build` 프로덕션 빌드 통과.
- 필터 UI 압축은 로직 변경이 없어(마크업 배치만 변경) 기존 `data-grid-client.test.tsx`
  전체가 수정 없이 그대로 통과함을 확인했다.

## 특이 사항
- **`ANALYZE open_spaces` 자체는 마이그레이션 파일로 관리하지 않는다** — 스키마
  변경이 아니라 통계 갱신(재실행 가능한 운영 유지보수 작업)이라 SQL 마이그레이션
  히스토리에 넣지 않고 이 기록에만 남긴다. 이 테이블이 대량으로 갱신되는 배치
  (수집 파이프라인) 직후 주기적으로 `ANALYZE`를 실행하는 것을 고려할 만하지만,
  이번 지시 범위(신고된 증상 해결)를 넘어서는 운영 정책 결정이라 별도 제안으로
  남긴다.
- 페이지네이션 도입으로 그룹이 "여러 페이지에 걸쳐 나뉘어 있으면 한동안 보이지
  않을 수 있다"는 기존에 이미 문서화된 트레이드오프(2026-09-04 최초 구현 기록
  참고)가 페이지 크기가 3000→50으로 줄면서 더 자주 드러날 수 있다 — "더 보기"로
  계속 누적하면 결국 합쳐지므로 기능적으로는 문제 없지만, 정직하게 다시 명시한다.
