## 실측 장애와 대응 (2회 시행착오)

### 1차 시도: 동시 5개 병렬 — 거의 전부 실패
708건 중 22건만 성공, 686건이 HTTP 429(요청 한도 초과)로 실패. 동시 5개가
시작하자마자 한도를 소진했고, 짧은 재시도 백오프(3~6초)로는 회복되지 않았다.

### 2차 시도: 순차 실행(동시 1개) + 요청 간 4초 간격 + 429 시 65초 대기
440건 정도까지는 오류 0건으로 정상 처리됐으나, 이후 모든 요청이 65초×4회 대기
후에도 계속 429로 실패 — **분당 한도가 아니라 일일 한도**임을 시사했다. 직접
Gemini API를 호출해 에러 본문을 확인한 결과 정확한 원인을 확인:
```
quotaId: "GenerateRequestsPerDayPerProjectPerModel-FreeTier"
quotaValue: "500"
```
**무료 티어(Free Tier)의 모델당 일일 500회 요청 한도**였다 — 708건을 하루 안에
전부 처리하는 건 이 한도로는 불가능하다(이미 관리자 화면 개발 중 호출한 테스트
요청들도 이 한도를 함께 소진했다). 진행 중이던 배치 실행은 이 사실을 확인한 뒤
중단했다(계속 재시도해도 오늘 안에는 회복되지 않으므로 무의미한 대기였음).

### 재개 가능하도록 스크립트 보강
- 처리한 각 행의 결과를 `scripts/tmp/classify-events-facility-type-progress.json`
  (git 추적 제외)에 기록하고, 다음 실행 시 이미 처리된 id는 자동으로 건너뛴다.
- 연속으로 "65초×4회 재시도"가 모두 실패하면(일일 한도로 추정) 즉시 중단하고
  안내 문구를 출력한다 — 회복되지 않는 상태로 몇 시간을 허비하지 않는다.
- `--dry-run`(DB 저장 없이 결과만 확인), `--limit=N`(소규모 검증), `--force`
  (진행 상황 무시하고 전부 재처리) 옵션 추가.

## 후속 (2026-09-18)

### 할당량 초기화 시점 규명
사용자 지적("한국시간으로 9/17에 시켰는데 지금 9/18인데?"): 재확인 결과 Gemini
무료 티어 일일 한도는 **한국 시간이 아니라 UTC(사실상 태평양 표준시 자정) 기준**
으로 초기화된다 — 실측 시점에 KST는 이미 9/18로 넘어갔지만 UTC는 아직 9/17
저녁이었다. 초기화 예상 시점(UTC 9/18 07:00 = KST 9/18 오후 4시경)에 자동으로
할당량 회복 여부를 확인하고 재개하도록 1회성 예약(CronCreate)을 걸어뒀다.

### 진행 상황 역산 복구
체크포인트 파일(`scripts/tmp/classify-events-facility-type-progress.json`)은
2차 시도가 실패한 뒤에야 추가한 기능이라, 그 이전 두 번의 실행에서 실제로
성공한 행들의 기록이 없었다 — 방치하면 재개 시 처음부터 다시 708건을 태워
똑같은 할당량 벽에 부딪힌다. 두 실행의 콘솔 로그(실패한 id 목록)와 현재 DB
상태를 대조해 "실제로 이미 새 값이 저장된 469건"을 역산 복원했다(대상 행 자체가
708→686건으로 약간 줄어든 것까지 반영 — 시한부 이벤트 일부가 그 사이
is_active=false로 바뀐 것으로 추정). 재개 시 남은 약 217건만 처리하면 된다
(무료 티어 일일 500회 한도 안에 충분히 들어간다).

### 일일 신규분 배치 신설
사용자 지시: "이것들 관련하여서는 매일 새로 들어오는거에 대하여 돌수 있도록
배치로 만들어줄수 있나? 일단 오늘 신규 반영된 건들에 한해서."
- 공용 로직을 `scripts/ingest/lib/facility-classification.mjs`(프롬프트/파싱/
  Gemini 호출/재시도)와 `scripts/ingest/lib/kst-date-range.mjs`(KST "오늘"
  계산, `src/lib/admin/kst-date-range.ts`를 스크립트용으로 이식)로 추출해
  일회성 백필 스크립트와 신규 일일 스크립트가 함께 쓰도록 리팩터링했다(제5장
  제4조 — 세 번째 복제 방지).
- 신규 `scripts/ingest/classify-new-events-facility-type.mjs`: 오늘(KST)
  `created_at` 이후 생성된 행 중 백필과 동일한 두 조건(is_active=true AND
  target_audience IN (...))을 만족하는 것만 대상으로 삼는다.
- 신규 GitHub Actions 워크플로 `.github/workflows/classify-new-events-facility-
  type.yml` — 매일 KST 04:05(UTC 19:05, 전일)에 실행, 기존 일일 수집 배치
  (KST 02:47)가 target_audience까지 채운 뒤 안전하게 실행되도록 시간을 띄웠다.
  기존 배치들(daily 02:47/monthly 03:52/mom-pick-grade 04:23/weather 매 3시간
  :47분)과 겹치지 않는 자리를 골랐다.
- **알아둘 점**: 이 일일 배치는 기존 일일 수집 배치의 카테고리 분류
  (`ai-tagging.mjs`)와 같은 `GEMINI_API_KEY`·같은 무료 티어 일일 한도를
  공유한다 — 신규 유입 건수가 적을 것으로 예상돼 지금은 문제없지만, 특정
  하루에 신규 유입이 몰리면(예: 새 데이터 소스 대량 추가) 그날의 신규분
  중 일부가 한도 초과로 다음 실행 전까지 미분류 상태(`복합` 기본값)로
  남을 수 있다 — 이 배치는 "오늘 생성된 것"만 조회하므로 다음날 배치가
  전날 놓친 건을 대신 잡아주지 않는다(범위 밖 — 필요해지면 재조회 창을
  넓히는 방식으로 후속 개선 가능).
