## 실측 장애와 대응 (2회 시행착오)

### 1차 시도: 동시 5개 병렬 — 거의 전부 실패
708건 중 22건만 성공, 686건이 HTTP 429(요청 한도 초과)로 실패. 동시 5개가
시작하자마자 한도를 소진했고, 짧은 재시도 백오프(3~6초)로는 회복되지 않았다.

### 2차 시도: 순차 실행(동시 1개) + 요청 간 4초 간격 + 429 시 65초 대기
440건 정도까지는 오류 0건으로 정상 처리됐으나, 이후 모든 요청이 65초×4회 대기
후에도 계속 429로 실패 — **분당 한도가 아니라 일일 한도**임을 시사했다. 직접
Gemini API를 호출해 에러 본문을 확인한 결과 정확한 원인을 확인:
```
quotaId: "GenerateRequestsPerDayPerProjectPerModel-FreeTier"
quotaValue: "500"
```
**무료 티어(Free Tier)의 모델당 일일 500회 요청 한도**였다 — 708건을 하루 안에
전부 처리하는 건 이 한도로는 불가능하다(이미 관리자 화면 개발 중 호출한 테스트
요청들도 이 한도를 함께 소진했다). 진행 중이던 배치 실행은 이 사실을 확인한 뒤
중단했다(계속 재시도해도 오늘 안에는 회복되지 않으므로 무의미한 대기였음).

### 재개 가능하도록 스크립트 보강
- 처리한 각 행의 결과를 `scripts/tmp/classify-events-facility-type-progress.json`
  (git 추적 제외)에 기록하고, 다음 실행 시 이미 처리된 id는 자동으로 건너뛴다.
- 연속으로 "65초×4회 재시도"가 모두 실패하면(일일 한도로 추정) 즉시 중단하고
  안내 문구를 출력한다 — 회복되지 않는 상태로 몇 시간을 허비하지 않는다.
- `--dry-run`(DB 저장 없이 결과만 확인), `--limit=N`(소규모 검증), `--force`
  (진행 상황 무시하고 전부 재처리) 옵션 추가.
