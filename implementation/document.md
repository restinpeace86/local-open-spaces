이 장표를 설명할 때의 핵심 포인트 (스피치 팁)
문제 제기 (Pain Point): "시중에 수많은 육아/공간 서비스들이 공공데이터를 그대로 가져다 쓰지만, 데이터가 분산되어 있고 중복과 오탈자가 심해 실제 유저들이 큰 불편을 겪습니다."

기술적 해결책 (Solution): *"당사는 단순 래퍼 서비스를 넘어, [지오코딩 ➡️ 공간 클러스터링 ➡️ Human-in-the-Loop 검수]*로 이어지는 독자적인 데이터 정제 파이프라인을 구축했습니다."

사업적 가치 (Moat): *"이 과정을 통해 타사는 절대 흉내 낼 수 없는 고품질의 자체 육아 공간 데이터 댐(Data Dam)*을 구축하며, 시간이 흐를수록 서비스의 신뢰도와 진입장벽이 압도적으로 높아집니다."



[ 1단계: 데이터 수집 (Ingestion) ]
  ├── 행안부 어린이놀이시설 (설치장소 유형 필드 보유)
  └── 서울시 공공예약 등 (대분류/중분류 체계 보유)
         │
         ▼
[ 2단계: 소스별 네이티브 분류 매핑 (Standardization) ]
  ├── 표준 대분류 (standard_major_category)  <- 원천 대분류 매핑 (예: 서울시 MAXCLASSNM)
  ├── 표준 중분류 (standard_middle_category) <- 원천 중분류 매핑 (예: 서울시 MINCLASSNM)
  └── 속성 태그 (Attribute Tags)           <- 민간/공공 등 소스별 상이한 부가 정보
         │
         ▼
[ 3단계: 백엔드 안전 적재 (Upsert Guard & Preservation) ]
  ├── [신규 데이터] 표준 대/중분류 및 메타데이터 적재
  └── [기존 데이터] 이미 관리자가 입력한 **'노출 중분류(exposure_category)' 및 '뱃지'는 절대 보호(Override 금지)**
         │
         ▼
[ 4단계: 관리자 워크벤치 검수 (Admin Curation) ]
  ├── 관리자 화면에서 소스별 [표준 대/중분류] 힌트 확인
  └── 최종 유저 지도에 띄울 **[노출 중분류]**를 수동 선택 및 뱃지 태깅 후 저장
         │
         ▼
[ 5단계: 최종 유저 서비스 노출 (User Map Exposure) ]
  └── 유저 앱/웹 지도의 카테고리 탭에서 **[노출 중분류]** 기준으로 필터링 및 노출


💡 중분류 로직 및 최종 노출 중분류 결정 방식
1. 표준 대/중분류 (Source-Native Middle Category)의 역할
정의: 각 공공데이터 소스가 가진 고유의 분류 체계(예: 서울시의 MAXCLASSNM/MINCLASSNM)를 그대로 수용하여 담아두는 시스템 내부 참고용 표준 분류입니다.

로직: 소스마다 데이터 구조가 달라도 억지로 끼워 맞추지 않고, 소스별 파서(Parser)를 통해 각자의 대/중분류 컬럼에 안전하게 안착시킵니다. 관리자가 대시보드 리스트를 볼 때 "아, 이 데이터는 원천에서 이런 분류였구나" 하고 파악하는 힌트 역할을 합니다.

2. 최종 '노출 중분류' (exposure_category)의 역할과 결정 로직
정의: 유저가 실제 앱 화면의 지도나 카테고리 필터에서 보게 될 최종 서비스용 중분류입니다.

결정 방식 (인간 검수 중심):

원천 데이터나 시스템이 자동으로 유저용 노출 중분류를 100% 확정하지 않습니다 (공공데이터의 분류가 부정확하기 때문).

관리자가 워크벤치에서 원천 소스의 표준 중분류와 블로그 후기 등을 종합적으로 검토한 뒤, 사람의 손으로 직접 올바른 노출 중분류를 선택하고 저장합니다.

업서트 방어 로직 (Safeguard):

한 번 관리자가 검수하여 exposure_category에 값이 채워지면, 이후 공공데이터 수집 배치가 주기적으로 돌아서 데이터를 갱신(Upsert)하더라도 기존 노출 중분류 값은 절대 덮어씌워지거나 초기화되지 않고 철저하게 보존됩니다.



🚀 [기술 차별성 제안서] 지능형 자가 치유(Self-Healing) 및 하이브리드 휴먼인더룹(HITL) 데이터 정제 파이프라인
1. 추진 배경 및 한계 직면 (The Problem)
공공데이터와 외부 API의 구조적 노이즈: 공공데이터는 위치/주소 정보가 누락되거나 부정확하며, 네이버 블로그 등 외부 검색 API는 검색 정렬(sim/date)의 한계 및 프랜차이즈 지점명 동음이의어(예: 쿠우쿠우 특정 지점 검색 시 타 지역 글 혼입)로 인해 심각한 데이터 오염(False Positive)을 유발함.

기존 방식의 한계: 이를 해결하기 위해 관리자가 전체 데이터를 전수 조사(검수의 지옥)하는 것은 운영 리소스를 극단적으로 소모하며 스타트업의 스케일업을 가로막는 병목 구간임.

2. 우리의 핵심 기술 및 해결 방안 (Our Solution)
① 스마트 자가 치유(Self-Healing) 동적 재검색 엔진
개념: 시스템이 수집된 블로그 본문의 텍스트와 대상 스팟의 주소/지역 키워드(예: '명월', '분당')를 실시간 교차 검증하여 타 지역 지점명 혼입(미스매치)을 자동 감지함.

동작 프로세스:

1차 수집된 블로그 중 미스매치된 개수(N개)를 실시간 카운트

DB에 내장된 주소 체계(시/군/구/읍/면)를 활용하여 상위 지역명과 결합된 확장형 스마트 쿼리([상호명] + [광역/기초지자체명])로 자동 변환

부족한 갯수(N개)만큼 API를 정밀 재호출(Auto-Refetch)하여 오염된 데이터를 깨끗한 데이터로 자동 교체

② 유의어·공백 정규화 및 맥락 가시화 하이라이팅
개념: "아기의자", "유아용 의자", "아기 의자" 등 파편화된 표현과 띄어쓰기 오류를 무력화하는 텍스트 정규화 전처리 엔진 탑재.

효과: 백엔드에서 공백을 제거(Whitespace-Insensitive)하고 확장형 유의어 사전과 매핑하여, 관리자 화면에서 핵심 뱃지 키워드뿐만 아니라 '지역/지점명' 맥락까지 노란색 하이라이트로 시각화하여 관리자의 속독(Speed-reading)과 직관적 판단을 지원함.

③ 예외 중심 자율 검수 (Anomaly-Driven Human-in-the-Loop)
개념: 사람이 모든 데이터를 검수하는 것이 아니라, 시스템이 정상 판정한 대량의 데이터는 자동 승인(Auto-Commit)하고, 오류나 의심 신호가 감지된 극소수의 '예외 케이스(Anomaly)'만 관리자 큐로 이관하는 지능형 라우팅 체계.

효과: 관리자의 피로도를 제로(0)에 가깝게 낮추면서도, 데이터의 최종 신뢰도는 100%를 보장하는 고효율·고정밀 큐레이션 워크벤치 완성.

3. 기대 효과 (Business Impact)
운영 효율성 극대화: 단순 반복 수동 검수 대비 데이터 정제 및 자산화 소요 시간을 80% 이상 단축.

데이터 품질 차별화: 공공데이터의 고질적인 오탐율과 위치 불일치 문제를 시스템 자동화와 정밀 휴먼 검수의 결합으로 극복하여, 서비스 지도 품질의 압도적인 우위 확보.
