# [예약 신청 폼 UI/UX 고도화 (ReservationRequestModal)]

## 요구사항
1. 방문 날짜 과거 선택 방지, 인원수 0/빈 값 방어(명확한 안내 문구), 연락처 포맷 힌트.
2. 제출 중 버튼 비활성화 + "접수 중..." 표시, 중복 제출 완벽 차단.
3. 상단 안내 문구 보강, 접수 성공 시 곧바로 닫지 않고 완료 메시지를 보여준 뒤 부드럽게 닫힘.
4. 검증 후 커밋/푸시.

## 구현 (`src/components/map/reservation-request-modal.tsx`)

### 1. 필드별 검증 강화
- 방문 날짜 `min` 속성(오늘)은 직전 작업에서 이미 적용돼 있어 유지.
- **인원수**: 기존 구현은 `onChange`에서 `Math.max(1, Number(value) || 1)`로 즉시
  자동 보정해, 사용자가 0이나 빈 값을 입력해도 그 상태를 화면에서 볼 수조차 없었다 —
  "0 이하/빈 값 입력 시 안내 문구"를 실제로 보여줄 방법이 없는 구조였다. 인원수를
  문자열 state로 바꿔 자유롭게 입력하게 하고, 제출 시점에 한 번에 검증해 "신청 인원은
  1명 이상의 숫자로 입력해 주세요."를 보여주도록 고쳤다.
- **연락처**: 기존 `placeholder="010-0000-0000"`에 더해, 입력창 아래에 상시 노출되는
  안내 텍스트("예: 010-1234-5678 형식으로 입력해 주세요.")를 추가했다. 이 텍스트를
  `<label>` 안이 아니라 밖(형제 요소)에 둔 이유: `<label>` 내부에 텍스트를 추가하면
  라벨-없는-`htmlFor` 래핑 라벨 패턴에서 접근성 트리상 라벨의 "이름"이 힌트 문구까지
  합쳐진 문자열로 계산돼(testing-library 등에서 실측 확인) "연락처"만으로 라벨을 찾을 수
  없게 되는 부작용이 있었다.
- 검증 메시지를 필드별로 구체화(날짜/인원수/연락처 각각 다른 문구)해 "모두 입력해
  주세요" 같은 뭉뚱그린 메시지보다 어디를 고쳐야 하는지 바로 알 수 있게 했다.

### 2. 로딩 상태 및 중복 제출 방지
기존에도 `isSubmitting`으로 버튼 비활성화 + "접수 중..." 표시는 이미 있었다. 요구사항의
"완벽히 차단"에 맞춰 `handleSubmit` 맨 앞에 `if (isSubmitting) return;` 이중 방어선을
추가했다 — 버튼의 `disabled` 속성과 별개로, 네트워크 응답을 기다리는 동안 폼이 다시
제출되는 경로(예: Enter 키 연타)까지 막는다.

### 3. 시각적 피드백 강화
- 상단에 안내 문구 추가: "전화나 방문 없이 간편하게 무료 예약 신청을 남겨보세요. 담당자
  확인 후 연락드립니다." (요구사항 예시 문구 그대로).
- **접수 성공 흐름 교체**: 기존(직전 작업)은 `window.alert(...)` 호출 직후 즉시
  `onClose()`를 불러 화면이 뚝 끊기는 느낌이었다. 이제 `submitStatus` 상태를
  `'idle' | 'submitting' | 'success'`로 관리해, 성공 시 폼을 완료 화면(✅ 아이콘 + "신청이
  접수되었습니다!" + 안내 문구)으로 교체하고, `useEffect`로 1.8초 후 자동으로
  `onClose()`를 호출한다. `window.alert()`는 더 이상 쓰지 않는다(요구사항: "곧바로
  닫히기보다 깔끔한 완료 메시지나 부드러운 피드백을 주고 닫히도록").

## 검증

### 코드 검증
- `npx tsc --noEmit` 통과.
- `npm run test`(64파일 662건 — `reservation-request-modal.test.tsx` 전면 재작성, 14건)
  통과. `npm run test`를 2회 연속 실행해 안정성(비-플레이키)도 확인했다.
- `npm run build` 통과.

### 테스트 안정성 이슈 발견 및 수정
접수 성공 후 자동 닫힘을 검증하는 테스트에서 처음에는 `vi.useFakeTimers()`를 썼는데,
단일 파일 실행(`npx vitest run <파일>`)에서는 통과하지만 **전체 스위트 실행
(`npm run test`)에서만 간헐적으로 실패**하는 것을 실측으로 확인했다 — 가짜 타이머가
testing-library의 `findByText`/`waitFor` 내부 폴링(설정에 따라 실제 타이머에 의존)과
상호작용이 불안정한 것으로 보인다. 가짜 타이머 대신 실제 시간을 그대로 흘려보내는
방식(`waitFor(..., { timeout: 3000 })`)으로 바꿔 재현 없이 안정적으로 통과함을 확인했다
(지연 시간이 1.8초로 짧아 테스트 스위트 전체 실행 시간에 미치는 영향은 미미하다).

## 특이 사항
- 성공 화면의 자동 닫힘 지연(1.8초)은 별도로 설정 가능하게 만들지 않았다(MVP, 제3장
  제3조) — 향후 필요하면 prop으로 노출할 수 있는 구조지만 이번 지시서 범위 밖이라 상수로
  고정했다.
