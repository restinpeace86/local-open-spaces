# 글쓰기 전체화면 제목 "첫 글 쓰기" 오표기 수정

## 구현 대상
맘스픽 전체 화면 글쓰기(`isFullScreenComposerOpen`)의 헤더 제목이 항상
"✍️ 첫 글 쓰기"로 고정되어 있던 문제 수정.

## 구현 일시
2026-09-14

## 배경
사용자 지시: "이거 제목이 왜 첫글쓰기야 ? 난 여러번째 글쓰기 중인데.."

## 원인
`mom-pick-view.tsx`의 이 전체화면은 두 경로로 열린다.
1. `not_sprout_yet`(새싹맘 미달성) 유저가 안내 팝업의 "첫 글 쓰러 가기"를
   누른 경우
2. `allowed`(이미 새싹맘 이상) 유저가 평소 "✍️ 글쓰기" 플로팅 버튼을 누른
   경우(`handleWriteClick`의 else 분기)

두 경로 모두 동일한 화면을 열지만 헤더 제목은 "1"번 경로만 염두에 두고
"✍️ 첫 글 쓰기"로 고정되어 있어, 이미 여러 번 글을 쓴 유저에게도 매번
"첫 글 쓰기"라고 표시되는 오류였다.

## 변경 사항
- `src/components/community/mom-pick-view.tsx`: 헤더 제목을 "✍️ 첫 글 쓰기"
  → "✍️ 글쓰기"로 변경(플로팅 버튼의 aria-label "글쓰기"와도 톤을 맞춤).
- `src/components/community/mom-pick-view.test.tsx`: 4곳의 기대값을
  "✍️ 글쓰기"로 갱신.

## 검증
- `npx tsc --noEmit`, `npm run test`(전체 1679개), `npm run build` 모두 통과.

## 특이 사항 — "사진 고르다 닫으면 처음으로 돌아감" 이슈 후속 (2026-09-14, 안드로이드 크롬 확인)
사용자가 기기를 "안드로이드 크롬"으로 확인해줘서 가설을 좁혔다. 안드로이드
크롬은 메모리 압박이 있으면 백그라운드로 간 탭을 통째로 버리고(discard),
돌아왔을 때 페이지를 처음부터 다시 불러온다(모든 React 상태 소실 — 이번
증상과 정확히 일치). 이 자체는 OS/브라우저 리소스 관리 영역이라 JS에서
완전히 막을 수는 없지만, **이번 세션에서 새로 추가한 @tensorflow/tfjs +
blazeface가 메모리 압박을 스스로 키우고 있었다는 실제 원인 하나를 찾아
고쳤다**:
- `@tensorflow-models/blazeface`의 `BlazeFaceModel`은 내부 GraphModel을
  private 필드로 감싸고 있어 공개 `dispose()` 메서드가 없다 — 한 번
  로드하면 그 GPU 메모리(WebGL 백엔드)를 우리 쪽에서 직접 해제할 방법이
  없는 라이브러리 자체의 한계다.
- 기존 코드는 사진을 편집할 때마다(큐에 여러 장이 있으면 장마다)
  `blazeface.load()`를 새로 호출하고 있었다 — 즉 사진을 여러 장 고를수록
  해제 불가능한 모델 인스턴스가 계속 쌓여 메모리 압박을 스스로 키우는
  구조였다. 사용자가 "사진첩을 찾아보고" 있었다는 정황(여러 장 후보를 보며
  왔다 갔다 했을 가능성)과 맞아떨어진다.
- 수정: 모듈 레벨에 모델 로딩 Promise를 캐시해 세션(페이지를 벗어나기
  전까지)당 딱 한 번만 로드하고, 이후 편집하는 모든 사진이 같은 모델
  인스턴스를 재사용하도록 했다(`loadBlazefaceModel()`).
- 검증: Playwright로 사진 2장을 연달아 편집하는 시나리오를 재현해, 모델
  관련 네트워크 요청(model.json + 가중치 파일, 리다이렉트 체인 포함 6건)이
  **첫 번째 사진에서만 발생하고 두 번째 사진에서는 추가 요청이 없음**을
  실측 확인했다.
- 한계: 이 수정은 "탭이 아예 버려지는" 근본 원인의 확률을 낮추는
  완화책이지, 안드로이드 크롬의 메모리 관리 자체를 없앨 수는 없다. 여전히
  기기 메모리가 매우 부족하거나 다른 원인(예: 위에서 언급한 전체화면
  자체의 뒤로가기 미보호)으로 재발할 가능성은 남아 있다.
