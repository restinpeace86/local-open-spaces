# 맘스픽 글쓰기 전반 응답속도 저하 원인 진단 및 조치

## 구현 대상
사용자 리포트 "지금 글쓰기할때 반응이 너무 느린데? 처음에 장소찾는것도
엄청느리고 사진추가때 사진 선택하고 완료버튼 누를때도 반응속도가 너무 늦어
안된건가 싶어서 2번이나 누르고 그러니 2번이나 선택되네.. 전반적으로
앱자체가 너무 느린거 같은데 왜그런지 원인 파악하고 조치해" — 세 가지 증상
각각의 실제 원인을 실측으로 찾아 조치.

## 구현 일시
2026-09-14

## 증상 1: 장소 검색이 느림 — 원인 및 조치
### 원인 (실측)
`searchSpacesNationwide`(스팟 검색)/`searchEvents`(이벤트 검색) 모두 검색어를
공백 기준 토큰으로 나눠 각 토큰마다 `(name/address ILIKE '%token%')` 조건을
AND로 체이닝한다. `open_spaces.name`/`address`에는 이미 pg_trgm GIN
트라이그램 인덱스(`idx_open_spaces_name_trgm`/`_address_trgm`,
2026-08-30-add-trigram-search-indexes.sql)가 존재하지만, **pg_trgm은 패턴에서
완전한 3글자 조합(trigram)을 뽑아낼 수 있어야 인덱스를 효율적으로 탈 수
있다** — 2글자 이하 토큰은 애초에 3글자 조합을 만들 수 없어 GIN 인덱스가
사실상 "테이블 전체가 후보"라고 답해버린다.

프런트엔드(`spot-picker.tsx`)는 검색어 **전체 문자열 길이**가 3자 이상인지만
검사하고, 공백으로 나뉜 **개별 토큰**의 길이는 검사하지 않는다. 그래서
"행복 어린이집"처럼 지극히 자연스러운 여러 단어 검색에서 "행복"(2자)이
그대로 필터 조건에 섞여 들어가, EXPLAIN ANALYZE로 실측한 결과 **8초 이상**
걸리는 쿼리가 만들어지고 있었다(실제 141,980행 중 143,214행이 "후보"로
반환되는 것을 직접 확인 — 사실상 인덱스가 아무것도 걸러내지 못함). 짧은
토큰용 인덱스 확장인 `pg_bigm`은 이 Supabase 프로젝트에 설치되어 있지 않음을
`pg_available_extensions`로 확인했다(설치 불가, 이번 조치 범위 밖).

### 조치
`src/lib/search/keyword-search.ts`에 `selectTrigramFriendlyTokens()` 추가 —
토큰 중 3자 이상인 것만 남기고(트라이그램이 만들어지는 최소 길이), 모든
토큰이 3자 미만인 예외적인 경우에는 결과가 아예 없는 것보다 낫도록 원래
토큰을 그대로 반환한다. `searchSpacesNationwide`/`searchEvents` 양쪽에
적용했다.

### 검증
운영 DB에 직접 `EXPLAIN (ANALYZE, BUFFERS)`를 실행해 실측:
- 기존: "행복 어린이집" 패턴(2자+4자 토큰 AND) → **8,009ms**
- 조치 후: "어린이집"만 필터 조건으로 남음 → **99.9ms** (80배 개선)
- 두 토큰 모두 3자 이상인 경우("강남구 어린이집")도 정상적으로 각각
  트라이그램 인덱스를 타며 818ms로 개선(기존 다른 패턴 대비 크게 개선,
  이 정도 조합은 절대적으로 드물고 여전히 1초 이내).
- 실제 `/api/spots/search` 엔드포인트(개발 서버, 운영 DB 대상)로 "용인
  어린이상상" 재현: 기존 버그의 실제 사례였던 "용인어린이상상의숲"이 여전히
  정상적으로 검색됨을 확인(200~300ms).
- `keyword-search.test.ts`에 `selectTrigramFriendlyTokens` 단위 테스트 4개,
  `get-home-feed.test.ts`의 기존 다중 토큰 테스트 2개를 새 동작에 맞게
  갱신 + 신규 테스트 2개(3자 이상 토큰만 있을 때 기존처럼 토큰별 `.or()`
  체이닝이 유지되는지) 추가.

## 증상 2·3: 사진 확인(완료) 버튼 응답 느림 + 중복 클릭으로 2번 등록
### 원인 (코드 확인)
`face-sticker-editor.tsx`의 `handleConfirm()`이 **원본 해상도 그대로**(휴대폰
사진은 보통 3000~4000px, 수 MB) 캔버스에 다시 그려 인코딩한 뒤 업로드하고
있었다 — 실제로 사진이 쓰이는 곳은 96px 썸네일(`post-detail-modal.tsx`)이나
화면 폭에 맞춘 모달(`post-photo-modal.tsx`)뿐이라 원본 해상도가 전혀
필요하지 않았다. 게다가 "완료"/"편집 없이 올리기"/"이 사진 취소" 버튼
어디에도 처리 중 비활성화가 없어, 인코딩+업로드가 끝나기 전에 사용자가
"안 눌렸나?" 하고 두 번째 클릭을 하면 `handleConfirm()`이 통째로 다시
실행되어 **같은 사진이 두 번 업로드**되고 있었다.

### 조치
- 업로드 전 이미지를 긴 변 기준 1600px로 다운스케일(`OUTPUT_MAX_LONG_SIDE`,
  JPEG 품질 0.85)한 뒤 인코딩하도록 변경 — 인코딩 시간과 업로드 용량을 크게
  줄인다.
- `isProcessing` 상태를 추가해 완료/건너뛰기/취소 버튼과 배경 클릭을
  클릭 즉시 모두 잠그고, "완료" 버튼에는 "처리 중..." 표시를 추가해 중복
  클릭 자체를 원천 차단.
- (2026-09-15 후속, 사용자 지시) "1600px가 업계 표준인거야? 더 낮추면
  품질 문제 생기나?" 질의에 인스타그램(1080px)/카카오톡(780~1200px)/
  네이버(1000~1600px)/페이스북(2048px 고화질 모드) 등 실제 사례를 근거로
  "고정된 업계 표준은 없고 대략 1000~2000px 범위"라고 답했고, 이 앱의 실제
  표시 환경(96px 썸네일 + 뷰포트 기준 모달, 레티나 배율 포함 실사용에
  필요한 해상도는 대략 900~1300px)을 근거로 1400px을 제안 → 사용자 승인.
  `OUTPUT_MAX_LONG_SIDE`를 1600 → 1400으로 조정.

### 검증
`npx tsc --noEmit`, `npm run test`(전체 1685개, 신규/갱신 테스트 포함),
`npm run build` 모두 통과.

## 특이 사항
- `searchEvents`가 참조하는 `idx_events_description_trgm` 인덱스는 Step 149
  (2026-09-13)에서 "사용 비율이 낮다"는 판단으로 삭제된 바 있다 — 이번 조치
  범위와는 무관하지만, description 필드로만 매칭되는 이벤트 검색은 title/
  venue_name 대비 인덱스 지원이 약하다는 점은 참고로 남겨둔다(별도 이슈로
  제기되면 그때 재검토).
- 이번 조치로 여전히 남는 절대적 예외 케이스: 검색어의 **모든** 토큰이
  3자 미만인 경우(예: "행 집") — 이런 경우는 원래 토큰을 그대로 써서
  느릴 수 있다(실사용에서 극히 드문 패턴으로 판단해 이번 범위에서는 그대로
  둠).
