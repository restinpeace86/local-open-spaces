# 문화센터 검색 성능 최적화 + 카드 정보 밀도 개선

## 구현 대상
사용자 피드백 5건을 실측으로 확인하고 수정:
1. 썸네일이 안 나온다 — 우리 기준에 맞게 픽셀을 맞춘 게 맞는지.
2. 카드에 "롯데몰수지점 8.5km"가 이미 보이는데 브랜드 뱃지가 중복 아닌지.
3. 성능이 너무 느리다 — Branch-First 최적화가 제대로 안 된 것 같다.
4. 카드 정보가 부족하고 여백이 많다 — 가격에 "몇회"가 안 보인다.
5. 수업일자/요일/시간 말고 접수일자(이마트엔 있는 데이터)가 안 보인다.

## 조사 결과 및 변경 사항

### 1. 썸네일
실측 확인: CDN URL 자체는 정상(둘 다 200, 실제 JPEG). 근본 원인은 데이터
쪽이다 — 이마트 전체 6,563건 중 `main_image_key`가 있는 건 544건(8.3%)뿐
이고, 나머지는 원본 API가 애초에 이미지를 안 준다(반복되는 정규 강좌엔
사진이 없고 일부 이벤트성 강좌에만 있음 — 추측 금지, 실측으로 확인했을
뿐 우리가 만들어낼 수 있는 데이터가 아니다). 다만 실제 원본 이미지가
정사각형이 아니라 가로형(271×173, 616×416 등 약 3:2)이라 기존 96×96
정사각형 박스에선 과도하게 크롭됐던 부분은 고쳤다 — `h-24 w-28`(112×96)
로 살짝 더 넓혀 크롭을 줄였다(`culture-club-tab-view.tsx`의 `ClassImage`).

### 2. 브랜드 뱃지 제거
카드 상단의 이마트/롯데마트 뱃지를 제거했다 — 하단 위치 줄
(📍 지점명 · 거리)이 이미 브랜드/위치 정보를 전달해 중복이었다. 할인/
마감임박/신설처럼 실제로 다른 정보를 주는 뱃지만 남겼고, 그 뱃지들이
하나도 없을 때는 빈 줄을 만들지 않는다(여백 완화에도 기여).

### 3. 성능 최적화 — 실측으로 원인 특정
실측: Supabase 원격 호출은 행 수와 무관하게 왕복마다 ~400~600ms 고정
지연이 있다(124건짜리 가벼운 RPC도 ~600ms, count 쿼리 ~470ms, 1,000건
select도 ~390ms — 전부 비슷한 고정 지연대).

- **지점 좌표 캐싱**: `get_culture_club_store_coordinates()` RPC를 검색
  API뿐 아니라 지점 선택 API(stores/lottemart-stores)도 매 요청마다
  호출하고 있었다. 지점 좌표는 거의 안 바뀌는 정적 데이터라 5분 TTL로
  메모리에 캐싱하는 `src/lib/home/culture-club-store-coordinates-cache.ts`
  를 추가하고, 검색 API와 지점 선택 API 둘 다 재사용한다.
- **count 쿼리와 첫 페이지 조회를 병렬화**: 기존엔 count를 기다린 뒤에야
  range 조회를 시작해(순차 3단계: RPC → count → range) 지연이 더해졌다.
  count는 "첫 1,000건을 가져왔다"는 사실과 독립적인 정보이므로, count
  쿼리와 첫 페이지(최대 1,000건) 조회를 `Promise.all`로 동시에 보낸다.
  첫 페이지가 꽉 찼을 때만(=더 있을 수 있을 때만) 추가 페이지를 더
  가져온다.
- 실측(동일 조건 반복 호출, 캐시 웜업 후): 검색 API 1.3s→0.3~0.5s대,
  지점 선택 API 왕복마다 ~600ms였던 게 0.09~0.18s로 대폭 단축됐다.

### 4~5. 카드 정보 밀도 개선
- `total_sessions`(회차)를 가격 바로 옆에 "N회"로 추가(기존엔 상세 시트
  에서만 보였다).
- `register_start_at`(접수 시작일시, 이마트만 값이 있음)을 "📅 접수
  {날짜}" 줄로 추가 — 없으면(롯데마트 등) 줄 자체를 생략한다(추측 금지).
- 제목+찜 버튼을 한 줄로 합치고, 특수 뱃지가 없을 땐 그 줄 자체를
  생략해 빈 여백을 줄였다.
