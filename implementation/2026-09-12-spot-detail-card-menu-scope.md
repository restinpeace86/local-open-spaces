## 검토 결과 — 2패턴 구조는 이미 구현돼 있었음
`detail-modal.tsx`는 최상단에서 `item.item_type === 'EVENT'`(`isEvent`)로 완전히
분리된 두 JSX 트리를 렌더링하고 있었다:

- **스팟 자체 상세카드**(`item_type='SPACE'`): 주소/운영시간/가격/메뉴/홈페이지 —
  운영시간·가격·메뉴는 `spot_curations`(관리자 큐레이션) 우선, 없으면 공공데이터
  (`operating_hours`/`is_free`) 폴백.
- **연결된 이벤트 상세카드**(`item_type='EVENT'`): 행사 기간/가격(이벤트 자체
  `price_text`)/타겟연령/예약 정보 — **운영시간 행 자체가 없고 메뉴 행 자체가
  없다.** 공연장 예시 그대로, 장소 자체 영업시간이 아니라 그 안에서 열리는
  이벤트의 기간/가격만 나온다.

→ 사용자가 제시한 2패턴 구분은 이미 `item_type` 하나로 정확히 갈라져 있어
추가 구조 변경이 필요 없었다.

## 발견한 실제 문제 — 스팟 카드 안에서 "메뉴"가 카테고리 무관하게 노출됨
스팟 카드 안의 운영시간/가격/메뉴 3개 행을 실측한 결과:
- **운영시간**: 공공데이터(`operating_hours`)가 도서관·박물관 등에도 실제로
  채워져 있어 폴백이 의미 있음 → 문제 없음.
- **가격**: `is_free=true`면 "무료입장"이 실제 사실이라 공원 등에도 유의미 →
  문제 없음.
- **메뉴**: 폴백이 없다. `spot-curations-panel.tsx`(관리자 큐레이션 화면)를
  확인한 결과, 이 기능 자체가 애초에 **"키즈친화 식당"(category_min='놀이방식당')
  후보만 검색되도록 하드코딩**돼 있었다(2026-09-01 결정). 즉 공원·도서관·
  캠핑장·광장 등은 메뉴를 입력할 방법 자체가 없는데도, 상세카드는 모든
  카테고리에 무조건 "메뉴" 행을 보여줘 "상세 메뉴 정보는 순차적으로 추가될
  예정이에요"라는, 사실은 추가될 일이 없는 문구가 영구히 노출되고 있었다.

사용자에게 메뉴 노출 범위를 확인한 결과: **"키즈친화식당만(현행 유지)"** 선택.

## 변경 사항

### 1. `src/lib/spaces/spot-category-groups.ts`
`spot-curations-panel.tsx`에 로컬로만 있던 상수를 이 파일로 옮겨 export했다 —
관리자 큐레이션 후보 검색 범위와 유저 화면 메뉴 행 노출 범위가 항상 같은 값을
가리키도록 단일 출처로 통일(제5장 제4·6조 하드코딩 최소화/기존 구조 우선).
```ts
export const KIDS_RESTAURANT_CATEGORY_MIN = CORE_SPOT_CATEGORIES.find((c) => c.id === 'kids-restaurant')?.minors[0];
```

### 2. `src/components/admin/spot-curations-panel.tsx`
로컬 정의를 제거하고 위 상수를 import해서 그대로 사용(동작 변화 없음, 중복
제거만).

### 3. `src/components/map/detail-modal.tsx`
"메뉴" 행을 감싸는 조건에 카테고리 검사를 추가했다:
```tsx
{curation !== undefined && item.category_min === KIDS_RESTAURANT_CATEGORY_MIN && (
  <div>...메뉴 행...</div>
)}
```
운영시간/가격 행은 위에서 설명한 대로 다른 카테고리에도 유의미한 폴백이 있어
그대로 두었다 — 이번 변경은 메뉴 행에만 한정했다.

## 특이 사항
- 이번 결정("키즈친화식당만")에 따라 **키즈카페(category_min='키즈카페')는 메뉴
  행이 계속 보이지 않는다** — 사용자가 언급한 "키즈카페도 메뉴가 있을 수 있어서"
  우려는 이번 범위에서는 반영하지 않았다(현행 유지를 명시적으로 선택함). 추후
  키즈카페도 메뉴를 지원하고 싶다면 (1) `spot-curations-panel.tsx`의 후보
  검색 범위를 키즈카페까지 넓히고 (2) `detail-modal.tsx`의 조건을
  `[KIDS_RESTAURANT_CATEGORY_MIN, 키즈카페_상수].includes(item.category_min)`
  형태로 바꾸면 된다 — 두 곳 모두 이번에 만든 단일 상수(`KIDS_RESTAURANT_
  CATEGORY_MIN`)를 배열로 확장하는 정도의 작은 변경이라 언제든 쉽게 확장
  가능한 구조로 만들어 뒀다.
- 별도로, "요일별로 다른 주차를 매칭하는" 운영 요일 규칙 확장(예: 2번째 화요일 +
  4번째 목요일을 따로 지정)은 사용자가 이번에 명시적으로 보류를 확정했다
  ("서로 다른 요일에 서로 다른 주차 따로 매칭은 안되는걸로 하자") — 기존
  구현(요일 여러 개 × 주차 여러 개의 전체 조합만 지원)을 그대로 유지하며 추가
  변경 없음.
