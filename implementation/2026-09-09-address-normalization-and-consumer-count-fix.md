사용자 질문: "어.. 중복 스팟 검수 및 매핑에서 저 버그 고쳤어? 그리고 현재
캠핑장 3395건 나오던데 open_spaces에서.. 그건 합친거는 대표 1건만 친거야?

## 구현 일시
2026-09-09

## 1. "저 버그" — 주소 광역 표기(장/단축형) 정규화
직전 대화에서 확인한 실측 사례: "플로렌스 글램핑"(주소: 경기**도** 가평군..)과
"플로렌스 글램핑 & 캠핑"(주소: 경기 가평군..)은 실제로 같은 캠핑장인데
`normalized_address` 완전일치 판정에는 걸리지 않았다(광역 표기가 "경기도"/
"경기"로 달랐기 때문) — 이번 사례는 좌표가 30m 이내라 GPS 근접 판정으로
우연히 잡혔을 뿐, 좌표가 부정확하거나 없는 다른 데이터였다면 놓쳤을 것이다.

### 변경 사항
`scripts/migrations/2026-09-09-normalize-address-region-prefix.sql`
- 신규 `normalize_address_region_prefix(addr text)` 함수: 주소 맨 앞
  광역 표기를 단축형으로 통일한다(예: "경기도"→"경기", "서울특별시"→"서울",
  "강원특별자치도"/"강원도"→"강원" 등 17개 광역 전체).
- **통째로 지우지 않고 단축형으로 통일한 이유**: 지워버리면 "서울 중구.."와
  "부산 중구.."처럼 서로 다른 광역시의 동일 구/도로명이 우연히 같은
  문자열로 뭉쳐 오묶음(false positive)을 만들 위험이 있다(제3장 제5조
  추측 금지 — 근거 없는 새 위험을 만들지 않는다). 단축형 통일은 광역 단위
  구분은 유지한 채 표기 차이만 없앤다.
- `find_spot_dedup_candidates`의 `normalized_address` 계산에 이 정규화를
  앞단(공백 제거보다 먼저)에 끼워 넣었다 — 이 RPC 하나만 고쳤다(같은
  주소를 다루는 다른 자동화 잡, `dedupe-open-spaces.mjs`의 교차 출처
  정제는 이번 지시 범위 밖이라 건드리지 않았다).

### 검증
- 실측: `normalize_address_region_prefix('경기 가평군..')`과
  `normalize_address_region_prefix('경기도 가평군..')`이 동일한 "경기
  가평군.."으로 정규화됨을 확인. `'서울특별시 중구..'`/`'부산광역시 중구..'`는
  각각 "서울 중구.."/"부산 중구.."로 서로 다르게 유지됨을 확인(교차 오묶음
  방지 확인). `null` 입력도 안전하게 `null` 반환.
- `find_spot_dedup_candidates`가 정규화 함수 적용 후에도 정상 동작(미매핑
  모드 5건 페이지, 키즈카페 중분류 5건 페이지 모두 정상 반환) 확인.

## 2. "캠핑장 3395건" — 대표 반영 여부 확인 및 실제 버그 수정
확인 결과: **소비자 화면(스팟픽 지도)의 노출 중분류 칩 카운트는 대표를
반영하지 않고 있었다** — 실제 버그였다.

`src/lib/spaces/get-service-category-counts.ts`(`/api/nearby/service-
categories`가 호출, 지도 대분류/중분류 바텀시트의 "N건" 칩 문구에 쓰임)는
[[2026-09-09-admin-grid-representative-collapse]](Step 82)에서 관리자
그리드에 적용한 `group_id is null or is_dedup_representative` 필터가
**빠져 있었다** — 병합된 중복 멤버까지 전부 세고 있었다.

실측(코드 수정 전 상태의 DB에 동일 필터 없이 다시 질의): 캠핑장 노출
중분류(자연/공원 > 캠핑장 / 피크닉장) 기준
- 대표 미반영(수정 전 코드가 실제로 세던 방식): 3,859건
- 대표만 반영(수정 후 코드가 세는 방식, 정확한 값): **3,399건**

사용자가 관찰한 "3395건"이 왜 raw(3,859)보다 대표값(3,399)에 훨씬 가까운지는
`count: 'estimated'`(정확한 COUNT가 아니라 플래너 추정치)라는 점 외에는
명확히 설명하지 못했다 — 어느 시점의 데이터를 봤는지, 통계가 얼마나
최신이었는지에 따라 추정치가 크게 흔들릴 수 있다는 점만 확인했다. 다만
**코드 자체에 대표 필터가 빠져 있었다는 것은 코드 리뷰로 명백히 확인된
사실**이라, 관찰된 숫자의 정확한 유래와 무관하게 수정이 필요했다.

### 변경 사항
`getServiceCategoryCounts`의 쿼리에 `.or('group_id.is.null,is_dedup_
representative.eq.true')`를 추가했다 — 관리자 그리드와 소비자 화면이
"하나의 깔끔한 레코드"라는 동일한 기준을 쓰도록 통일.

### 검증
- 실측: 수정 후 쿼리를 직접 실행해 캠핑장 기준 정확히 3,399건(대표만)이
  나옴을 확인.
- `npx tsc --noEmit` / `npm run test`(1385건, 변경 없음 — 이 함수는 다른
  API 라우트/서버 함수와 동일하게 이 코드베이스에서 전용 테스트 파일을
  두지 않는 관례를 따름, 실측 SQL로 검증) / `npm run build` 전체 통과.

## 특이 사항
- `getServiceCategoryCounts`처럼 `service_category_id` 기준으로 개수를
  세는 다른 화면이 앞으로 추가된다면 이 필터를 빠뜨리지 않도록 주의가
  필요하다 — 이번 건으로 "대표 필터가 필요한 조회 지점"이 최소 3곳(관리자
  그리드, `get_nearby_spaces_and_events`/`get_spots_by_service_category`
  RPC, 이 카운트 함수)임이 드러났다.
