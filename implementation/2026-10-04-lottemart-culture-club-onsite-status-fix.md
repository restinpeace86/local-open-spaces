# 롯데마트 5번째 접수상태("현장접수") 발견 및 분류 버그 수정

## 구현 대상
사용자 지시(2026-10-04): "나도 상태 변화 알림이 좋을것 같지만 ... 여기
접수가능 / 접수준비로 되어있던데... 접수상태/수강신청쪽에 상태쪽은 어떤것들이
있지?" — 관리자 패널에서 "전체 상태" 필터가 4개뿐인 걸 보고 실제로 몇 개가
있는지 재확인을 요청받았다.

## 실측 확인
기존엔 13개 지점 약 220건 표본으로 4개 상태(바로신청/대기자신청/접수마감/
전화문의)만 확인했었다. 이번엔 60개 지점 × 대상 3 × 학기 2 **전체 조합을
전수 스캔**(15,101행, 15,396개 상태 버튼)해 버튼 텍스트를 집계했다:

| 상태 | 건수 |
|---|---|
| 접수마감 | 6,504 |
| 전화문의 | 5,209 |
| 바로신청 | 3,374 |
| 대기자 신청 | 295 |
| **현장접수** | **14** |

**정확히 5개**였다 — "현장접수"를 처음에 놓쳤다. 실제 마크업은
`<a href="#none" id="" class="btn-status">현장접수</a>`로 **onclick 속성
자체가 없다**(전화문의의 `fn_fieldCnsl('')`처럼 빈 함수 호출도 아님). 기존
파서(`parseRegistrationStatus`)는 onclick 패턴으로만 판별했기 때문에 이
14건을 전부 기본 폴백인 '접수마감'으로 **잘못 분류**하고 있었다.

## 변경 사항
- `scripts/ingest/lottemart-culture-club.mjs`: `parseRegistrationStatus`에
  텍스트 기반 분기(`>현장접수<`) 추가 — onclick 패턴 우선순위(바로신청 >
  대기자신청 > 전화문의) 다음, 접수마감 폴백 이전에 위치.
- `scripts/migrations/2026-10-04-lottemart-culture-club-onsite-status.sql`
  (신규, 적용 완료): `registration_status` CHECK 제약에 '현장접수' 추가.
- `scripts/ingest/lottemart-culture-club.test.mjs`: 실측 현장접수 마크업
  fixture + 테스트 1개 추가.
- `src/components/home/lottemart-culture-club-view.tsx` /
  `src/components/admin/lottemart-culture-club-panel.tsx`: 타입 유니온에
  '현장접수' 추가, 뱃지 색상은 전화문의와 동일 톤(회색, onclick 없는 순수
  안내 문구라는 공통점)으로 묶음. 관리자 패널 상태 필터 옵션에도 추가.
- **전체 재수집 1회 실행**(60개 지점, 수정된 분류 로직으로) — 기존에
  접수마감으로 잘못 들어간 14건이 현장접수로 교정됨.

## 검증
- `npx tsc --noEmit` / `npm run test`(265개 파일 2,771개, 신규 1개 포함) /
  `npm run build` 전부 통과.
- 재수집 후 실제 DB에서 현장접수 건수가 발견했던 14건과 일치하는지 확인.

## 특이 사항
- 이 버그가 발견된 경위 자체가 유의미하다 — 처음 설계할 때 ~220건 표본으로
  "상태 필드 없음, 버튼으로 판별" 로직을 확정했는데, 표본이 전체의 1.5%
  수준이라 희귀 상태(0.09%, 14/15,101)를 놓쳤다. 사용자가 관리자 화면에서
  필터 옵션 개수를 직접 보고 의문을 제기하지 않았다면 계속 조용히 틀린
  채로 남아있었을 것 — 전수 스캔 없이 표본만으로 "이게 전부다"라고 단정하면
  안 된다는 교훈.
