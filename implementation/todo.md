## 📋 이벤트 링크 버튼 노출 3단계 우선순위

1. **1순위: 직접 예약/신청 링크가 있는 경우**
   - **조건:** 원천데이터에 개별 프로그램의 공식 접수/예약 URL이 포함되어 있는 경우. (ex. seoul_public_reservation 등)
   - **버튼 UI:** `[예약 / 신청하기]`
   - **동작:** 해당 원천 예약 URL로 다이렉트 이동.

2. **2순위: 예약 링크는 없지만, 공식 상세/홈페이지 URL이 있는 경우**
   - **조건:** 별도의 예약 시스템은 아니지만, 해당 행사의 공식 안내 페이지나 상세 소개 URL(`DETAIL_URL` 등)이 원천데이터에 포함된 경우. (각 원천데이터를 확인하여 상세 URL 이 있는지 확인할것.. 이건 Image URL과 다름)
   - **버튼 UI:** `[상세 정보 보기]` (또는 `[공식 안내 페이지]`)
   - **동작:** 원천데이터에 포함된 공식 상세 페이지 URL로 이동하여 행사의 깊이 있는 정보(일정, 준비물 등) 제공.

3. **3순위: 둘 다 없는 경우 (Fallback)**
   - **조건:** 예약 링크와 상세 페이지 링크가 모두 누락된 경우.
   - **버튼 UI:** `[네이버에서 정보 찾아보기]`
   - **동작:** 네이버 스마트 검색 딥링크로 연결.
     - **검색어 조합 규칙:** `https://search.naver.com/search.naver?query={이벤트명}` 형태로 URL 인코딩하여 유저가 네이버에서 바로 관련 정보를 탐색할 수 있도록 방어. (이벤트명이[서초문화재단] 서리풀청년아트갤러리 전시 [Fictionally Alibi] 등 되어있을 경우 사족이 너무 많아 title로 검색하면 나오지 않음.. 서리풀청년아트갤러리 전시 서초와 같이 title 축약 + 장소로 하여 검색어 조합할 것.
     [도림생활문화센터(4분기)]모임방 (1시간 5,000원/추가 시간당 2,500원)의 경우 모임방 영등포 이렇게 하면 또 검색하면 나오지 않음.. 이경우는 도림생활문화센터 모임방 영등포 이런식으로 되어야됨.
     상기와 같이 규칙에 대하여 네이버 스마트 검색 결과로써 정보에 대한 정확도가 높을 것 같은 검색어로 조합하여 url 던져야됨

현재 관리자 화면의 **[오늘 반영 현황 / 재수집 도구]** 탭에서 다음과 같은 치명적인 버그와 성능 저하 현상이 발생하고 있습니다. 이를 진단하고 수정해 주세요.

## 🐛 발생 중인 문제점

1. **건수가 0건으로 초기화되는 현상 (타임존 버그)**
   - 처음 화면에 진입할 때는 건수가 정상적으로 집계되지만, 특정 타이밍이나 리렌더링/새로고침 시 **오늘 날짜의 건수가 갑자기 `0`건으로 튀어버리거나 사라지는 현상**이 발생합니다. (이에 따라 하기 리스트 조회도 오늘 건수 조회하기가 처음에는 나오는데 그후로는 0건으로 나옴)
   - 원인 추정: Supabase/PostgreSQL 서버의 기본 타임존(UTC)과 한국 시간(KST) 간의 시차 충돌로 인해 날짜 경계선 계산이 꼬이거나, 프론트엔드 상태(State) 관리 과정에서 로딩 중 기본값(`0`)으로 덮어씌워지는 문제.

2. **집계 속도가 지나치게 느린 현상 (성능 저하)**
   - 오늘 반영 현황 건수를 집계할 때 로딩이 매우 오래 걸립니다. 
   - 원인 추정: 인덱스가 없는 상태에서 매번 무식하게 테이블 전체를 뒤지는(`Full Scan`) 비효율적인 `COUNT(*)` 쿼리가 실행되고 있거나, 개별 에이전트마다 쿼리를 다중으로 날리고 있을 가능성.

---

## 🛠️ 요구 사항 및 수정 방향

1. **KST(한국 시간) 기준 명시적 날짜 범위 설정**
   - 서버의 기본 `CURRENT_DATE`나 `NOW()` 함수에 의존하지 말고, 쿼리를 생성할 때 **명확하게 한국 시간(KST, UTC+9) 기준 오늘 00:00:00부터 23:59:59까지**의 타임스탬프 범위를 문자열(ISO 또는 명시적 포맷)로 정확히 산출하여 쿼리 조건(`>= AND <=`)으로 전달하도록 수정해 주세요.

2. **집계 쿼리 최적화 및 인덱스 확인**
   - 불필요하게 무거운 `COUNT(*)`를 여러 번 파편화해서 날리지 말고, 한 번의 쿼리로 그룹화(`GROUP BY agent_name` 등)하여 깔끔하게 가져오도록 최적화해 주세요.
   - Supabase DB 측에서 `created_at` 컬럼 등에 인덱스가 제대로 걸려있는지 확인하고, 빠른 조회가 가능하도록 쿼리를 다듬어 주세요.

3. **프론트엔드 상태(State) 및 로딩 방어**
   - 데이터를 불러오는 동안 UI가 버벅이거나 이전 데이터를 빈 값(`0`)으로 잘못 초기화해 버리는 상태 관리의 허점이 있다면 이를 보완하고, 명확한 로딩 스피너/상태 처리 로직을 적용해 주세요.

위 내용에 따라 현재 구현된 서버 액션(API) 쿼리와 프론트엔드 컴포넌트 코드를 검토하고, **타임존 문제를 해결한 정확한 날짜 계산 로직**과 **최적화된 집계 쿼리 코드**를 작성해 주세요.

현재 구축 중인 스팟 큐레이션 기능 중 **네이버 플레이스 등에서 긁어온 메뉴 데이터를 파싱하여 '키즈메뉴'를 자동으로 감지하고, 관리자 뱃지 연동 및 유저 화면 하이라이트(UI)까지 이어지는 풀사이클 기능**을 구현하고자 합니다.

다음 요구사항에 맞춰 데이터 구조, 백엔드 파싱/키워드 매칭 로직, 그리고 프론트엔드 UI 컴포넌트 코드를 작성해 주세요.

## 📋 세부 구현 요구 사항

### 1. 엄선된 '키즈메뉴' 감지 키워드 사전 (Keyword Dictionary)
메뉴판에 실제로 단독 주문 가능한 품목으로 등재되어 있으며, 아이들이 선호하거나 자극지 않는 메뉴들로 한정하여 다음 키워드 사전을 적용해 주세요. (오탐지 방지를 위해 일반 공기밥, 설렁탕류, 냉동너겟 등은 철저히 배제)

- **밥/주먹밥 계열:** `주먹밥`, `김가루밥`, `꼬마김밥`, `참치주먹밥`, `볶음밥`
- **면/분식 계열:** `잔치국수`, `우동`, `짜장`, `짜장면`, `카레라이스`,  `스파게티`
- **국물 계열 (선별 적용):** `미역국`, `소고기미역국`
- **고기/메인 찬 계열:** `떡갈비`, `함박스테이크`, `돈까스`, `돈가스`, `치즈돈까스`, `순살치킨`, `불고기`
- **계란 및 사이드 계열:** `계란말이`, `치즈계란말이`, `계란찜`, `달걀찜`, `감자튀김`

### 2. 관리자 화면: 메뉴 파싱 및 '키즈메뉴' 자동 뱃지 부여
- 관리자가 스팟 큐레이션 화면에서 **[메뉴 파싱]** 버튼을 실행하면, 수집된 메뉴 이름들이 위 키워드 사전과 대조(Regex 또는 Includes 매칭)됩니다.
- 매칭되는 키즈메뉴가 하나라도 발견될 경우:
  - 스팟 큐레이션 설정의 **[키즈메뉴] 뱃지가 자동으로 활성화(ON)** 되도록 연동해 주세요. (관리자가 수동으로 끄거나 켤 수도 있어야 함)
- 개별 메뉴 데이터 저장 시, 키즈메뉴 조건에 부합하는 항목에는 `is_kids_menu: true` (또는 관련 태그 플래그)를 함께 저장해 주세요.

### 3. 유저 화면: 스팟 상세 메뉴판 하이라이트 및 태깅 (UX)
- 유저가 특정 스팟 상세 화면에서 메뉴 리스트를 조회할 때, `is_kids_menu: true`로 마킹된 메뉴 아이템은 시각적으로 즉시 눈에 띄도록 강조해 주세요.
- 단일 스크롤형 스팟 상세 페이지 내 **[메뉴 정보] 섹션 타이틀 바로 하단**에 다음 안내 문구를 은은한 인포 배너 형태로 배치해 주세요.
  - **안내 문구 텍스트:** `💡 "아이들이 선호하는 인기 메뉴 데이터를 AI가 분석하여 ⭐️ 태그로 추천해드려요!"`
- **UI 연출 가이드:**
  - 해당 메뉴 카드/행에 은은한 파스텔톤(예: 연한 노란색) 배경 적용
  - 메뉴 이름 옆에 ⭐️ **별표 아이콘**과 함께 **`[키즈추천]`** (또는 `[아이와 함께]`) 뱃지/태그 노출

## 🛠️ 요청 사항
1. **데이터 모델/스키마 수정 제안:** 메뉴 데이터 구조(JSON 등)에 `is_kids_menu` 플래그를 저장하기 위한 구조 보완.
2. **파싱 & 키워드 매칭 로직:** 메뉴 텍스트 배열을 입력받아 위 키워드 사전을 대조하고 `is_kids_menu` 여부를 판별하여 뱃지 상태까지 산출하는 백엔드(Server Action 등) 함수 코드.
3. **프론트엔드 UI 컴포넌트:** 유저 스팟 상세 화면에서 키즈메뉴에 대해 노란색 배경 하이라이트와 별표 태그를 렌더링하는 UI 코드.

[개선사항 6] [Feature Implementation Task] 이벤트/체험 스팟 '다중 소스 가격 수집 및 관리자 검증 UI' 구현

현재 개발 중인 이벤트/체험 큐레이션 관리자 대시보드에 **여러 경로로 가격 정보를 병렬 수집(OR 조건)하고, 관리자가 한 페이지에서 모든 소스 결과를 쉽게 비교하며 원문을 확인·확정할 수 있는 파이프라인 및 UI**를 구현하고자 합니다.

다음 요구사항에 맞춰 데이터 모델, 병렬 수집 로직, 그리고 관리자 검증 화면(UI) 코드를 작성해 주세요.

## 📋 세부 구현 요구 사항

### 1. 다중 소스 병렬 가격 수집 파이프라인 (OR 조건)
특정 이벤트 스팟에 대해 아래 4가지 소스에서 **동시에 가격 및 연령/대상 기준 데이터를 수집(추출)**하여 후보군(Candidates)으로 생성해 주세요.
- **소스 1 (블로그 큐레이션 파싱):** 연동된 선별 블로그 본문 내 가격 및 연령 키워드 텍스트 추출.
- **소스 2 (원천 소스 상세 설명 파싱):** 공공데이터 API 등의 기본 제공 상세 설명(Description) 텍스트 분석.
- **소스 3 (공식 홈페이지 크롤링):** 원천 데이터에 포함된 공식 상세 URL 직접 크롤링.
- **소스 4 (정형 요금 필드):** 공공데이터 API의 요금 전용 컬럼(`USE_FEE` 등) 데이터 추출.
- **소스 5 그 외:** 그 외 가격에 대하여 가져올 수 있는 방법이 있다면 제안해주세요. (없으면 없다고 하기)
- *참고:* 가격 데이터 추출 시, 금액뿐만 아니라 **연령/대상 기준(예: 성인, 아동, 36개월 이상, 초등학생 이하 등)**도 함께 파싱되도록 구조화해 주세요.

### 2. 관리자 검증 대시보드 (Single-Page UI/UX) - ★ 핵심 요구사항
관리자가 이벤트 탭의 상세 페이지에 진입했을 때, 블로그 큐레이션버튼과 동일 레벨로 가격 큐레이션 버튼이 존재하여야 함.
가격 큐레이션 버튼을 눌렀을 경우 사기와 같이 화면이 구성되며, **스크롤 한 번으로 모든 소스의 수집 결과를 한 화면에서 비교하고 원문에 즉시 접근**할 수 있어야 합니다. ([가격 및 이용요금 다중 소스 검증] 참조)
- **화면 구성 가이드 (가격 검증 섹션):**
  - **4개 소스별 카드/영역 나열:** 각 소스(블로그, 원천설명, 공식홈페이지, API필드)별로 추출된 '가격 및 연령 기준'과 '수집 상태(성공/실패/데이터없음)'를 카드 형태로 한눈에 배치.
  - **즉시 이동/확인 링크 (Direct Action):**
    - 소스 1: 수집된 블로그 글로 곧바로 이동하는 외부 링크(새창) 제공.
    - 소스 2: 원천 설명 텍스트 전문을 펼쳐서 볼 수 있는 뷰어/모달 제공.
    - 소스 3: 공식 상세 홈페이지로 넘어가는 외부 링크(새창) 제공.
    - 소스 4: 원천 데이터의 어느 부분에 정형 요금 필드가 있어서 가져왔는지 명시
  - **최종 확정 입력 폼 (Final Input Form):**
    - 관리자가 각 소스의 후보를 참고하여 직접 입력/수정할 수 있는 최종 입력 필드 제공.
    - 항목 구성: 유무료 여부(무료/유료/변동), 최종 연령 기준, 최종 가격 텍스트, 추가 메모.
    - **[가격 정보 최종 확정 및 저장]** 버튼.


## 🛠️ 요청 사항
1. **데이터 모델(스키마) 설계:** 4개 소스별 수집 결과와 최종 확정된 가격/연령 데이터를 저장할 수 있는 DB 테이블/JSON 구조 제안.
2. **병렬 수집 로직 (Backend):** 1~4번 소스에서 각각 가격과 연령 기준을 파싱하여 구조화된 후보 데이터로 반환하는 서버 액션(API) 코드.
3. **관리자 검증 UI 컴포넌트 (Frontend):**

[개선사항 7] [Feature Implementation Task] 상단 날씨 위젯 및 실시간·주말 날씨 바텀시트(Bottom Sheet) 구현

부모 유저를 위한 키즈/놀이방 식당 및 이벤트 큐레이션 앱의 **메인 홈 상단 헤더(Header) 및 날씨 정보 연동 UI**를 구현하고자 합니다. 

챗봇 백엔드에서 이미 수집 중인 '오늘 실시간 기상 데이터'와 '이번 주말 예보 데이터'를 프론트엔드 UI에 안정적으로 녹여내는 작업을 진행해 주세요.

## 📋 세부 구현 요구 사항

### 1. 최상단 헤더(Header) 컴팩트 레이아웃 구성
메인 홈 최상단 고정 헤더를 공간 효율적이고 미니멀하게 한 줄로 구성해 주세요.
- **좌측:** 현재 지역 선택 (예: `📍 분당구 ▾`) -> 클릭 시 위치 변경/설정 바텀시트 연동 (현재 성남시 분당구로 시/군/구 까지 되어있는데 분당구만 보여주고 가로폭 축소할 것)
- **중앙:** 검색창 (예: `🔍 가고 싶은 식당, 이벤트 검색...`) (검색창 길이도 조금 축소할 것) 
- **우측 (신규):** 날씨 위젯 (예: `☀️ 24°`) -> 아이콘과 기온만 미니멀하게 노출하여 공간 절약
- *요구 사항:* 모바일 가로 폭에서 찌그러지지 않도록 flex 레이아웃과 적절한 텍스트 줄임 처리 적용.

### 2. 날씨 위젯 클릭 시 '날씨 리포트 바텀시트(Bottom Sheet)' 구현
상단의 날씨 위젯(`☀️ 24°`)을 터치했을 때, 화면 하단에서 스르륵 올라오는 바텀시트 모달을 만들어 주세요.
- **상단 탭 구성:** `[오늘 실시간]` / `[이번 주말 예보]` 탭 전환 기능.
- **[탭 1] 오늘 실시간 뷰:**
  - 현재 기온 및 날씨 상태 아이콘
  - 핵심 대기질 지표: 미세먼지(PM10), 초미세먼지(PM2.5) 상태 뱃지 (좋음/보통/나쁨 컬러링)
  - 강수 정보: 강수 확률 및 상태
  - **스마트 가이드 멘트 박스:** 대기질이나 비 소식에 따라 "오늘 미세먼지가 나쁘니 실내 놀이방 식당을 추천해요!" 같은 맞춤형 텍스트 노출 영역.
- **[탭 2] 이번 주말 예보 뷰 (토/일):**
  - 토요일 / 일요일 각각의 예상 기온, 날씨 아이콘, 강수 확률, 주말 나들이 추천 한 줄 평 카드 나열.

### 3. 데이터 연동 및 컴포넌트 구조
- 백엔드(또는 기존 챗봇 API)에서 전달되는 날씨 데이터 타입/인터페이스 정의.
- 반응형 모바일 UI(Tailwind CSS 등 활용)로 깔끔하고 직관적인 카드형 디자인 구현.

[개선사항 8] 당신은 영유아 동반 나들이 및 식당 큐레이션 서비스("웰컴키즈존")를 위한 전문 AI 데이터 큐레이션 어시스턴트입니다. 당신의 역할은 특정 매장에 대해 수집된 멀티 쿼리 블로그 검색 스니펫들을 분석하여, 매장의 동일성/위치를 엄격하게 검증하고 영유아 친화 편의 시설 속성을 정확하게 추출하여 엄격한 JSON 형식으로 반환하는 것입니다.


### 1단계: 매장 동일성, 주소 및 지점 검증 (가장 중요)
- 시스템이 제공하는 대상 매장의 **[도로명 주소, 지번 주소, 행정동(예: 정자동), 도로명(예: 불정로)]**을 블로그 스니펫 내용과 철저히 대조합니다.
- 블로그 본문 안에 대상 주소와 일치하는 키워드(예: 해당 '동' 이름, '도로명', 혹은 특정 지점명인 'OO점')가 포함되어 있는지 확인하세요.
- 만약 글 내용이 상호명은 같지만 **다른 지역/다른 지점(예: 강남점, 부산점 등)**을 다루고 있거나, 대상 주소와 전혀 무관한 곳이라면 `is_valid_match`를 `false`로 처리해야 합니다.


### 2단계: 블로그 글의 최신성 극대화(1년 이내)
- 네이버 블로그 검색 API는 결과값으로 가져오는 포스팅 날짜를 postdate (형식: YYYYMMDD, 예: 20251014) 사용하여 최신 1년 이내의 글이 아닐 경우는 배제합니다.
- 가장 신뢰도가 높고 최근의 바뀐 정책(아기의자 유무 등)을 최대한 정확히 반영하기 위함입니다.

### 2단계: 속성 추출 규칙 (유효한 매장인 경우에만)
1. **is_valid_match (boolean):** 스니펫이 대상 매장/위치와 신뢰할 수 있게 일치하면 `true`, 지점이 다르거나 다른 지역이라 일치하지 않으면 `false`.
2. **has_high_chair (boolean):** 해당 매장에 아기의자(하이체어, 아기 의자)가 있다는 언급이 명시적이거나 암시적으로 있으면 `true`, 없으면 `false`.
3. **has_baby_tableware (boolean):** 유아식기, 아기식판, 유아용 포크/숟가락, 앞접시 등이 제공된다는 언급이 있으면 `true`, 없으면 `false`.
4. **space_type (string):**
   - `"indoor"`: 일반적인 실내 식당/카페 (기본값)
   - `"outdoor"`: 전면 야외 공간 (야외 좌석, 캠핑장 등)
   - `"mixed"`: 테라스, 잔디마당, 루프탑, 야외 테이블 등 실내와 야외 공간이 공존하는 형태
5. **confidence (string):** 텍스트의 명확성과 빈도에 따라 `"high"`, `"medium"`, `"low"` 중 선택.
6. **evidence_summary (string):** 한국어로 결정 이유를 간략하게 요약. 잘못되었거나 모호한 스니펫을 필터링했다면 그 내용을 명시할 것.

-  1년 이내 최신성 필터링 (코드 레벨): 가져온 6개 글의 postdate를 확인하여 현재 기준(2026년)으로부터 정확히 1년 이내 글들만 남기고 오래된 글들은 즉시 버립니다.
- 필터링 후 남은 글들에 대하여 LLM으로 분석을 곧바로 Gemini AI로 던져 분석을 돌립니다. (하기 '출력 제약 사항' 참고)
