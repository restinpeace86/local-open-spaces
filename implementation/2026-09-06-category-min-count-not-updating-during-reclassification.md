# 어린이놀이시설(실내) 재분류 중 총 건수(페이징)가 안 바뀌는 문제

## 구현 대상
사용자 질문: "내가 키즈/놀이시설 대분류의 어린이놀이시설(실내) 중분류에서 많은
건수에 대하여 기타 혹은 놀이방식당으로 변경하고 있는데... 페이징에서 총
1364건 1/28페이지가 변하지 않아 이건 왜그런거야?"

## 구현 일시
2026-09-06

## 원인 (실측)
`/api/admin/data-grid`의 open_spaces 조회는 성능을 위해
`count: 'estimated'`(Postgres 플래너 통계 기반 추정치)를 쓴다(기존 설계,
전체 141,815행 무필터 카운트가 느려서 채택한 관례). 이 값은 실시간
COUNT(*)가 아니라 **마지막 ANALYZE(통계 갱신) 시점의 스냅샷**이다.
autovacuum은 테이블 전체 행 수의 5%(`autovacuum_analyze_scale_factor=0.05`,
141,815행 기준 약 7,100행) 이상 바뀌어야 자동으로 다시 ANALYZE를 실행하는데,
사용자가 지금 하는 것처럼 수십~수백 건씩 수동으로 재분류하는 정도로는 이
임계치에 한참 못 미친다(실측: 이번 확인 시점까지 146건 변경, 자동 ANALYZE
발동 안 함). 그래서 실제로는 계속 줄어들고 있는데도(실측: 1,482건 →
1,398건으로 확인, 사용자가 반영한 변경이 실제 DB에는 정상 반영되고 있었다)
화면에 보이는 "총 건수"만 마지막 ANALYZE 시점 값(1,364)에 멈춰 있는 것처럼
보였다.

## 변경 사항
`src/app/api/admin/data-grid/route.ts`의 `queryOpenSpaces`: `category_min`
필터가 걸려 있을 때는 `count: 'exact'`(정확한 실시간 COUNT)를 쓰도록
바꿨다. 필터가 없는 "전체" 조회는 기존 `'estimated'`를 그대로 유지한다.

실측(EXPLAIN analyze, buffers) 근거:
- `category_min = '어린이놀이시설(실내)'` 필터가 있는 정확한 COUNT(*):
  idx_open_spaces_category_min_created_at 인덱스를 그대로 타 **0.66ms** —
  estimated와 체감 차이가 없어 exact로 바꿔도 성능 비용이 사실상 0에 가깝다.
- 필터가 전혀 없는 전체 테이블 COUNT(*): **612ms**(전체 스캔) — 이 비용은
  기존처럼 estimated를 유지해 새로 추가하지 않았다(무필터 조회는 관리자가
  가장 자주 여는 기본 화면이라 성능 저하를 감수할 이유가 없음).

## 검증
- `npx tsc --noEmit` / `npm run test`(115개 파일, 1231개 테스트) /
  `npm run build` 전체 통과. 이 route.ts는 기존 관례상 직접 단위 테스트하지
  않는다(로직이 파일 내부 헬퍼 함수로만 존재하고 Supabase 클라이언트가
  필요해 이 프로젝트 전반의 다른 admin route와 동일하게 별도 테스트가
  없다) — 이번 변경도 조건 1줄 추가라 이 관례를 그대로 따랐다.
- EXPLAIN으로 실측한 비용 차이(0.66ms vs 612ms)를 근거로 필터 있음/없음을
  가르는 것으로 충분하다고 판단했고, 별도 회귀 테스트를 새로 만들지는
  않았다.

## 특이 사항
- `only_unmapped`/`only_mapped` 필터 등 다른 필터 조합까지 전부 exact로
  바꾸는 것은 이번 요청 범위 밖이라 하지 않았다 — 사용자가 실제로 겪은
  시나리오(category_min으로 좁혀서 재분류 작업 중)만 정확히 해결했다.
  다른 필터 조합에서 같은 증상이 재현되면 그때 동일한 방식(EXPLAIN으로
  실측 후 판단)으로 확장할 수 있다.
- 필터 없는 "전체" 조회의 estimated 카운트 오차는 여전히 남아 있다 —
  이는 이번 요청과 무관한, 이 프로젝트가 이미 받아들인 기존 트레이드오프다.
