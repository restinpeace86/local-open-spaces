## 재검증 — 1차 수정이 실제로 배포됐는지부터 확인
운영 도메인의 `/admin/data-grid` 응답 HTML과 컴파일된 CSS 번들을 직접
다운로드해 `.max-h-\[45vh\]{max-height:45vh}` 규칙이 실제로 존재함을 확인했다
— 배포 자체는 정상이었다(캐시 문제 아님). 즉 1차 수정은 적용됐지만 근본적으로
접근 방식이 부족했다.

## 근본 원인 재분석
1. **`vh`는 전역 뷰포트 기준값이라 형제 요소가 이미 가져간 공간을 모른다.**
   이 앱은 `src/app/layout.tsx`에서 모든 페이지(관리자 페이지 포함)에 전역
   하단 탭바(`BottomTabs`, `grid-cols-4`)를 렌더링한다. `body`는
   `h-dvh flex flex-col overflow-hidden`으로 정확히 뷰포트에 맞게 잡혀 있고,
   `AdminDataGridClient`의 루트(`flex-1 min-h-0`)는 "body 높이 − BottomTabs
   높이"만큼만 실제로 받는다. 그런데 필터 바의 캡을 `vh`(전체 뷰포트 기준)로
   줬기 때문에, BottomTabs가 떼어간 만큼을 반영하지 못해 실제 남은 영역보다
   큰 값으로 계산됐다.
2. **필터 바 위 헤더 블록("오늘 반영 현황" + "재수집 도구")에는 애초에 캡이
   없었다.** 1차 수정 때는 사용자가 지목한 "중분류나 등록일등의 조건"만
   필터 바로 좁게 해석해 이 블록은 손대지 않았는데, 사용자가 "여전히 90%"라고
   재확인한 것을 보면 실제로는 이 두 블록(헤더+필터 바)을 합친 영역 전체가
   "검색조건"으로 보이고 있었다 — 필터 바만 캡을 씌워도 위 헤더가 여전히
   크면 합계는 그대로였다.

## 변경 사항
`src/components/admin/data-grid-client.tsx`:
1. 필터 바의 `max-h-[45vh]` → **`max-h-[42%]`**로 변경. CSS 퍼센트 높이는
   "자신을 담고 있는 블록(부모)의 실제 높이"를 기준으로 계산되므로, 부모인
   `AdminDataGridClient` 루트(`flex-1 min-h-0`, 이미 BottomTabs만큼 뺀 실제
   가용 높이를 가짐)를 기준으로 정확히 42%가 계산된다 — 하단 탭바 유무나
   화면 크기와 무관하게 항상 정확한 비율을 보장한다.
2. "오늘 반영 현황"(`TodayBatchSummary`) + "재수집 도구"(`IngestRerunPanel`)를
   기본 접힘 상태로 바꿨다 — `isOpsToolsExpanded`(기본 `false`) 토글 버튼
   ("▾ 오늘 반영 현황 / 재수집 도구 보기")을 추가해, 펼쳐야만 렌더링되게
   했다. 기존 "▾ 상세 필터 더보기"와 동일한 UX 관례. 이 두 위젯은 검수
   작업의 핵심이 아닌 보조 운영 도구라 기본 숨김이 합리적이라 판단했다.

이 두 변경을 합치면: 헤더 블록은 접힘 상태에서 제목+탭 줄 정도(약 80~100px)
로 작아지고, 필터 바는 (BottomTabs를 이미 제외한) 실제 가용 높이의 42%를
넘지 않아, 결과 목록(flex-1)이 항상 남은 절반 이상을 확보한다.
