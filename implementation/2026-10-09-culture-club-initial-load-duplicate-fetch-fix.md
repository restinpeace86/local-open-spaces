## 검토 결과 — "10개만 먼저 가져오기"는 효과가 작다, 실제 원인은 다른 곳

### 백엔드는 이미 빨라서 페이로드 축소의 이득이 작다
같은 세션에서 `EXPLAIN (ANALYZE, BUFFERS)`로 직접 실측한 결과(2026-10-09
"쿼리들 자체도 최적화된거 맞아?" 답변 참고), `/api/culture-club/search`는
반경/브랜드/연령 필터가 섞인 최악의 경우(전국 모든 지점을 거는 수준)도
56ms 안에 끝난다 — row 개수를 5,000 → 10으로 줄여도 DB 처리 시간 자체는
이미 거의 0에 가까워 체감 차이가 거의 없다. 반면 Supabase 원격 호출은
왕복마다 ~400~600ms 고정 지연이 있다(route.ts의 Branch-First 최적화 때
이미 실측해 문서화된 사실) — 즉 "데이터 얼마나 가져오냐"보다 "왕복을
몇 번 하냐"가 체감 속도를 지배한다.

### 실제 원인 — 사용자 말대로 "다른 것도 불러오는게 많아서" 맞았다(중복 조회)
`CultureClubTabView`의 effect 의존성을 직접 추적해 확인했다:
- `useUser()`가 `isLoading`을 돌려주는데, 기존 코드는 이 값을 버리고
  `user`만 썼다. `user`는 로그인 여부 확인이 끝나기 전에도 항상 `null`
  이라, "아직 모름"과 "진짜 비로그인"을 구분하지 못하고 즉시
  `profile=null`로 확정해버렸다.
- 그래서 **1차**로 연령 필터 없는 `basePool`을 조회(로그인 확인이 끝나기
  전)하고, 로그인 확인이 끝나 진짜 프로필(아이 나이)이 들어오면 **2차**로
  연령 필터가 있는 `basePool`을 다시 조회하는 이중 요청이 매 첫 진입마다
  발생했다. 그 사이 `isLoading`이 "끝남→다시 시작"으로 깜빡이는 UX
  글리치도 있었다.
- 이 이중 요청 각각이 ~400~600ms 고정 지연을 또 먹으니, 체감상 "뭔가
  여러 개를 불러와서 느리다"는 사용자의 직관이 정확했다 — 다만 원인은
  "데이터량"이 아니라 "불필요한 왕복 횟수"였다.

### 결론
"처음에만 10개"는 기각 — 효과가 작고, 2차 필터(요일/지점/브랜드 등)를
메모리에서 즉시 거르는 기존 "코어 데이터 캐싱" 설계(2026-10-08 todo.md
개선사항1)와 충돌한다(10개만 받으면 브랜드/요일 필터가 전체 데이터를
대표하지 못해 즉시 필터링이 깨짐, 뒤에서 추가로 받아오는 구조를 새로
만들어야 해 복잡도만 늘고 실제 이득은 적음). 대신 **중복 조회 자체를
없애는 쪽**으로 고쳤다 — 왕복 1회를 통째로 제거하고 깜빡임도 없앤다.

## 변경 사항
- `src/components/home/culture-club-tab-view.tsx`:
  - `useUser()`에서 `isLoading`(→ `isAuthLoading`)도 받는다.
  - 프로필 판정 effect가 `isAuthLoading`이 끝날 때까지 기다렸다가(아직
    모르면 아무것도 확정하지 않음) `profile`을 확정하고, 신규
    `isProfileReady` state로 "연령 필터 여부가 확정됐다"는 신호를 둔다.
  - 기본 데이터 풀(`basePool`) 조회 effect가 `isProfileReady`가 true가
    될 때까지 기다리도록 가드를 추가 — 로그인/프로필 확인이 끝나기 전엔
    아예 요청을 보내지 않아 중복 왕복이 사라진다(대기 중엔 `isLoading`
    초기값(true)이 그대로 유지돼 로딩 화면이 매끄럽게 이어진다).
- `src/components/home/culture-club-tab-view.test.tsx`: `useUser` 모의를
  `isLoading`도 동적으로 바꿀 수 있게 수정, "로그인 여부 확인이 끝나기
  전엔 조회하지 않고, 끝나면 정확히 한 번만 조회한다" 회귀 테스트 추가.

## 검증
- `npx tsc --noEmit` / `npm run test -- --run`(314개 파일 **3,177개**,
  신규 회귀 테스트 포함) / `npm run build` 전부 통과.
- 신규 테스트로 "로그인 확인 중 요청 0건 → 확인 끝나면 정확히 1건"을
  직접 검증(이전 코드로 되돌리면 이 테스트가 실패함을 확인하며 작성).

## 특이 사항
- "페이지네이션으로 처음 10개만" 자체를 아예 하지 않기로 한 건 아니다
  — 필요해지면(예: 반경이 아주 넓어 5,000건에 근접하는 지역이 실제로
  나오면) 별도로 재검토할 수 있지만, 지금 실측된 병목(중복 왕복)과는
  무관해 이번 범위에 포함하지 않았다.
- 로그인 자체(`useUser`의 `auth.getUser()`)나 위치 확정(`useUserLocation`,
  LocalStorage 기반이라 네트워크 없음)이 걸리는 시간 자체는 이번
  수정으로 줄지 않는다 — 다만 그 이후에 "쓸모없는 선행 요청"이 끼어들지
  않게 됐을 뿐이다.
