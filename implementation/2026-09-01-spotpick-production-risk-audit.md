# [코드 점검 및 성능 안정화 요청] 스팟픽(SpotPick) 백엔드/프론트엔드 프로덕션 리스크 진단 및 개선

## 구현 일시
2026-09-01

## 배경
직전 세 작업(기상/대기질 3시간 주기 크론, AI 맞춤 추천 챗봇 엔진, 14만 건 규모
`open_spaces` 검색)의 프로덕션 리스크를 6개 항목 기준으로 코드베이스 전수 점검하고,
실제로 문제가 확인된 항목만 수정했다(추측으로 "일단 고치기"를 하지 않고, 각 항목을
EXPLAIN ANALYZE/실측 호출/유닛 테스트로 먼저 검증한 뒤 결정).

## 점검 결과 및 조치

### 1. DB 공간 검색 인덱싱/Bounding Box — **이미 충족, 코드 변경 없음**
- `open_spaces`는 `latitude`/`longitude` 개별 컬럼이 아니라 PostGIS
  `GEOMETRY(Point,4326)`(project/database_schema.md) 구조다 — 지시서가 가정한 "위경도
  복합 인덱스"에 정확히 대응하는 것은 이미 존재하는 `idx_open_spaces_location_geography`
  (geography 캐스팅 표현식 GIST 인덱스, 2026-08-29 별도 장애 디버깅으로 이미 추가됨)다.
- **실측(EXPLAIN ANALYZE, 라이브 DB)**: `get_nearby_spaces_and_events` 내부 쿼리가
  실제로 `Index Scan using idx_open_spaces_location_geography`를 타는 것을 확인했다.
  `Index Cond`에 `location && _st_expand(...)`가 그대로 찍히는데, 이것이 정확히
  지시서가 요구한 "Bounding Box로 후보군을 줄인 뒤 정밀 계산"이다 — PostGIS GIST
  인덱스는 R-tree 바운딩 박스 프루닝을 `ST_DWithin` 호출 시 자동으로 수행하므로,
  별도의 명시적 `WHERE lng BETWEEN ... AND lng ...` SQL을 추가로 걸 필요가 없다(오히려
  중복이라 이득이 없음).
- **잔여 리스크(별도 과제로 분리, 이번 범위에서 코드 변경하지 않음)**: 반경이 넓을수록
  (특히 40km "1시간 이상" 티어) 바운딩 박스 후보 수 자체가 커져(실측: 15km 반경에서
  후보 2,798건) `ST_Distance` 정렬 비용이 늘어난다. 더 근본적인 개선(KNN `<->` 연산자
  기반 최근접 N개 조회로 전환)은 가능하지만, 이 RPC는 스팟픽 지도 화면(마커 렌더링)의
  핵심 경로를 챗봇과 공유하는 이미 검증된 기존 함수라 — 알고리즘 자체를 바꾸는 것은
  이번 "점검/안정화" 범위를 넘어서는 구조 변경(제5장 제3조 MVP 우선, 임의 확장 자제)
  으로 판단해 별도 지시로 분리 제안한다. 대신 애플리케이션 레이어에서 이미
  (직전 작업에서) 가장 넓은 반경을 선제 조회하지 않도록 재설계해 실질적 위험은 크게
  줄여둔 상태다(아래 항목 5·실측 참고).

### 2. 배치 크론 대량 Upsert 청크 처리 — **대부분 이미 충족, 사각지대 1건 수정**
- `scripts/ingest/lib/supabase-admin.mjs`의 공용 `upsertRows`/`upsertRawIngestData`
  (대부분의 어댑터가 재사용)와 `kma-weather-adapter.mjs`의 `upsertWeatherCaches`는
  이미 500건 단위 청크 + 순차 처리 + 재시도(`withRetry`)로 구현돼 있었다(82,373건
  규모의 playground.mjs가 실제로 겪었던 "단일 upsert에 전량을 담아 응답 없이 멈춤"
  장애를 2026-08-22에 직접 겪고 고친 관례 — 500건은 지시서가 제안한 1,000~5,000건
  범위보다 더 보수적인 값이라 안전 방향으로 이미 충족한다고 판단, 상향 조정하지 않음).
  읽기 쪽(`fetchAllExactSpots` 등 커서 페이지네이션)도 1,000건 단위로 이미 안전하다.
- **사각지대 발견 및 수정**: `scripts/ingest/adapters/deals-collector.mjs`의
  `upsertDeals()`만 이 공용 청크 관례를 타지 않고 `rows` 전체를 단일 `upsert()` 호출에
  그대로 담고 있었다(현재는 실제 제휴 API가 아직 연결되지 않은 뼈대 코드라 당장 대량
  데이터가 들어올 일은 없지만, 실제 연동 후 응답 건수가 커지면 playground.mjs와 동일한
  장애를 재현할 수 있는 잠재적 지뢰였다). 500건 청크 + `withRetry`로 수정.

### 3. Gemini API 하드 타임아웃 — **실제 문제 확인, 수정**
- `summary.ts`의 `buildFinalSummary()`가 `fetchWithTimeout(..., 10000)`으로 **10초**
  타임아웃을 쓰고 있었다 — Gemini가 지연되면 바텀시트 결과 화면이 최대 10초간
  로딩 상태로 보일 수 있어 지시서가 지적한 리스크가 실제로 존재했다. **3.5초**로
  단축했다(요구사항 범위 3~4초 안). 실패/타임아웃 시 항상 `buildTemplateSummary()`로
  폴백하는 기존 catch 로직은 그대로 유지되며 손상되지 않았다.
- 실측: fake timer로 "Gemini가 응답 없이 멈추는(hang)" 상황을 재현해 5초 이내에
  반드시 템플릿 요약으로 폴백함을 신규 테스트로 확인.

### 4. 맛집 지연 로딩 클라이언트 캐싱 — **아키텍처 재확인 후 실제 캐싱 갭 발견, 수정**
- 실제 구현 확인 결과, "🍽 근처 키즈친화 맛집" 조회는 결과 리스트의 개별 스팟(spot_id)
  단위가 아니라 **사용자 자신의 위치(center) 하나를 기준으로 한 세션 단일 조회**다
  (지시서 문구 "이 스팟 저 스팟 상세를 열어볼 때"가 가정한 스팟별 조회 아키텍처와는
  다름 — 실제 코드 기준으로 판단해 그에 맞는 캐싱을 설계했다).
- 이 아키텍처 기준으로 실제 캐싱 갭을 발견했다: 기존에는 React 컴포넌트 state(`
  restaurants`)에만 캐시가 있어, 바텀시트를 닫았다 다시 열면(컴포넌트가 리마운트되어
  state가 초기화됨) 좌표가 그대로인데도 서버에 다시 요청하는 중복이 발생했다.
- 모듈 스코프(컴포넌트 생명주기 밖) 캐시 `nearby-restaurants-cache.ts`를 신설해
  좌표(4자리 반올림, 약 11m 오차 허용) 기준으로 결과/진행 중인 Promise 자체를
  캐싱한다 — 동시에 여러 번 트리거돼도 실제 네트워크 요청은 1회만 나가고, 실패한
  요청은 캐싱하지 않아 재시도가 가능하다.
- 실측(Playwright): 같은 좌표로 챗봇 전체 플로우를 두 번(시트 닫기→다시 열기 포함)
  진행해 "🍽 근처 키즈친화 맛집 보기"를 두 번 클릭해도 실제 네트워크 요청은 정확히
  1회만 발생함을 확인했다.

### 5. 1회성 소프트 폴백의 무한 루프 방지 및 투명성 — **무한 루프 없음(구조적으로 불가능), 투명성 보강**
- `/api/ai-chat/search/route.ts`의 폴백 로직은 반복문/재귀가 전혀 없는 단일 `if`
  블록이라 구조적으로 2회 이상 완화가 발생할 수 없다(코드 검토로 확인 — 원래부터
  안전했음).
- **투명성 보강**: 기존에는 폴백이 일어나도 서버 콘솔에 아무 로그가 남지 않았고,
  사용자에게도 "살짝 범위를 넓혀 찾아봤어요"라는 뭉뚱그린 안내만 갔다. (a) 1차/2차
  조회 각각의 반경·후보 수·필터 통과 수를 서버 콘솔에 명시적으로 로그하도록 추가했고,
  (b) 응답에 `originalRadiusMeters`/`finalRadiusMeters`를 추가해 요약 문구(템플릿·LLM
  프롬프트 양쪽)가 "반경을 1km에서 5km로 넓혀서 찾아봤어요"처럼 실제 조정값을
  구체적으로 안내하도록 개선했다.
- 실측: 1000m→5000m로 완화된 실제 요청/응답에서 `originalRadiusMeters:1000`,
  `finalRadiusMeters:5000`이 정확히 돌아오고 LLM 요약도 자연스럽게 이를 반영함을
  확인.

### 6. Supabase RPC의 STABLE/읽기 전용 여부 — **이미 충족, 코드 변경 없음**
- 라이브 DB에서 `pg_proc.provolatile`을 직접 조회해 `get_nearby_spaces_and_events`와
  `get_nearest_spot_weather` 둘 다 `'s'`(STABLE)로 선언돼 있음을 확인했다 — 두 함수
  모두 `SELECT`만 수행하는 순수 읽기 함수라 STABLE이 정확한 분류다(데이터를 변경하지
  않으므로 VOLATILE일 필요가 없고, 같은 트랜잭션 내에서 파라미터가 같으면 결과가
  달라지지 않으므로 IMMUTABLE보다는 STABLE이 맞다 — IMMUTABLE은 트랜잭션/시간과
  무관하게 항상 같은 결과를 보장해야 하는데 공간 데이터가 계속 갱신되는 테이블을
  읽으므로 해당하지 않음). "커넥션 풀"은 Supabase가 PgBouncer로 관리하는 인프라
  영역이라 애플리케이션 코드가 직접 관리할 대상이 없음을 확인했다.

## 특이 사항
- 항목 1의 "KNN 연산자 기반 재작성"은 스팟픽 지도 화면과 공유하는 기존 핵심 RPC의
  알고리즘 자체를 바꾸는 구조 변경이라, 이번 점검/안정화 범위를 넘어선다고 판단해
  코드를 바꾸지 않고 별도 지시 필요 사항으로만 남겨둔다.
- 항목 4의 캐싱은 지시서가 가정한 "스팟별(spot_id) 캐싱"이 아니라 실제 구현에 맞는
  "사용자 위치별 캐싱"으로 구현했다 — 실제 아키텍처와 다른 전제로 지시가 내려왔을 때
  실제 코드 기준으로 판단해 적용한 사례로 투명하게 기록한다.
