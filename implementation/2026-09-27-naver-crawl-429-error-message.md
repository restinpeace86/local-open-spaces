# 네이버 플레이스 크롤링 실패 안내문 — 429(레이트리밋)와 실제 오류 구분

## 구현 대상
사용자 지시(2026-09-27): 네이버 플레이스 URL(`.../place/2000513092/review/visitor`)로
"⚡ 데이터 가져오기"를 눌러도 "네이버 플레이스 페이지를 가져오지 못했습니다
(네트워크 오류 또는 존재하지 않는 장소). URL을 다시 확인해 주세요."가 뜨는
이유를 물어봄 → 원인 진단 후 관리자가 오해하지 않도록 안내문을 고쳐달라는
후속 요청.

## 배경/진단
`extractNaverPlaceId`(정규식 `/\/place\/(\d+)/`)는 이 URL에서 ID
`2000513092`를 정상적으로 뽑는다(직접 재현 확인). 실패는 그 다음 단계 —
`https://pcmap.place.naver.com/restaurant/{id}/home`을 서버에서 fetch하는
단계였다. 직접 curl로 재현한 결과:
- 이 ID로 요청 → HTTP 429(Too Many Requests), 서버 헤더 `server: nfront`
  (네이버 WAF)
- 이전에 정상 동작이 확인됐던 다른 place ID로도 동일하게 429 — 즉 이 URL/ID만의
  문제가 아니라 요청을 보내는 IP 자체가 네이버 쪽에서 일시적으로 레이트리밋된
  상태
- 사용자가 실제 운영 관리자 화면에서도 동일한 에러 문구를 재현 확인 — 운영
  서버에서도 같은 현상

기존 코드(`fetchHtmlOrNull`)는 `res.ok`가 아니면 상태 코드를 버리고 무조건
`null`만 반환해, 429(임시 차단)와 진짜 404/URL 오류를 구분하지 못하고 둘 다
"존재하지 않는 장소일 수 있다"는 오해를 주는 문구로 뭉뚱그렸다.

## 변경 사항
`src/app/api/admin/spot-curations/naver-crawl/route.ts`:
- `fetchHtmlOrNull`이 `string | null` 대신 `{ html: string | null; status:
  number | null }`를 반환하도록 변경 — HTTP 상태 코드를 보존한다.
- home/menu 요청이 둘 다 실패했을 때, 그중 하나라도 상태가 429였으면 별도
  안내문("네이버 쪽에서 요청이 너무 많다고 응답했습니다(429). URL은 정상이니
  잠시 후(수 분 뒤) 다시 시도해 주세요.")을 반환한다. 그 외(404, 네트워크
  예외 등)는 기존 안내문을 그대로 유지한다.

## 검증
- `src/app/api/admin/spot-curations/naver-crawl/route.test.ts`(신규 4개):
  (1) 429 응답 시 429 안내문(존재하지 않는 장소 문구 없음), (2) 404 등 일반
  실패는 기존 문구 그대로, (3) fetch 예외로 실패해도 기존 문구 그대로, (4) URL
  자체에서 ID를 못 찾으면 429 여부와 무관하게 400.
- `npx tsc --noEmit` / `npm run test`(206개 파일 2,395개) / `npm run build`
  모두 통과.

## 특이 사항
- 이번 수정은 "정확한 진단 안내"만 제공한다 — 429 자체를 우회하거나 재시도
  로직을 추가하지는 않았다. 재현 결과 짧은 간격(3초)을 두고 재시도해도 동일하게
  429였어서, 서버 쪽에서 즉시 재시도해도 성공할 근거가 없다(오히려 레이트리밋을
  더 자극할 위험). 관리자가 수 분 뒤 직접 재시도하는 것이 지금은 유일한 대응이다.
- 이 문제는 네이버 측 WAF/레이트리밋이라 우리 코드로 근본 해결이 불가능하다 —
  크롤링 빈도를 줄이거나(예: 짧은 시간 내 반복 크롤링 자제) 시간을 두고
  재시도하는 것 외의 회피 방법은 없다.
