# /partner 응답 속도 개선 — 순차 쿼리 병렬화 + 미들웨어 파트너 확인 캐싱

## 구현 대상
사용자 지시(2026-09-23): "지금 /partner 쪽 너무 반응이 느린거 같은데? 데이터가
거의 없는데도 그래.. 원인 확인하고 빠르게 조치해"

## 실측으로 확인한 원인
데이터가 거의 없는 실사용 파트너 계정(`goodguy0515@gmail.com`, "괴산
서울농장")의 실제 세션을 주입해(Playwright + curl 두 방식으로 교차 확인)
nadri-pick.com의 `/partner/today`·`/partner/monthly`를 반복 측정했다.
- 개별 Supabase 호출 자체(직접 supabase-js로 같은 쿼리를 실행)는 전부 빨랐다
  — `auth.getUser()` ~60ms, `partners` 존재 확인 ~150ms, `bookings` 조회
  각 ~100~150ms. 데이터가 적어서 쿼리 자체가 느린 게 아니었다.
- 그런데 실제 페이지 로드는 반복 측정에서 0.6초~2.1초로 편차가 크고 전반적으로
  느렸다. 정적 페이지(`/partner/login`)나 미인증 리다이렉트는 항상 130~200ms로
  일관되게 빨라 순수 네트워크/Vercel 왕복 자체는 문제가 아니었다.
- 원인은 "느린 쿼리 1개"가 아니라 **매 페이지 로드마다 여러 Supabase 왕복이
  순차로 쌓이는 구조**였다:
  1. 미들웨어가 모든 `/partner/*` 요청마다 `auth.getUser()` (인증 확인, 필수) +
     `partners` 존재 여부 조회(온보딩 완료 여부 확인)를 순차로 수행.
  2. `/partner/today` 페이지가 그 뒤에 또 서로 무관한 두 조회(`bookings`,
     `recentProductRows`)를 순차 `await`로 실행.
  서버리스 환경에서 Supabase로의 왕복 하나하나가 개별로는 빨라도, 이런 식으로
  3~4개가 사슬처럼 이어지면 왕복마다의 연결 설정 비용까지 겹쳐 체감 지연이
  크게 불어난다.

## 조치
### 1) `/partner/today` — 독립적인 두 쿼리를 병렬 실행
`src/app/partner/(tabs)/today/page.tsx`: `bookings` 조회와
`recentProductRows` 조회는 서로의 결과에 의존하지 않는데 순차 `await`로 짜여
있었다. `Promise.all`로 병렬 실행하도록 변경 — 이 페이지의 쿼리 시간을
거의 절반으로 줄인다.

### 2) 미들웨어 — 파트너 등록 여부 확인을 쿠키로 캐싱
`src/middleware.ts`: "이 계정이 온보딩을 마쳤는지"는 한 번 확인되면 이
계정이 존재하는 한 절대 바뀌지 않는 사실이다(이 코드베이스에 파트너 행 자체를
삭제하는 기능이 없음을 확인 — HQ도 예약만 삭제 가능). 그런데도 지금까지는
`/partner/*`로 이동할 때마다 매번 `partners` 테이블을 다시 조회하고 있었다.
한 번 확인되면 `partner_verified` 쿠키(값=user.id)에 기록해 두고, 이후
탐색에서는 이 쿠키가 현재 로그인한 사용자와 일치하면 DB 왕복 자체를 건너뛴다.
다른 계정으로 로그인하면 세션이 바뀌어 user.id도 달라지므로 캐시가 자동으로
무효화된다 — 별도 무효화 로직이 필요 없다.

  바꿔 기존 커버리지 범위 밖) / `npm run build` 모두 통과.
- 배포 후 동일한 실측 방식(실제 세션 주입 + 반복 측정)으로 개선 폭을
  재확인할 예정(이 기록 갱신).

## 특이 사항
- `getUser()`(JWT를 Supabase 서버에 다시 검증하는 호출, `getSession()`보다
  느리지만 더 안전함)는 건드리지 않았다 — 이 프로젝트의 RLS 보안 모델 전체가
  미들웨어의 실제 사용자 신원 확인에 의존하므로, 속도보다 보안을 우선했다
  (제3장 제1조 — 사용자 가치/서비스 신뢰성이 개발 편의·속도보다 우선).
- `partner_verified` 캐시는 "온보딩으로 되돌려보낼지" 판단만 건너뛰게 할 뿐,
  실제 예약 데이터 접근은 여전히 RLS(`auth.uid() = partner_id`)가 매 쿼리마다
  강제한다 — 이 쿠키를 조작해도 남의 데이터를 볼 수 있게 되는 경로는 없다.
