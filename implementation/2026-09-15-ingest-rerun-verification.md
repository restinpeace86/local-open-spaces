# 관리자 개별 소스 수동 재수집 기능 실측 검증 및 타임아웃 위험 조치

## 구현 대상
사용자 지시: "관리자화면에서 개별 소스 수동 재수집 제대로 동작하는지 확인해봐
문제 있으면 수정하고" — `/api/admin/ingest/rerun`(GET: 소스 목록, POST: 개별
재수집 실행)과 이를 호출하는 관리자 UI(`IngestRerunPanel`,
`data-grid-client.tsx`)를 실제로 동작시켜 검증.

## 구현 일시
2026-09-15

## 검증 방법
개발 서버를 띄우고 실제 API를 직접 호출해 운영 DB 대상으로 실측했다(단순
코드 리뷰가 아니라 실제 실행 확인).

1. **GET (소스 목록 조회)**: 정상 — daily 4종/monthly 16종이 run-daily.mjs/
   run-monthly.mjs의 실제 STEPS에서 정확히 반영됨을 확인.
2. **POST — daily 소스(SEOUL_YEYAK)**: 정상 동작 — 원본 2,601건 수신,
   2,574건 반영, 에러 0건(COORDINATE_PARSE_FAIL 13건은 좌표 파싱 실패로
   정상적으로 스킵된 것). **다만 응답까지 157초가 걸렸다.**
3. **POST — monthly 소스(SWIMMING_POOL)**: 정상 동작, 16초 만에 완료.
   에러 1,022/2,565건(약 40%)이 처음엔 의심스러워 `docs/pipeline-log.md`의
   과거 기록(2026-08-25, 2026-08-26)을 대조한 결과, 이 소스는 예전부터
   항상 이 정도 비율(1,018~1,022/2,546~2,565)로 "✅ [OK]" 처리되어 온
   기존 특성임을 확인했다(공공/민간 두 API 중복 제거 + 폐업 시설 필터링
   과정에서 자연스럽게 발생하는 수치) — 버그 아님, 조치 불필요.

## 발견한 실제 문제와 조치
`src/app/api/admin/ingest/rerun/route.ts`에 Next.js `maxDuration` export가
없었다. 이 라우트는 원래도(2026-08-30 주석) fetch~upsert를 서버리스 함수
안에서 동기적으로 끝까지 도는 구조라고 명시되어 있었지만, 실제로 얼마나
걸리는지 실측된 적은 없었다 — 이번에 SEOUL_YEYAK 하나만으로도 157초가
걸림을 확인했다. `maxDuration`을 지정하지 않으면 Next.js/Vercel의 플랫폼
기본 실행 시간 제한(통상 수십 초 이내)이 그대로 적용되므로, **실제 운영
(Vercel) 환경에서는 이 버튼이 SEOUL_YEYAK 같은 소스에 대해 거의 확실히
타임아웃(504)났을 것**이다. 로컬 개발 서버에는 이런 제한이 없어 지금까지
드러나지 않았다.

`export const maxDuration = 300;`을 라우트에 추가해 플랫폼이 허용하는
한도까지(Vercel Pro 기준 최대 300초, Hobby 플랜이면 플랫폼이 자체 상한으로
자동 하향 적용 — 안전) 여유를 준다.

## 검증
`npx tsc --noEmit`, `npm run test`(전체 1691개), `npm run build` 모두 통과.
기능 자체는 실제 API 호출로 daily/monthly 각 1개 소스씩 운영 DB 대상 실측
검증 완료.

## 특이 사항
- 매우 큰 소스(주석에 언급된 "12만 건 규모")는 300초로도 부족할 수 있다 —
  이 경우는 기존 코드 주석이 이미 권장하는 대로 CLI(`node scripts/ingest/
  run-daily.mjs --only=<소스>`)로 직접 실행하는 것이 더 안전하다(이번
  조치는 "일반적인 소스"의 안정성을 높이는 것이지, 극단적으로 큰 소스의
  근본 해결책은 아니다 — 근본 해결은 GitHub Actions workflow_dispatch로
  위임하는 것인데 이는 새 PAT 시크릿 발급이 필요해 이 세션이 직접 할 수
  없다는 점이 코드 주석에 이미 명시되어 있다).
