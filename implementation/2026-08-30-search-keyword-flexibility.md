# [개발 요청] 검색창/지도 검색 키워드 유연성 대폭 개선 ('용인 어린이상상' 등 검색 누락 방지)

## 요구사항
1. 부분 일치(ILIKE)/대소문자 무시 검색 적용.
2. 검색 대상 필드 확장(title뿐 아니라 description/address/location_name 등).
3. 공백 정규화 — 유저가 띄어 써도 데이터가 붙어 있으면 매칭.

## 점검 일시
2026-08-30

## 사전 조사 — 실측으로 원인을 특정함

사용자가 준 예시("용인 어린이상상")를 실제 DB에서 직접 조회해 정확한 원인을 규명했다.

### 발견 1: 해당 사례는 텍스트 매칭이 아니라 데이터 자체가 만료됨(정상 동작)
`events` 테이블에서 `title ILIKE '%어린이상상%'`로 찾은 행("용인어린이상상의숲 상상파티시엘"
등)은 전부 `is_active=false`이고 `end_date`가 2022~2024년으로 이미 지났다 — 이벤트픽
GNB 검색(`searchEvents`)은 원래부터 `is_active=true`/`end_date >= 오늘` 조건을 걸고
있어(만료된 행사를 "지금 진행 중"처럼 보여주지 않기 위한 정상적인 필터), 텍스트
매칭을 아무리 완벽하게 고쳐도 이 특정 예시는 여전히 안 나오는 게 맞다 — 버그가
아니다.

### 발견 2(핵심): `open_spaces`에 인덱스 없는 ILIKE가 간헐적 타임아웃을 일으킴
같은 시설이 `open_spaces`(141,980행)에 "용인어린이상상의숲"이라는 실제 시설로 존재한다.
그런데 `name ILIKE '%어린이상상%'`를 인덱스 없이 실행하면 **3.5초 이상 걸리고, 부하가
걸린 시점에는 statement timeout으로 아예 실패**하는 것을 실측으로 재현했다 — "간헐적으로
결과가 누락된다"는 증상과 정확히 일치하는 패턴이다(느린 쿼리는 서버 부하/캐시 상태에
따라 성공하기도 실패하기도 함). `pg_trgm`(PostgreSQL 표준 확장, Supabase 기본 지원)을
설치하고 GIN 트라이그램 인덱스를 추가하니 동일 쿼리가 **80~100ms**로 떨어졌다(35배
이상 개선, 타임아웃 위험 제거).

### 발견 3: `/nearby`(스팟픽) 지도 검색은 클라이언트 필터라 "화면에 보이는 반경 밖"은
애초에 검색 대상이 아님(별도 특이 사항 참고, 이번 지시서 범위 밖)

## 조치

### 1. `scripts/migrations/2026-08-30-add-trigram-search-indexes.sql`
`pg_trgm` 확장 설치 + `open_spaces(name, address)` / `events(title, description,
venue_name)` / `curated_items(title)`에 GIN 트라이그램 인덱스 추가. ILIKE 성능 문제의
근본 원인을 고쳐 "튼튼한" 검색의 전제 조건을 마련했다.

### 2. `src/lib/search/keyword-search.ts` (신규 공유 유틸)
- `splitSearchTokens(query)`: 공백 기준으로 토큰을 나눈다("용인 어린이상상" →
  ["용인", "어린이상상"]). 각 토큰이 (부분 문자열로, 대소문자 무시) 검색 대상 필드
  중 어디에든 존재하기만 하면 매치되도록 하는 것이 핵심이다 — 데이터가
  "용인어린이상상의숲"처럼 붙어 있어도 "용인"과 "어린이상상" 각각이 그 문자열 안에
  부분 문자열로 존재하므로 정상적으로 매치된다(요구사항 3).
- `escapeIlikePattern(value)`: 기존 `/api/admin/data-grid/route.ts`에 있던 로직을
  여러 라우트가 공유하도록 옮겼다 — 검색어에 `%`/`_`가 있어도 와일드카드로 오인되지
  않고 리터럴로 취급된다.

### 3. `searchEvents`(`src/lib/home/get-home-feed.ts`, 이벤트픽 GNB 검색)
`title` 단일 필드 → `title`/`description`/`venue_name` 3개 필드, 토큰마다 `.or()`를
체이닝(각 `.or()` 호출은 이전 필터와 AND로 묶이므로 "모든 토큰이 어느 필드에서든
등장해야 함" 조건이 됨)으로 확장했다(요구사항 1/2/3). `is_active`/`target_audience`/
`category_min`/`end_date` 필터는 그대로 유지했다 — 이들은 "이벤트픽은 유아/어린이/가족
대상 콘텐츠 전용"(2026-08-27 사용자 지시, 명시적 Decision)처럼 텍스트 매칭과 무관한
별도의 콘텐츠 큐레이션 결정이라, 이번 지시서(텍스트 매칭 유연성 개선)만으로 임의로
되돌리지 않았다(제3장 제5조 추측 금지).

### 4. `/api/admin/data-grid/route.ts` (open_spaces/events 검색)
이미 다중 필드(name+address, title+venue_name) OR 검색을 하고 있었으나 검색어 전체를
하나의 패턴으로만 걸었다 — 토큰 단위로 나눠 같은 방식으로 넓혔다. SEOUL_YEYAK 소스
전용 메모리 필터 경로(raw_data JSONB 때문에 SQL이 아닌 JS 필터를 쓰는 특수 경로)도
동일하게 고쳤다.

### 5. `/api/admin/curated-items/route.ts` (큐레이션 상품 검색)
검색어를 이스케이프 없이 그대로 ILIKE 패턴에 꽂고 있던 것(`%`/`_` 리터럴 검색 시
오동작 가능)을 고치고, 토큰 단위 매칭을 적용했다.

### 6. `src/components/map/map-explorer.tsx` (스팟픽 지도 클라이언트 필터)
`name` 한 필드만 검색어 전체로 `.includes()` 하던 것을 `name`+`address` 두 필드,
토큰 단위 매칭으로 넓혔다.

## 특이 사항 — 사용자 확인이 필요한 남은 구조적 이슈

1. **`/nearby`(스팟픽) 지도 검색의 근본적 범위 제한(이번 지시서 범위 밖으로 판단해
   손대지 않음)**: 이 화면의 키워드 검색은 서버 쿼리가 아니라, 현재 지도 중심/반경
   기준 RPC(`get_nearby_spaces_and_events`)가 이미 내려준 항목들을 클라이언트에서
   다시 텍스트로 거르는 구조다 — 즉 **찾으려는 장소가 현재 지도에 보이는 범위 밖에
   있으면, 텍스트 매칭을 아무리 유연하게 고쳐도 애초에 후보 목록에 없어 검색되지
   않는다.** 이것이 "용인 어린이상상"류 검색이 실패하는 더 근본적인 이유일 가능성이
   높다(실제로 이 시설은 open_spaces에 존재하지만, 유저가 다른 지역을 보고 있었다면
   지도 검색으로는 원천적으로 찾을 수 없다). 이번 지시서의 3가지 요구사항(부분
   일치/필드 확장/공백 정규화)은 전부 "텍스트 매칭 방식"에 관한 것이라 이 구조는
   그대로 두었다 — 지도 반경과 무관하게 전국 어디에 있든 이름으로 찾을 수 있는
   서버사이드 스팟 검색(별도 엔드포인트 신설 필요, 이번 트라이그램 인덱스로 성능은
   이미 준비됨)을 원하시면 별도 지시로 진행 가능하다.
2. 이벤트픽 검색의 `is_active`/`target_audience`/`category_min` 필터(2026-08-27 사용자
   지시로 확정된 콘텐츠 큐레이션 정책)를 검색에서도 유지할지, 아니면 "명시적으로
   이름을 검색하는 행위"에는 더 느슨하게 적용할지도 별도 판단이 필요하다 — 이번
   지시서 범위(텍스트 매칭 유연성)를 넘어서는 정책 결정이라 임의로 변경하지 않았다.
