# 블로그 검색 스마트 쿼리 + 텍스트 정규화 + 지역명 하이라이팅/경고 + 뱃지 자동 체크

`implementation/todo.md` [개선사항3] — 블로그 수집/검증 파이프라인 및 관리자
워크벤치의 "지능형 자가 치유 및 텍스트 정규화" 기능.

## 구현 일시
2026-09-07

## 착수 전 확인 질문과 사용자 답변(설계 확정)
원래 todo.md 원문은 "가져온 블로그 본문 텍스트 내에.. 실시간으로 검사"라고만
적혀 있어, 이를 문자 그대로(검색 결과 후보 전부의 본문을 미리 크롤링해 검증)
구현할지, 아니면 이미 확보된 데이터만으로 구현할지 확인이 필요했다 — 전자는
후보 건마다 네이버 블로그 크롤링을 추가로 여러 번 호출해야 해 API 호출량이
크게 늘고 검색이 느려지는 트레이드오프가 있었다.

사용자 답변으로 방식을 확정했다:
- **1차 검색 쿼리**: "현재 상호명가지고 검색하고 있는데.. rgnCdNm/ronaAddr/
  lotnoAddr 등 이미 주소데이터 있지않아? 서울시 노원구라고 하면 상호명 + 노원
  이런식으로" — 원천 주소 필드 대신, open_spaces에 이미 있는 정규화된
  `sigungu_name` 컬럼(예: "서울시 노원구")의 핵심 지역명("노원")을 상호명 뒤에
  붙인다.
- **적합성 검증/하이라이팅**: "가져온 본문 데이터에 대하여 노원 이란 단어가
  포함되어있는지 확인하고 노란색 마크하면돼.. 이건 기존 뱃지들 keyword 체크랑
  같지 않아? .. 가져온 텍스트 데이터에 대하여 하는거니깐 크롤링이 N회
  발생하지 않아" — **추가 크롤링 없이**, 관리자가 이미 열어본(활성 탭) 본문에
  대해서만 지역명 매칭/하이라이팅/경고를 수행한다. 이 판단에 따라 원래
  todo.md의 "미스매치 개수 파악 → 확장 쿼리로 자동 재검색(최대 1~2회)" 자가
  치유 루프는 **이번 구현 범위에서 제외**했다 — 여러 후보의 본문을 미리
  모아야 미스매치 개수를 셀 수 있는데, 그러려면 크롤링이 늘어나 사용자가
  명시적으로 원치 않는다고 밝힌 방향이기 때문이다. 대신 "더 나은 1차 쿼리로
  애초에 성공률을 높이는" 예방적 접근 + "이미 본 데이터로 즉시 경고"하는
  사후 확인 접근으로 실질적으로 같은 목적(미스매치 줄이기/드러내기)을
  달성했다.

## 변경 사항

### 1. 스마트 검색 쿼리 (`src/lib/admin/naver-blog-search.ts`)
- `extractSigunguCoreName(sigunguName)`: "서울시 노원구" → "노원"(마지막 토큰의
  시/군/구 접미사만 제거).
- `buildSmartBlogQuery(name, sigunguName)`: `${name} ${core}` (지역명 없으면
  상호명만).
- `useSpotCurationForm`의 최초 검색이 `spot.name` 대신 이 함수를 쓴다.
  `SpotForCuration`에 옵셔널 `sigungu_name` 필드를 추가했다(기존 호출부가
  안 넘겨도 예전처럼 상호명만으로 동작 — 점진적 적용, 하위 호환).
- `BlogCurationModal`/`MobileCurationWorkbench`가 부모(각각 `RawDataModal`,
  `CategoryMappingPanel`의 RowPicker)로부터 받는 스팟 객체 타입에
  `sigungu_name`을 추가하고, `AdminOpenSpaceRow`/`AdminOpenSpaceRowLite`가
  이미 갖고 있던 값을 그대로 넘기도록 배선했다(새 조회 없음 —
  `OPEN_SPACES_COLUMNS`에 이미 포함돼 있던 컬럼).

### 2. 공백 무시 + 유의어 확장 (`src/lib/admin/curation-badges.ts`)
- 기존 평면 `HIGHLIGHT_KEYWORDS` 배열을 뱃지 키별 `BADGE_KEYWORD_GROUPS`로
  재구성(값은 그대로 파생 — 중복 없음)했다. 4번 요구사항(뱃지 자동 체크)을
  구현하려면 "어느 키워드가 어느 뱃지에 속하는지" 역참조가 필요했기 때문.
- 유의어 추가(todo.md 예시 그대로): "아기의자" 그룹에 "유아용의자"/"유아의자",
  "주차" 그룹에 "차댈곳"/"발렛" 등.
- `highlightKeywords`가 이제 각 키워드를 글자 단위로 `\s*`(선택적 공백)를
  끼워 정규식화해, "아기의자"/"아기 의자"/"아 기 의 자"를 모두 동일하게
  매칭한다.

### 3. 지역/지점명 동시 하이라이팅 + 미스매치 경고 (`blog-reference-viewer.tsx`)
- `highlightKeywords(text, extraKeywords)`로 확장 — 뱃지 키워드 외에 임의
  키워드(지역명)도 같은 방식(공백 무시 포함)으로 하이라이트할 수 있게 했다.
- `useSpotCurationForm`이 `regionKeyword`(스팟의 시군구 핵심명)와
  `hasRegionMismatchWarning`(이미 로드된 본문에 그 단어가 없으면 true)을
  계산해 반환한다 — **추가 API 호출 없이** 기존에 캐시된 `bodyByLink` 상태만
  본다.
- 본문이 로드됐는데 지역명이 없으면 "⚠️ 본문에서 "OOO" 지역명을 찾지
  못했습니다 — 다른 지점 글이 아닌지 확인해주세요" 경고를 보여준다(본문
  로딩 중/실패 시에는 판단 근거가 없어 표시 안 함).

### 4. 키워드 하이라이팅에 따른 뱃지 자동 체크 (세미오토 검수)
- `matchBadgeKeysFromText(text)`: 본문에서 실제 매칭된 키워드들의 뱃지 키
  Set을 반환한다.
- `useSpotCurationForm`에 신규 effect 추가: **신규 등록(기존 큐레이션 없음)
  이고, 아직 한 번도 자동 체크하지 않았을 때만**, 활성 탭 본문이 로드되면
  매칭된 뱃지를 자동 체크한다. 기존 큐레이션을 수정하는 중이면 관리자가
  이미 골라둔 뱃지를 덮어쓰지 않고(경쟁 상태 방지를 위해
  `hasCheckedExistingCuration` 플래그로 "기존 큐레이션 조회가 끝났는지"까지
  확인한 뒤 판단), 탭을 전환해도 다시 체크하지 않는다(딱 1회) — 관리자가
  방금 수동으로 해제한 뱃지가 되살아나지 않게 하기 위함.

## 특이 사항 — 이번에 하지 않은 것
- **자동 재검색(Auto-Refetch) 루프**: 위 "착수 전 확인" 절에서 설명한 대로
  사용자 지시에 따라 구현하지 않았다. 대신 스마트 1차 쿼리로 애초에 성공률을
  높이는 방향을 택했다.
- **재시도 횟수 제한/단계적 쿼리 확장(2차: [상호명]+[시/군/구])**: 위와
  연동된 요구사항이라 함께 범위 밖으로 뒀다. sigungu_name 자체가 이미
  "시/군/구" 단위이므로, 이번 1차 쿼리가 원래 todo.md의 "2차(최종)" 단계와
  사실상 동일한 지역 단위를 쓴다 — 별도 escalation이 필요 없어졌다는 점도
  이번 접근이 실질적으로 커버하는 부분이다.
- 콤보박스(노출 중분류) 변경 시 카테고리별 뱃지/하이라이트 실시간 전환은
  [개선사항4]의 범위라 이번엔 다루지 않았다.
