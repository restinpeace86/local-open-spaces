# 롯데마트 문화센터 변화 감지 ping (경량 매시간 배치)

## 구현 대상
사용자 지시(2026-10-04): "전체 찌르는건 시간 많이 걸리고 성능 많이 걸리는데...
뭔가 1페이지라던가 첫페이지라던가 신규가 생겼던가 변화가 있는지에 대하여
주기적으로 찔러서 변화감지하는거? ... ping 같은 기능이지... 이런거로 확인
실시간 감지 하는건 어렵나?" → "좀더 자주 가져올수 있으면 자주가져오는게
맞아.. 단 가져오는쪽에 성능이슈 줄정도라거나 우리가 봇이라는 걸 알아채게
하면안돼" → "학기 2가지 하지마 지금 가을이니깐 가을학기만해... 수강대상은
일단안넣어도 되는데?"

## 설계 — 사용자와 함께 비용을 실제로 줄여나간 과정
1. 처음 구상: 지점60 × 대상3 × 학기2 = 360개 조합을 1페이지씩 ping → 매시간
   돌리면 360×24 = 8,640건/일(기존 650~700건/일의 12배) — 사용자가 "계산이
   이해 안 된다"고 해서 표로 재설명.
2. 사용자가 두 가지 축소를 제안: (a) 겨울학기(202604) 뺴고 가을학기만, (b)
   대상(target) 필터 자체를 빼기.
3. 둘 다 실측으로 검증:
   - 겨울학기: 60개 지점 중 3곳(103/455/802) 확인 결과 전부 응답 27바이트
     (pageInfo조차 없는 빈 응답) — 겨울학기는 아직 데이터가 전혀 없다.
   - 대상 필터 생략: `search_cls_target=''`로 요청하면 대상 구분 없이
     한꺼번에(성인강좌 포함) 돌려준다 — 실제 페이지 1에서 "성인강좌/유아강좌/
     영아강좌" 카테고리가 섞여 나오는 것까지 확인.
4. 결과: 조합 수 360 → **60**(지점만). 매시간 ping = 60×24 = **1,440건/일**
   (기존의 약 2배 — 사용자가 "자주 가져오는게 맞다"고 한 전제하에 수용 가능한
   수준으로 판단).

## 변경 사항
- `scripts/migrations/2026-10-04-lottemart-culture-club-ping-state.sql`
  (신규, 적용 완료): `lottemart_culture_club_store_ping_state` 테이블 —
  지점별 마지막 ping의 3개 버킷 건수(접수가능/온라인마감/접수마감)를 저장.
- `scripts/ingest/lottemart-culture-club.mjs`: `fetchPage`/`parsePageInfo`/
  `fetchAllForCombo`/`STORES`/`TARGETS`를 export로 전환(제5장 제4조 — ping
  스크립트가 그대로 재사용, 요청/파싱 로직을 두 번 만들지 않음).
  `parsePageInfo`가 기존엔 totalPage만 뽑았는데, pageInfo 문자열("1|18|354|
  34|0|320")의 4~6번째 숫자(접수가능/온라인마감/접수마감 버킷 건수)까지
  함께 추출하도록 확장 — 이 세 버킷은 search_reg_status='1'/'2'/'3' 필터와
  1:1 대응하며(2026-10-03 실측 확인 당시 알아낸 것), 개별 강좌의 상태
  전환(예: 전화문의→바로신청)이 일어나면 두 버킷의 합계가 같이 바뀐다 —
  그래서 이 숫자 3개만 비교해도 "지점 내 뭔가 바뀜"을 감지할 수 있다.
- `scripts/ingest/lottemart-culture-club-ping.mjs`(신규): 60개 지점을
  순회하며 1페이지만 조회 → 버킷 3개 비교(`hasChanged`) → 바뀐 지점만
  `fetchAllForCombo`로 대상 2/3/4 전체 재수집해 upsert. 처음 보는 지점(ping
  기록 없음)은 무조건 "변화"로 간주해 기준값을 세운다.
- `.github/workflows/lottemart-culture-club-ping.yml`(신규): 매시간 7분에
  실행(정각이 아니라 7분 — "봇처럼 보이면 안 된다"는 지시를 반영해 기계적인
  정시 패턴을 피함). timeout 30분.
- `scripts/ingest/lottemart-culture-club.test.mjs`: `parsePageInfo` 확장
  검증 2개 추가.
- `scripts/ingest/lottemart-culture-club-ping.test.mjs`(신규): `hasChanged`
  4개 테스트(최초 지점/무변화/버킷별 변화 감지).

## 검증
- `npx tsc --noEmit` / `npm run test`(269개 파일 2,801개, 신규 6개 포함) /
  `npm run build` 전부 통과.
- **실제 라이브 ping 1회 전체 실행**(dry-run 아님) — 첫 실행은 모든 지점이
  "처음 봄"이라 전부 변화로 간주돼 60개 지점 전체 재수집이 일어난다(기존
  일일 배치와 동일한 비용, 1회성 기준값 수립 과정). 이후 ping부터는 실제로
  바뀐 지점만 재수집되므로 비용이 크게 줄어든다 — 다음 실행에서 재수집
  건수가 크게 줄어드는지 추가로 확인 예정.

## 특이 사항 — 트레이드오프를 사용자가 명시적으로 수용
- 대상(target) 필터 없이 요청하면 성인강좌도 같이 세어지므로, **성인강좌만
  바뀌어도 그 지점이 "변화"로 오탐될 수 있다.** 오탐 비용은 "그 지점 1곳
  재수집"(수백 건 upsert) 정도로 작고, 대상별로 ping을 쪼개 조합을 다시
  180~360개로 늘리는 것보다 훨씬 가볍다 — 사용자가 이 트레이드오프를 직접
  제안하고 수용했다.
- 겨울학기는 현재 ping 대상에서 완전히 빠져 있다. 겨울학기 데이터가 실제로
  올라오기 시작하면(기존 일 1회 전체 배치 lottemart-culture-club.mjs는
  이미 두 학기 다 수집하고 있어 거기서 먼저 잡힘) `CURRENT_SEMESTER` 상수를
  수동으로 넓혀야 한다 — 학기 전환을 자동 감지하는 로직은 이번 범위에
  넣지 않았다(제5장 제7조 — 필요 이상으로 설계하지 않음).
