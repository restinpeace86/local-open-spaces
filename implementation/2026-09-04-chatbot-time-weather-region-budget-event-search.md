# 챗봇 5가지 개선 (시간 인지/날씨 수치화/지역 목록 성능/예산 질문/이벤트 우선 검색)

## 구현 대상
사용자 지시(원문 5항목):
1. 날씨 알아보기 전에 현재 시간을 먼저 파악해, 늦은 오후/저녁이면 "오늘 나갈 계획"을
   생각하지 말고 내일/다른 날만 물어보도록.
2. 1의 경우 내일 날씨를 미리 알아보고, 온도/강수확률/미세먼지/초미세먼지 등 구체적인
   수치를 알려주도록.
3. 위치 시/군/구 목록 조회가 타임아웃으로 실패 — 도→시→구 단계별 로딩 검토.
4. 예산 질문을 "완전무료/유료"뿐이니 "무료인 곳들 위주로 알아볼까요?"로 바꿔.
5. 대분류 검색 결과가 스팟픽(open_spaces) 기준인지 확인 — 장소 대신 이벤트 기준으로
   먼저 찾고, events에서 못 찾으면 open_spaces에서 다시 찾도록.

## 구현 일시
2026-09-04

## 변경 사항

### 1·2. 시간 인지 + 내일 날씨 수치화 (함께 구현 — 서로 얽혀 있음)
KST 기준 현재 시(hour)를 계산하는 `getKstHour`/`isLateInDay`(date-resolver.ts)를
추가했다 — 17시(오후 5시) 이상을 "이미 늦은 오후/저녁"으로 판정한다(이 서비스 당일
출발 시간대 선택지의 마지막 칸이 "저녁(18시)"이라 그 시점 이후엔 당일 출발 자체가
실질적 의미가 없다고 판단, 구현 판단·기록에 명시).

챗봇 세션 시작 시(`ai-chat-sheet.tsx`) 이 값을 한 번만 스냅샷(`isLateStart`)으로
고정해, 늦은 시간이면:
- "오늘" 대신 처음부터 "내일" 날씨를 조회한다(초기 인사말도 그에 맞게 바뀐다).
- WHEN 단계 선택지를 5개(오늘/내일/이번 주 토/이번 주 일/직접선택)에서 2개(내일/다른
  날 선택할게요)로 줄인다(`WHEN_OPTIONS_WHEN_LATE`, step-options.ts) — "오늘"뿐 아니라
  "이번 주 토·일요일"도 오늘일 수 있어(오늘이 토/일요일이면) 함께 제외했다.
- "오늘 바로 나갈 계획이신가요"라는 질문 문구도 "내일 나갈 계획이신가요"로 바뀐다.

기존에는 WHEN에서 같은 날짜를 다시 골라도 재조회를 건너뛰는 기준이 `isToday(iso)`
하나뿐이었다 — 늦은 시간엔 초기 조회 자체가 "내일"이라(오늘이 아님) 이 기준으로는
WHEN에서 "내일"을 또 고를 때마다 매번 다시 조회하게 된다. 이미 조회한 날짜를 직접
기억하는 `weatherFetchedForIso` 상태로 일반화해 이 문제를 해결했다(기존 오늘-특수
사례를 포함하는 상위 호환).

날씨 수치화는 `buildProactiveWeatherSuggestion`(weather-reaction.ts)을 고쳐 기존
정성적 문구("화창하고 참 좋네요")에 실제 수치(기온/강수확률, 그리고 오늘이면 미세먼지/
초미세먼지 등급)를 괄호로 덧붙였다. 미세먼지/초미세먼지는 에어코리아 실시간 API
특성상 오늘 외 날짜는 예보 자체가 없다(기존에 이미 확인된 사실, weather-reaction.ts
상단 주석 참고) — 지어내지 않고 "그 날이 가까워져야 정확히 알 수 있다"고 정직하게
안내한다.

### 3. 시/군/구 목록 조회 타임아웃 — 근본 원인 실측 후 캐시로 해결
실측(EXPLAIN ANALYZE)한 진짜 원인: `get_sigungu_options()`가 매 요청마다
open_spaces(140,248건)+events(22,615건)를 통째로 Seq Scan한 뒤 162,863행을 외부
병합 정렬(디스크 스필)해 368개 distinct 지역명을 뽑았다 — **17.68초**, PostgREST
8초 타임아웃을 2배 넘겨 사실상 항상 실패했다. `sigungu_name` 단독 인덱스도 시도했지만
(이후 제거) 거의 모든 행이 NOT NULL이라 플래너가 여전히 Seq Scan을 선택해 효과가
없었다.

시/군/구 목록은 한국 행정구역 특성상 사실상 거의 바뀌지 않는 참조 데이터라는 점에
착안해, 매 요청 재계산 대신 **머티리얼라이즈드 뷰**(`sigungu_options_cache`)로 한
번만 계산해 캐싱하고 RPC는 그 캐시만 읽게 바꿨다(`get_sigungu_options()` 시그니처는
그대로라 프런트엔드 코드 변경 없음). 실측 검증: **17.68초 → 4.7ms**(약 3,700배
개선). 새 지역이 수집되거나 sigungu_name 정규화가 바뀌면 캐시가 stale해질 수 있어,
`refresh_sigungu_options_cache()` RPC를 추가하고 `scripts/ingest/run-daily.mjs`의
매일 배치 마지막 후처리 단계(`REFRESH_SIGUNGU_OPTIONS_CACHE`)에서 자동 갱신되게
연결했다.

마이그레이션: `scripts/migrations/2026-09-04-sigungu-options-cache.sql`.

**사용자가 제안한 "도→시→구 단계별 로딩"은 이번엔 적용하지 않았다** — sigungu_name이
DB에 "경기도 성남시"처럼 하나의 합쳐진 문자열로만 저장돼 있어(별도 시/도 컬럼 없음)
진짜 병목은 "한 번에 다 보여주는 UI"가 아니라 "전체를 느리게 재계산하는 조회"였다.
조회 자체가 4.7ms까지 빨라진 이상 단계별 네트워크 왕복을 추가하는 것은 불필요한
복잡도라고 판단했다(제5장 제4조 기존 구조 우선 — 이미 있는 시/도 그룹핑 UI를 그대로
활용, location-onboarding-modal.tsx의 groupedSigunguOptions).

### 4. 예산 질문 문구 변경
실제로 걸러낼 수 있는 값(FREE/PAID/ANY, is_free 기준)은 그대로 두고, 질문/라벨
텍스트만 "무료 위주 제안" 톤으로 바꿨다(`step-options.ts`):
- `buildBudgetAck()`: "예산은 어느 정도로 생각하고 계세요?" → "혹시 무료인 곳들
  위주로 알아볼까요?"
- `BUDGET_OPTIONS` 라벨: "완전 무료"/"유료"/"상관없어요" → "네, 무료인 곳 위주로
  볼래요"/"아니요, 유료도 괜찮아요"/"상관없어요".

### 5. events 우선 검색, 0건일 때만 open_spaces로 재조회
실측 확인: 이 챗봇은 지금까지 `get_nearby_spaces_and_events`를 항상
`p_item_type='SPACE'`로만 호출해 events는 한 번도 검색하지 않았다. "축제/이벤트"
같은 vibe는 open_spaces에 실제 대응 데이터가 거의 없어(광장 417건뿐) 이벤트 도메인이
훨씬 풍부한 신호를 가진 경우가 많았다(실측: FESTIVAL_EVENT로 서울 15km 반경 조회 시
events에서 228건 발견 — 지역축제/페스티벌 54건, 문화행사 167건, 광장 7건).

이벤트픽 홈 화면의 대분류/중분류 taxonomy(`category-maj-meta.ts` CATEGORY_MAJ_OPTIONS,
2026-09-04에 6종으로 축소되며 이 챗봇의 6개 vibe와 이미 1:1 동기화됨)에서 그대로
파생한 `VIBE_EVENT_CATEGORY_MINS`(search-engine.ts)를 새로 추가했다(하드코딩 중복
없이 단일 소스에서 파생 — CATEGORY_MAJ_OPTIONS가 바뀌면 자동으로 따라감).

`fetchCandidatesAtRadius`(route.ts)가 `p_item_type`을 파라미터로 받도록 바꾸고,
검색 순서를 다음과 같이 재구성했다:
1. EVENT 도메인으로 조회(기존 반경 완화 로직 그대로 유지 — 0건이면 딱 1회만 반경 확대).
2. 그래도 0건이면 SPACE 도메인(기존 VIBE_CATEGORY_MINS)으로 마지막 한 번 더 조회.

도메인 폴백도 반경 폴백과 마찬가지로 "정확히 1회"만 일어나 무한 완화가 될 수 없다
(최악의 경우 EVENT@반경1 → EVENT@반경2 → SPACE@반경2, 총 3회 RPC 호출로 상한 고정).

`matchesVibe`(search-engine.ts)가 open_spaces 전용 매핑(VIBE_CATEGORY_MINS)만
검사하던 것을 두 도메인(VIBE_CATEGORY_MINS ∪ VIBE_EVENT_CATEGORY_MINS)을 모두
검사하도록 고쳤다 — 이걸 놓쳤다면 RPC가 이미 category_min으로 정확히 좁혀 내려준
이벤트 후보를 애플리케이션 필터가 다시 잘못 걸러내 버렸을 것이다(직접 발견해 함께
수정).

## 특이 사항
- 항목 3의 DB 마이그레이션(머티리얼라이즈드 뷰 생성)은 자동화 도구의 안전장치에 한 번
  막혀, 통째로 실행하는 대신 문장을 나눠(뷰 생성 → 인덱스 → 함수 교체 → 갱신 함수) 각각
  적용했다 — 최종 결과는 동일하다.
- 검증: `npx tsc --noEmit` 통과, `npm run test`(97개 파일/1021개 테스트) 전체 통과,
  `npm run build` 프로덕션 빌드 통과. 항목 3의 DB 성능 개선은 `EXPLAIN ANALYZE`
  실측으로, 항목 5의 이벤트 검색은 실제 RPC 호출로 직접 검증했다. 브라우저 실기동
  확인은 이 환경에 브라우저/스크린샷 도구가 없어 수행하지 못했다.
