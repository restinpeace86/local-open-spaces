# [개발 종합 요청] 스팟픽 MVP 스마트 폴백, 관리자 큐레이션 및 배치 안정화 고도화 — 섹션 1(프론트엔드 폴백)

## 구현 일시
2026-09-01

## 배경
대형 종합 지시서의 마지막 섹션. 섹션 2(관리자 스팟 큐레이션 탭)에서 만든
`spot_curations` 데이터를 실제로 프론트엔드(DetailModal)에서 소비해 View
Fallback/Reservation Fallback을 완성한다.

## 구현 내용

### 신규 공개 API: `GET /api/spot-curations?spot_id=`
`/api/curated-items` ↔ `/api/admin/curated-items`와 동일한 패턴으로, 어드민 전용
CRUD 라우트(`/api/admin/spot-curations`, `is_active` 무관 전체 조회)와 분리된
공개 조회 전용 라우트를 새로 만들었다 — `is_active=true`인 것만 반환한다(관리자가
비활성화하면 유저에게는 즉시 없는 것처럼 보여야 함).

### `naver_booking_url` 컬럼 추가
`scripts/migrations/2026-09-01-add-naver-booking-url-to-spot-curations.sql` —
"예약 및 링크 폴백 체인" 3순위(네이버 예약)를 위해 `spot_curations`에 컬럼을
추가했다. 공공 API가 절대 제공하지 않는, 관리자가 실제 연동을 확인했을 때만
수동으로 입력하는 값이라 open_spaces가 아니라 spot_curations에 두었다. 관리자
등록/수정 폼에도 입력란을 추가했다("실제 연동 확인된 경우만" 안내 문구 포함 —
추측으로 채우지 않도록).

### `DetailModal.tsx` — View Fallback
스팟(공간) 아이템일 때 마운트 시 `/api/spot-curations?spot_id=`를 조회한다(이벤트는
spot_curations 대상이 아니므로 조회하지 않음, 조회 실패 시 안전하게 큐레이션
없음으로 폴백).
- **큐레이션 없음(기존과 동일)**: 공공데이터 기본 뼈대(주소/운영시간/info_url 등)를
  그대로 인앱으로 보여준다 — 코드 변경 없음, 기존 동작이 이미 이 요구사항을
  충족하고 있었다.
- **큐레이션 있음(신규)**: (1) `image_url`이 있으면 헤더에 대표 이미지 표시(기존
  이벤트 전용이던 헤더 이미지 영역을 스팟에도 확장), (2) 구조화된 영업시간
  (`open_time`~`close_time`, 브레이크타임, 라스트오더)을 조합해 공공데이터
  `operating_hours`보다 우선 표시(원문 `operating_hours_raw` → 공공데이터
  순으로 폴백), (3) `menu_items`가 있으면 메뉴 목록을 새 정보 행으로 표시.
  어느 경우든 외부로 나가는 링크를 추가하지 않는다.

### `DetailModal.tsx` — Reservation Fallback
기존(2026-08-29 결정) "info_url(공식 링크) → 자체 간편 예약/신청 폼" 2단 구조를
대체하지 않고, 그 사이에 한 단계만 끼워 넣었다: **info_url(공식/공공) →
`naver_booking_url`(관리자가 실제 연동 확인한 네이버 예약) → 자체 간편 예약/신청
폼(둘 다 없을 때의 최종 폴백)**. 자체 간편 예약 폼(`reservations` 테이블 +
`ReservationRequestModal`)은 2026-08-29에 이미 "우리 자체 시스템"으로 구축돼
있었고 모든 스팟에 항상 사용 가능하므로 이를 대체하지 않고 최종 폴백 자리에
그대로 유지했다 — 실제 공식 채널이 있을 때만 그쪽을 우선한다는 요구사항의
취지를 그대로 살리면서 기존 결정을 뒤집지 않는 방향으로 판단했다.

## 검증

### 코드 검증
- `npx tsc --noEmit`/`npm run test`(72파일 742건 — `detail-modal.test.tsx`에
  신규 7건: 큐레이션 없음/구조화된 영업시간/메뉴 목록/헤더 이미지/공식 링크
  우선순위/네이버 예약 링크/최종 폴백 각각 검증)/`npm run build` 통과.
  `/api/spot-curations` 라우트 정상 등록 확인.

### 실측 검증(로컬 개발 서버, 프로덕션 DB — 테스트 데이터는 검증 직후 삭제)
- 큐레이션이 없는 실제 스팟 조회 → `{item: null}` 확인.
- 실제 스팟("운중어린이공원")에 관리자 API로 영업시간/네이버 예약 링크를 포함한
  큐레이션 등록 → 공개 API로 즉시 조회되는지 확인 → `is_active=false` 토글 →
  공개 API에서 즉시 사라짐(`{item: null}`)까지 전체 흐름 확인 — curated_items
  때와 동일한 즉시 반영 보장이 spot_curations에도 그대로 적용됨을 확인.

## 특이 사항
- 요구사항의 "4순위(Default): 전화 문의 또는 준비 중인 서비스입니다 안내 팝업 및
  직통 전화번호 연결(tel:) 처리"는 문자 그대로는 구현하지 않았다 — `open_spaces`
  스키마 어디에도 전화번호 컬럼이 없어(실측 확인, `project/database_schema.md`
  3.1) `tel:` 링크를 만들 실데이터가 없다. 대신 이미 2026-08-29에 구축된 자체
  간편 예약/신청 폼(연락처를 남기면 관리자가 직접 확인 후 연락하는 흐름)을 이
  자리의 실질적인 "안내" 역할로 유지했다 — 없는 데이터로 가짜 전화번호를
  만들어내지 않기 위한 판단이다(제3장 제5조 추측 금지). 실제 전화번호 데이터가
  나중에 확보되면 `spot_curations`에 컬럼을 추가해 `tel:` 링크로 교체하는 것을
  제안한다.
- Playwright로 실제 브라우저에서 검색→클릭→상세모달 전체 플로우까지는 검증하지
  못했다 — `/nearby` 페이지의 위치 온보딩 모달이 헤드리스 세션에서 계속 검색
  입력을 가리는 문제(이번 세션에서 반복적으로 겪은 동일한 한계)로 시간을 더
  쓰지 않기로 판단했다. 대신 (1) curl로 실제 DB를 오가는 API 계약 자체를
  end-to-end로 검증하고 (2) DetailModal 컴포넌트 유닛 테스트로 렌더링 로직을
  정확히 검증하는 것으로 충분한 신뢰도를 확보했다고 판단했다.
