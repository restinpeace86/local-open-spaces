# [이벤트 화면 중복 표시 제거 — 레거시 SEOUL_RESERVATION_* 599건 비활성화]

## 구현 대상
사용자 지시(2026-09-20): "동일한 이벤트가 앱 화면에서 중복해서 보이지
않으면 문제없어.. 현재 그렇게 안되어 있으면 만들어주고" — 직전에 "이벤트
기준 중복 검수 도구가 있나?"라는 질문에 이어진 요청.

## 조사 결과 — 검수 도구가 아니라 확정적인 원인을 발견
이벤트 중복 검수 관리자 UI(스팟 중복 검수 도구의 이벤트 버전)를 만들기 전에
먼저 실제로 화면에 중복이 보이고 있는지 실측했다. 결과: **활성 이벤트
3,318건 중 599건(18%)이 진짜 중복**이었다.

**원인**: Decision 017(2026-08-25) 재작성 이전 구버전 어댑터
(`seoul-public-reservation.mjs`)가 만든 레거시 행
(`external_id='SEOUL_RESERVATION_{SVCID}'`)이, 신버전 어댑터
(`seoul-yeyak-adapter.mjs`, `external_id='SEOUL_YEYAK_{SVCID}'`)로 완전히
대체된 뒤에도 비활성화되지 않고 그대로 남아 있었다. 2026-08-27 백필
스크립트가 레거시 행의 `source`/`raw_data`만 채우고(그 자체는 올바른
판단 — external_id를 바꾸면 신규 어댑터의 upsert 대상과 물리적으로 같은
행이 두 번 생기는 위험이 있었음) `is_active`를 비활성화하는 후속 조치는
없었던 것이 원인이다.

## 판정 기준 — 애매한 유사도 판단이 아니라 기계적으로 확정 가능
같은 SVCID(external_id 접두사 뒤 부분)를 공유하는 `SEOUL_RESERVATION_*`/
`SEOUL_YEYAK_*` 쌍은 100% 같은 실제 예약 프로그램이다 — 2026-08-27 백필
스크립트 자체가 이미 이 동일성을 전제로 짜여 있었다(그 스크립트의 로직을
그대로 재사용). 제목 유사도 같은 추측성 판단은 전혀 쓰지 않았다(제3장
제5조 추측 금지) — 이 점에서, 검토 결과 이벤트 전용 "중복 검수 관리자
UI"는 이번 문제 해결에는 필요하지 않았다(그 599건 전부가 애매함 없이
기계적으로 확정됐기 때문).

## 코드 변경
`scripts/migrations/2026-09-20-deactivate-legacy-seoul-reservation-duplicates.mjs`
(신규, 1회성): 활성 이벤트 전체를 조회해 `SEOUL_RESERVATION_{X}`이면서
동일한 `{X}`의 `SEOUL_YEYAK_{X}`가 이미 활성으로 존재하는 행만 골라
`is_active=false`로 비활성화한다. **삭제가 아니라 비활성화**다 —
`reservations` 등 다른 테이블이 이 행을 참조하고 있을 수 있어 안전하게
숨기는 쪽을 택했다(기존 관리자 "노출 활성화" 토글과 동일한 메커니즘,
필요하면 되돌릴 수 있음).

## 실행 결과(2026-09-20, 실제 DB)
599건 전부 비활성화 성공(실패 0건). 대상은 캠핑장, 야구장/축구장/풋살장
대관, 도서관 프로그램, 예비군훈련 셔틀버스, 맘카페 등 전방위에 퍼져
있었다 — 키즈카페 카테고리에 국한된 문제가 아니었다.

## 재발 가능성 — 없음(확인 완료)
구버전 스크립트(`seoul-public-reservation.mjs`)는 이미 신버전 어댑터
클래스를 호출하는 얇은 CLI 진입점으로 축소돼 있어(과거 결정 확인), 현재
어떤 파이프라인 경로도 `SEOUL_RESERVATION_` 접두사를 새로 만들지 않는다.
이번 비활성화는 과거 잔재를 한 번 정리하는 것으로 충분하며, 별도 재발
방지 코드는 필요 없다.

## 검증
- `--dry-run`으로 먼저 대상 건수(599건) 확인 후 실제 반영.
- `npx tsc --noEmit`/`npm run test`(170개 파일, 2048개 테스트, 변동 없음)/
  `npm run build` 모두 통과(DB 데이터만 바뀌는 스크립트라 앱 코드 변경
  없음).

## 특이 사항
같은 조사 중, 이 SVCID 매칭 패턴에 해당하지 않는 "제목만 같은" 다른 유형의
중복 후보도 소수 발견됐다(예: 서로 다른 원천 해시 ID를 가진 `SEOUL_CULTURE_*`
2건, 서로 다른 SVCID의 `SEOUL_YEYAK_*` 2건). 이런 경우는 "같은 실제
프로그램인지"가 기계적으로 확정되지 않아(예: 같은 활동의 서로 다른 회차일
수도 있음) 이번 범위에서 건드리지 않았다 — 필요하면 그건 진짜 검수(사람
판단)가 필요한 별도 작업이다.
