# [가격 큐레이션 소스1: 독립 블로그 검색 + 검색어 노출/재검색 UI]

## 구현 대상
사용자 지시(2026-09-16, 직전 소스1 수정에 이어): "1관련하여 블로그 큐레이션
소스에 대하여 어떤 걸로 검색했는지도 좀 표시해줘... 정말 맞는 검색어를 던져서
블로그 서치했고 봤는지 확인하게... 그리고 블로그 큐레이션 기존꺼 처럼 좀
이상한 검색어 던진거면 내가 수동으로 수정해서 다시 한번 던져보게"

사전 확인 질문(사용자 응답: "완전 독립 검색으로 교체"): 직전 수정에서 소스1이
기존 "🔍 블로그 큐레이션" 모달이 미리 선택해 둔 `curated_blog_urls`를 크롤링하는
구조였는데, 이 커브(그 모달을 아직 안 썼거나 검색어가 나빴던 이벤트는 소스1이
전혀 동작하지 않음)를 없애기 위해 `curated_blog_urls` 의존을 완전히 제거하고
가격 큐레이션 화면 안에서 독립적으로 검색하기로 결정.

## 구현 일시
2026-09-16

## 변경 사항
### `src/app/api/admin/events/price-candidates/route.ts`
- `curated_blog_urls` select/사용을 완전히 제거.
- `title`, `sigungu_name`을 추가로 select해 `buildSmartBlogQuery(title, sigunguName)`로
  기본 검색어를 계산(기존 "블로그 큐레이션" 모달과 동일한 규칙 재사용, 제5장
  제4조).
- `?blog_query=`로 관리자가 직접 지정한 검색어가 있으면 그것을 우선 사용.
- `searchBlogs(query)` 신규: NAVER API HUB 블로그 검색(blog-search 라우트/
  llm-verify 라우트와 동일한 엔드포인트·인증 헤더, sort=date, 최대 3개)을 이
  라우트 안에서 직접 호출.
- 검색 결과 각 URL의 본문을 크롤링(`fetchBlogBody`, 직전 수정에서 만든 것 그대로
  재사용)해 `buildBlogCandidate`에 전달 — 이 순수 함수는 URL 출처가
  `curated_blog_urls`든 실시간 검색이든 상관없이 그대로 재사용 가능해 변경이
  필요 없었다.
- 응답에 `blogSearch: { query, items }`를 추가해 실제 사용된 검색어와 찾은
  블로그 목록(가격 발견 여부와 무관하게 전부)을 그대로 실어 보낸다.

### `src/components/admin/event-price-curation-modal.tsx`
- 신규 `BlogSearchControls` 컴포넌트: 검색어 입력창 + "🔄 다시 검색" 버튼 +
  검색된 블로그 목록(제목/블로거명/작성일)을 소스1 카드 안에 표시.
- 최초 로드 시 서버가 계산한 기본 검색어로 입력창이 채워지고, 관리자가 수정 후
  "다시 검색"을 누르면 `?blog_query=`를 붙여 재요청 → 4개 소스 전체를 새로
  받아와 갱신(소스1만 바뀌지만 한 번의 GET으로 나머지 3개도 최신 상태 유지,
  구현 단순성 우선).

### 테스트
- `event-price-curation-modal.test.tsx`에 2개 신규: (1) 검색어/검색 결과 목록이
  화면에 표시되는지, (2) 검색어를 수정하고 "다시 검색"을 누르면 실제로 그
  검색어(`encodeURIComponent`된 `blog_query`)로 재요청해 결과가 갱신되는지.
